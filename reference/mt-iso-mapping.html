MT to ISO 20022 Mapping Reference

Cross-border payments are moving from SWIFT MT messages to ISO 20022 MX messages. This page is the field-level reference for that move. It covers the message pairs a business analyst meets most often, the MT103 to pacs.008 field mapping in detail, what is lost in translation, the character sets, and how to validate an MX message against its schema. Message versions are stated where they are fixed by the CBPR+ usage guidelines. Where a version depends on the scheme or the receiving bank, the page says so.

How to read this page

MT is the SWIFT FIN message format: fixed fields, tagged blocks, and the SWIFT X character set. MX is the ISO 20022 XML format: named elements in a defined order, validated against an XML schema, and written in UTF-8. A mapping is never a word-for-word translation. Some MT fields have an exact MX element, some map to a different element with a narrower meaning, and some have no MX equivalent at all. The tables below mark each case. Always check the current CBPR+ usage guidelines and the receiving bank's own usage guidelines before treating a mapping as final, because usage guidelines can restrict an element that the base schema leaves open.

What a BA must check in this table

Three checks catch most migration defects. First, confirm which elements the receiving bank treats as mandatory, because the schema and the usage guideline disagree on several fields. Second, confirm the version of pacs.008 the receiver expects, because element names and cardinalities change between versions. Third, test the fields that have no direct equivalent, :53a: and free-text :72:, because those are the fields that silently lose data.

Translation from MT to MX is lossy. The table below lists the losses a BA must document, because each one can change what the beneficiary sees or what an intermediary bank can screen.

Character sets: SWIFT X versus ISO 20022 UTF-8

MT messages use the SWIFT X character set. It contains the letters a to z in both cases, the digits 0 to 9, and the characters slash, hyphen, question mark, colon, open and close brackets, full stop, comma, apostrophe, plus sign, space, and carriage return with line feed. Nothing else is permitted in an MT message. ISO 20022 messages are XML in UTF-8, which can represent accented letters, non-Latin scripts, and symbols that the X set cannot.

That difference is a real migration problem. A beneficiary name with an accented letter, such as a name containing an e with an acute accent, is valid in pacs.008 but cannot be written in an MT103. A name in a non-Latin script, such as Chinese or Arabic characters, is valid in UTF-8 but cannot be written in MT at all. When a payment moves from MX to MT, or when an MX message is generated from data that was stored for MT, the characters outside the X set must be handled, and the handling must be agreed in advance.

Banks handle this in three ways. The first is transliteration: replacing an accented or non-Latin character with the nearest X set equivalent, for example writing an accented e as a plain e. The second is rejection: refusing the payment at the point of entry and asking the customer to resubmit with characters the channel supports. The third is a mapping table held by the bank, which converts specific characters consistently so the same customer name is always written the same way. What a bank must never do is silently drop the character or replace it with a blank, because the name on the payment then no longer matches the name on the account or on a sanctions list, and that mismatch can cause a screening hit or a failed beneficiary match at the receiving bank.

A BA documenting this should record: which characters the source system can store, which characters the sending channel accepts, what the transliteration rule is, and what happens to a payment that contains a character with no agreed transliteration. That record is part of the migration specification, not a footnote.

XML namespaces and schema validation

Every ISO 20022 message carries a namespace that identifies the message and its version. The namespace is a URN, and it must match the schema the message is validated against. The three namespaces used most often in cross-border payments are:

MessageNamespace URN
pacs.008.001.10urn:iso:std:iso:20022:tech:xsd:pacs.008.001.10
pacs.009.001.08urn:iso:std:iso:20022:tech:xsd:pacs.009.001.08
camt.053.001.08urn:iso:std:iso:20022:tech:xsd:camt.053.001.08

Schema validation has four steps. First, check the namespace on the document element matches the expected URN for the message and version. Second, validate the XML against the published XSD for that version, using a validating parser. Third, validate against the usage guidelines, which add rules the schema cannot express, such as which optional elements are mandatory in practice and which code values are permitted. Fourth, validate the business rules, such as checking that the BIC is well formed and that the currency code is a valid ISO 4217 code.

The common validation failures are: a wrong namespace, usually because the message was built against one version and validated against another; a missing mandatory element, usually a debtor name or a charge bearer code that the usage guideline requires; elements in the wrong order, because ISO 20022 schemas require elements in sequence order and a message built from a flat file often gets the order wrong; an invalid BIC format, such as a BIC that is not 8 or 11 characters or that has invalid characters in the country or location positions; and an amount with too many fraction digits for the currency, such as three decimal places for a currency that allows two. A validation failure must be reported back to the sender with the element path and the rule that failed, so the sender can fix the source data rather than patching the message by hand.

Version discipline

Never hard-code a single message version into a specification without naming the usage guideline it comes from. CBPR+, SEPA, and a domestic high-value system can each use a different version of pacs.008, and a message built to one version will fail validation against another. The specification should name the message, the version, the usage guideline, and the date that guideline was published.
