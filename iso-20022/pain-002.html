pain.002: Customer Payment Status Report

pain.002 is the ISO 20022 message a bank sends to its customer to report the status of payments instructed in a pain.001 file. It tells the customer whether each payment was accepted, rejected, pending or completed, with reason codes for any failure. Corporates use it to reconcile payment files, fix rejected items and confirm salaries and supplier payments reached the bank.

At a glance

  • Message: pain.002
  • Title: Customer Payment Status Report
  • Current version: pain.002.001.10
  • Versions: pain.002.001.03, pain.002.001.10, pain.002.001.12
  • Fields: 12 (3 mandatory, 9 optional)

Participants

The sending participant is the bank that received the pain.001 file (the debtor agent). The receiving participant is the customer that sent the file (the initiating party), which uses the report to reconcile its payments.

Structure

pain.002 is an ISO 20022 XML message with a GroupHeader (GrpHdr) followed by OriginalGroupInformationAndStatus (OrgnlGrpInfAndSts) for the whole file, then OriginalPaymentInformationAndStatus (OrgnlPmtInfAndSts) per block and TransactionInformationAndStatus (TxInfAndSts) per payment. Each status block carries a status code and, where needed, StatusReasonInformation (StsRsnInf).

Scheme rules

pain.002 is a base ISO 20022 message: the structure and fields below are the base definition, and each scheme adds its own rules for its rail. Under SEPA the status report must use the SEPA reason codes for rejected payments, and the bank must report the group status before the customer can treat the file as accepted. Banks may also agree bilateral reporting times and file delivery channels with each customer on top of the scheme rules.

Fields

FieldNameMandatoryDescription
GrpHdrGroup HeaderMThe header with message identification, creation date and time and initiating party. It identifies the status report and links it to the bank that produced it. The customer uses it to match the report to its own systems and to detect a duplicate or out of sequence status report.
OrgnlGrpInfOriginal Group InformationMInformation about the original pain.001 group, including its message identification and the group status. It tells the customer which file this report refers to. The group status can be accepted, partially accepted or rejected, and it summarises the outcome for the whole file.
OrgnlGrpInfAndStsOriginal Group Information and StatusMThe original group reference plus the status and any status reason for the whole group. It carries codes such as ACCP for accepted, RJCT for rejected or PART for partially accepted. The customer reads this first to know whether the file as a whole passed validation.
OrgnlPmtInfAndStsOriginal Payment Information and StatusOStatus information for one payment information block from the original file, with its identification and status. It lets the customer see which blocks were accepted and which were rejected. A block can be rejected for a bad execution date or a missing debtor account while other blocks succeed.
OrgnlTxRefOriginal Transaction ReferenceOReference data from the original payment, such as amount, currency, debtor and creditor, copied into the status report. It helps the customer match the status to the correct payment in its own system when the payment identification alone is not enough to identify the item.
TxInfAndStsTransaction Information and StatusOStatus information for a single transaction, with its identification, status and reason. It is the most detailed level of the report. The customer uses it to identify exactly which supplier or salary payment failed and why, so it can correct and resend only that item.
StsRsnInfStatus Reason InformationOThe reason for a status, with a coded reason and additional free text. Codes include NARR for narrative, DUPL for duplicate, AC01 for wrong account number and CUST for a customer requested rejection. Clear reason codes let the customer fix the root cause instead of guessing why the payment failed.
NbOfTxsPerStsNumber of Transactions per StatusOA count of transactions in each status, for example 48 accepted and 2 rejected. It gives the customer a quick summary of the file outcome without reading every transaction. Reconciliation teams compare the counts with their own file totals to confirm no transaction was lost.
OrgnlPmtInfIdOriginal Payment Information IdentificationOThe identification of the original payment information block, copied from the pain.001 file. It links the status block to the customer block. The customer uses it to update the status of all payments in that block in its enterprise resource planning system.
OrgnlInstrIdOriginal Instruction IdentificationOThe instruction identification of the original payment, copied from the pain.001 file. It links the status to one customer instruction. It is the key the customer system uses to mark a single payment as accepted, rejected or pending in its own ledger.
OrgnlEndToEndIdOriginal End to End IdentificationOThe end to end identification of the original payment, copied from the pain.001 file. It stays unchanged through the payment chain and lets the customer, the bank and the creditor all refer to the same payment. It is useful when a customer queries a payment by its own reference.
ChrgsInfCharges InformationOCharges applied to the payment, when the bank reports them in the status message. It can show the amount and bearer of any fee deducted. The customer uses it to reconcile bank charges against its own fee schedule and to query any charge that does not match the agreed pricing.

Valid example

Meridian Bank London sends a pain.002 to Northgate Trading for file NGT-20261105: group status ACCP for 47 payments and one transaction status RJCT with reason AC01 for a wrong creditor account number. Northgate corrects the one account number and resends only that payment.

Invalid example

A pain.002 arrives quoting an original group identification that matches no file the customer ever sent. The customer cannot reconcile the report and must query the bank (error: unknown original group reference).

Validation errors

  • Unknown original group reference: a status report that quotes a pain.001 message identification the customer never sent cannot be matched and must be investigated.
  • Missing transaction status for a rejected item: a RJCT status with no reason code leaves the customer unable to fix the payment.
  • Status code outside the allowed set: a code other than ACCP, RJCT, PDNG or PART fails validation and the report is rejected by the customer system.

Processing notes

The customer system matches the report to its original file by group identification, updates each payment to accepted, rejected or pending, and queues rejected items for correction. A partially accepted file needs item level tracking so one bad payment does not block the rest of the file.

Accounting notes

A pain.002 posts no accounting entries itself; it only reports the status of payments instructed in the pain.001. The customer ledger is updated from the report: accepted payments are marked as sent, rejected payments stay open as unpaid, and the bank statement in camt.053 remains the record of what actually posted.

Related messages

pain.001, pacs.002, camt.053, pacs.008
