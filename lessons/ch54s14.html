Show transcript

A SWIFT message does not go everywhere by default. Routing is controlled at several layers, and a message addressed to a destination the sender is not authorised to reach is rejected before it travels. The controls exist for good reasons: they prevent misdirected payments, they enforce the commercial agreements between institutions, and they keep closed communities closed. A business analyst who understands routing restrictions can diagnose a rejected message in minutes; one who does not will chase the message format while the real problem sits in an authorisation table.

The first layer is the Relationship Management Application, known as RMA. Before two institutions exchange FIN messages, they authorise each other through RMA: which message types, which services, and in which direction. The authorisation is recorded centrally, and SWIFT enforces it: a message sent to a BIC without the matching RMA authorisation is rejected with a NAK. RMA replaced the bilateral key exchange, BKE, during the SWIFTNet Phase 2 migration in 2007 and 2008, moving authorisation from pairwise key arrangements to a centrally managed, auditable service. RMA is the most common cause of a message that is well formed but still rejected.

The second layer is the closed user group. Services that run inside a CUG, such as the corporate access models and market practice communities, are restricted to members. A message for a CUG service sent by a non member, or to a non member, is rejected. The restriction is enforced by membership: the group administrator admits members, and the network checks membership on every message. CUG restrictions are how a community keeps its traffic private and its rules enforceable, and they are why joining a service is an onboarding project, not just a configuration change.

The third layer is local routing, inside the sender interface. The interface holds routing tables that decide how each message leaves the building: which logical terminal sends it, which session carries it, and which queue it waits in. Routing rules direct messages by type, by currency, by correspondent, and by service. A routing rule that sends a payment to the wrong queue delays it; a routing table that points at a decommissioned terminal loses it. Local routing is configured by the bank operations team, and it changes whenever a correspondent is added, a service is joined, or an interface is upgraded.

The fourth layer is the BIC directory, the reference data that says which BICs exist and how they are reached. Routing depends on the directory being current: mergers, closures, and new joiners change it, and SWIFT publishes updates. A stale directory misroutes messages to BICs that no longer exist, or fails to route messages to BICs that are newly reachable. Directory management is a quiet operational routine with loud failure modes, and it belongs in the same change control as any other reference data.

When routing fails, the symptoms point at the layer. A NAK with an authorisation error points at RMA. A rejection naming a closed user group points at membership. A message stuck in a queue points at local routing. A message addressed to a BIC the network does not recognise points at the directory. The fix is usually an authorisation, a membership change, a routing table update, or a directory refresh, not a message repair. Routing design belongs in the onboarding checklist for every new correspondent, every new service, and every new message type, because a payment that cannot be routed is a payment that cannot be made.
