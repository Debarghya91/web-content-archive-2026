Correct result. A correct request has all mandatory fields, a valid idempotency key, and the right resource and operation. The success response confirms acceptance, and the error response names the field or rule that failed.

Why. An API contract is a promise between two systems. If the request is wrong, the API must reject it cleanly, not fail silently.

This is a real case from the industry, and it shows how a thousand tiny payments can add up to a large loss when no one sets a limit. An AI agent paid for API calls with stablecoins all weekend. Each call cost a few cents. No single call looked risky, no single call needed approval, and no one was watching the total. By Monday morning the total was EUR 8,000, and no one had set a limit.

A thousand tiny payments is still EUR 8,000. When a machine pays a machine, the controls must be machine sized too. A human-sized control, like approving each payment one by one, does not work when the payments happen in seconds, all weekend, without a human in the room. You need controls that work at machine speed and machine volume.

The first is a spend cap. A hard maximum for the day or the weekend, after which no further payment can go through without a human approving a higher cap. The second is a velocity limit. A maximum number of calls or payments per hour, so a sudden spike is stopped before it runs all weekend. The third is an alert threshold. A warning well before the cap is hit, sent to a named person, so someone knows the spend is climbing while there is still time to act. The fourth is a named owner who sees the total. Not a dashboard that no one opens, but a person who receives the daily total, the number of calls, and the exceptions, and who can pause the agent.

Before any agent is given a way to pay, set all four, test them with a small amount, and prove that the cap actually stops the spend.
