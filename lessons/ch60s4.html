Why take this lesson

By the end of this lesson, you will be able to explain pain.001 in customer-to-bank space. In customer to bank space, pain.001 is a direct instruction from a customer to its own bank, and the bank is the debtor agent for every payment in the file. If the payment has already been executed and sent as a pacs.008, cancellation is no longer a customer to bank matter, and the bank must use a recall or return process in the interbank space.

Key terms

Execution date: The date on which the bank executes a payment instruction, debiting the debtor account and sending the message onward.

Charge bearer: A code that states who pays the charges for a payment. In ISO 20022 the values are DEBT for debtor, CRED for creditor, SHAR for shared and SLEV for service level.

Authorisation: Approval by the issuer for a card transaction to proceed, confirming the card is valid and funds or credit are available.

In customer to bank space, pain.001 is a direct instruction from a customer to its own bank, and the bank is the debtor agent for every payment in the file. A corporate treasurer, a payroll manager, or a public sector finance officer creates the file in an enterprise resource planning system or a treasury workstation, signs it, and sends it through a secure channel such as a host to host connection or an online banking portal. The bank receives the file as a customer instruction, not as an interbank payment, and it is responsible for validating the instruction, debiting the customer account, and creating the onward interbank message.

Customer to bank pain.001 files are often large batch files, because they carry the routine payment runs of a business. A retailer might send a pain.001 file every Friday with 1,200 supplier payments worth EUR 4,800,000 in total, while a mid sized manufacturer might send a monthly salary file with 850 payments worth EUR 2,100,000. Each payment in the batch is independent, so one wrong IBAN should reject one payment, not the whole file, and the bank pain.002 report must identify the failed payment precisely. Batch discipline matters, because a single file error that blocks 1,200 payments can halt a supply chain and damage supplier trust within a day.

Banks apply several validation layers to a customer to bank pain.001 file before they accept it. The first layer checks the file format, the XML structure, and the message version, because a file built to pain.001.001.03 cannot be processed as if it were pain.001.001.09. The second layer checks the business rules, including the debtor account, the currency, the execution date, and the charge bearer. The third layer checks funds, limits, and sanctions, including screening the creditor name and country against sanction lists. A payment of EUR 45,000 to a creditor in a sanctioned jurisdiction will be stopped at this layer even if every field is correctly formatted.

The customer to bank space also carries the rules for cancellation and amendment, which are handled through pain.001 status handling and through separate cancellation messages. A customer that discovers an error after sending a file can ask the bank to cancel an instruction before execution, and the bank will report the outcome in pain.002 with a status that shows whether the cancellation succeeded. If the payment has already been executed and sent as a pacs.008, cancellation is no longer a customer to bank matter, and the bank must use a recall or return process in the interbank space. That boundary is important, because customers often assume they can cancel any payment at any time, while banks can only stop payments that have not yet left the bank.

Security and authorisation are central to customer to bank pain.001, because a file can move millions of euros on a single approval. Banks require signed files, dual authorisation for large amounts, and agreed limits per user and per file. A treasury team might allow one user to create a file worth EUR 500,000 but require a second approver for any file above EUR 100,000, and a file worth EUR 5,000,000 might need two senior approvers. The bank checks the digital signature and the authorisation before it processes the file, and it rejects unsigned or unauthorised files with a pain.002 rejection, so a stolen password alone cannot move a large payment without the second approval.
