Show transcript

A defect in payments must be recorded with enough detail for a developer to reproduce it without guessing. A good defect report includes the environment, the test case reference, the payment reference, the amount and currency, the steps taken, the expected result and the actual result. For example, a defect might state that a pacs.008 for 50,000 dollars to Citibank was created with the charge bearer set to DEBT instead of SHAR, and that the ledger posted an incorrect charge of 25 dollars. A screenshot, a message copy and a log extract help the developer find the cause quickly, and a vague report such as payment failed will waste time and delay the fix.

Defect severity in payments is judged by financial and customer impact, not only by technical difficulty. A critical defect is one that moves money incorrectly, duplicates a payment, or allows a payment to bypass sanctions screening. A high severity defect is one that blocks a common payment type, such as all SEPA payments failing validation. A medium defect might affect a rarely used field, and a low defect might be a spelling error on a confirmation screen. A team must agree these definitions before testing starts, so that severity is not argued case by case when a deadline is near.

Entry criteria define when testing can start, and they prevent wasted effort. Testing should not start until the code is deployed to the test environment, the test data is ready, the simulators are available, and the requirements are clear. If testing starts before the environment is stable, testers will log false defects and lose trust in the results. A simple entry checklist, signed by the test lead and the development lead, makes the decision visible and stops pressure to start testing on an unfinished build.

Exit criteria define when testing can stop, and they protect the bank from releasing too early. A typical exit rule requires that all critical and high defects are fixed and retested, that all mandatory test cases have passed, that regression testing has passed, and that the business has signed UAT. A release with an open critical defect, such as duplicate pacs.008 generation, must not go live, even if the project is late. Exit criteria give the test lead the authority to say no, and that authority is essential when commercial pressure pushes for an early release.

Defect management also needs a clear retest process. When a developer fixes a defect, the tester must rerun the original failing case and a set of related cases to prove that the fix works and has not broken anything else. The defect is only closed when the retest passes and the evidence is attached. A defect that is marked as fixed without a retest is still open in practice. A weekly defect review, with open defects, ages and owners, keeps the team honest and ensures that no critical issue is hidden in a spreadsheet until the day before go live.

A severity matrix makes defect triage objective. A critical defect is one that moves money incorrectly, duplicates a payment, or allows a payment to bypass sanctions screening; it blocks release. A high defect is one that corrupts data or produces a wrong message format; it must be fixed before go-live. A medium defect is one that affects usability or reporting but does not move money incorrectly; it can be deferred with a documented workaround. A low defect is a cosmetic issue. Each defect report must include the environment, the test case reference, the payment reference, the expected result, the actual result, and the evidence, so that a developer can reproduce it without guessing. A defect that cannot be reproduced cannot be fixed.

Entry and exit criteria protect both the tester and the bank. Testing should not start until the code is deployed to the test environment, the test data is ready, the simulators are available, and the test cases are written and reviewed. Testing should not stop until all critical and high defects are fixed and retested, all mandatory test cases have passed, and the evidence pack is complete. A typical exit rule requires zero open critical defects, zero open high defects, and a pass rate of 100 percent on mandatory cases. When a developer fixes a defect, the tester must rerun the original failing case and a set of related cases to prove that the fix works and has not broken anything else. That retest is not optional; it is the evidence that the fix is real.
