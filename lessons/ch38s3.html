What you will learn

Your objective. By the end of this lesson, you will be able to explain source-to-target mapping and field transformation. Mapping starts with a mapping table that lists each source field, the canonical field it feeds, and the rule that governs the transfer.

Why it matters. A good mapping table is a controlled document, reviewed by business analysts, developers, and operations staff, and changed only through a formal change request so that no one edits a live mapping by accident.

Chapter objective: Learner designs a payment data model, including parties, accounts, instructions, transactions, and statuses, and maps fields between a core banking system and ISO 20022 messages. Learner demonstrates this skill using realistic banking examples, explaining each step clearly and using correct terminology throughout.

Key learning points

  • Mapping table: source field, canonical field and transfer rule
  • Field transformation
  • Conditional mapping
  • Unmapped values and rejection handling
  • Silent truncation
  • Testers comparing canonical record and target message field by field

Key terms

Execution date: The date on which the bank executes a payment instruction, debiting the debtor account and sending the message onward.

Purpose code: A code that states the commercial reason for a payment, such as supplier payment, salary or goods. Purpose codes are taken from an ISO external code list and support regulatory reporting, screening...

Exception: A payment that cannot be processed normally and needs manual handling, investigation or repair. Exceptions arise from missing data, failed screening, account errors or system faults.

Mapping starts with a mapping table that lists each source field, the canonical field it feeds, and the rule that governs the transfer. For example, the mobile app field sender_name maps to the canonical debtor name, the branch field remitter maps to the same canonical field, and the corporate file field debit_party maps there too. The table also records whether the field is mandatory, optional, or conditional, and what should happen when the source value is missing. A good mapping table is a controlled document, reviewed by business analysts, developers, and operations staff, and changed only through a formal change request so that no one edits a live mapping by accident. Field transformation changes a value from the source format into the canonical format without changing its meaning. A date of 06/11/2026 in a branch screen becomes 2026-11-06 in the canonical model. An amount of 8750 in a file with no decimal point becomes 8750.00 when the currency is EUR, but the same digits become 8750 when the currency is JPY, because the Japanese yen has no minor unit. A country name written as Germany becomes the code DE, and a charge code of S in a legacy system becomes SHAR in the canonical model. Each transformation is written as a rule with examples, and each rule is tested with values that sit on the boundary, such as zero amounts and leap year dates. Conditional mapping decides which canonical fields are populated based on the payment type and the destination. A domestic payment inside the United Kingdom may need a sort code and account number, while a payment to Germany needs an IBAN and a BIC. A payment marked urgent may require a priority flag and an earlier cutoff time, while a future dated payment needs a stored execution date and a release instruction. A payment above EUR 100,000 may require an additional purpose code and a senior approval flag. When these conditions are written clearly, the mapping engine can apply them automatically instead of relying on an operator to remember which fields matter for which payment. Mapping must also handle values that do not fit, and the correct response is to reject or flag the payment rather than silently change it. If a creditor name has sixty characters but the target system allows only thirty five, the mapping must not cut the name in half and send the payment anyway. It must raise an exception, hold the payment, and ask operations to shorten the name with the customer or choose a different channel. If a reference contains characters the target system cannot carry, the mapping must record the original value, apply an agreed replacement, and log the change. Silent truncation is one of the most common causes of rejected payments and failed reconciliations. Every mapping is proven with a test pack before it goes live, and the pack is kept for later regression testing. The pack includes a normal payment, a payment with the longest allowed name and address, a payment with the shortest allowed reference, a payment in a zero decimal currency such as JPY 125,000, a payment in a three decimal currency such as BHD 1,250.500, a payment with a future execution date, and a payment that should be rejected because a mandatory field is missing. Testers compare the canonical record and the target message field by field, and they record the expected result for each case. When a later change is made, the same pack runs again to prove that nothing else broke.
