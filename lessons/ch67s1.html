What you will learn

Your objective. By the end of this lesson, you will be able to explain reading an ISO 20022 schema: xsd patterns. An XSD, or XML Schema Definition, is a formal description of what a valid message may contain.

Why it matters. A business analyst must know the difference between schema mandatory and business rule mandatory, because a message can pass schema validation and still be rejected by the scheme.

Chapter objective: Learner reads an ISO 20022 XSD, explains currency and amount precision, UTC offsets and timestamps, and the market practice layers of PMPG, CBPR+ and SEPA. Learner traces the EUR 10,000 Atelier Lumiere payment as a pacs.008 under both CBPR+ and SEPA, explains LEI and FATF Recommendation 16, and validates an ISO 20022 XML file against schema and business rules.

Key learning points

  • XSD: formal description
  • Schema type reuse: the key to reading the schema
  • Reading: following these types
  • Charge bearer with 0..1
  • Message: expected

Key terms

Remittance information: Information that explains what a payment is for, such as invoice numbers, contract references or salary month.

Charge bearer: A code that states who pays the charges for a payment. In ISO 20022 the values are DEBT for debtor, CRED for creditor, SHAR for shared and SLEV for service level.

ISO 20022: An international standard for financial messaging that defines XML message formats for payments, securities and trade.

  1. What to do. List the main blocks of the message, name the field that carries the amount, and name the field that identifies the payment.

Correct result. The message is made of blocks, each carrying a part of the payment instruction. The amount field and the identification field are the two a receiving bank checks first, because without them it cannot process or reconcile the payment.

Why. A message is only useful if you can read it. The blocks tell the receiving bank what to do, and the amount and identification fields are what it checks first.

An XSD, or XML Schema Definition, is a formal description of what a valid message may contain. It names each element, states its type, and says whether it is mandatory or optional and how many times it may appear. An ISO 20022 schema for pacs.008.001.08, for example, defines a document element, inside which sits the customer credit transfer initiation or the financial institution credit transfer, and inside that sit the group header, the payment information, and the transaction information. Each level nests inside the one above it, like boxes inside boxes, and the schema is the rule book for which boxes are allowed and in what order. The schema reuses types, and that reuse is the key to reading it. A type such as ActiveOrHistoricCurrencyAndAmount is used wherever an amount appears, and it carries a currency attribute and a decimal value. A type such as PartyIdentification135 is used wherever a party appears, and it carries a name, a postal address, and an identification block. When you see the same type name in two places, the structure is the same in both places, which means you learn it once and recognise it everywhere. The schema also uses choice blocks, where only one of several options may appear, and sequences, where elements must appear in a fixed order. Reading a schema means following these types and choices, not memorising every element. Cardinality is the rule that says how many times an element may appear, and it is written as a pair such as 0..1 or 1..n. The first number is the minimum, so 0 means optional and 1 means mandatory, and the second number is the maximum, so 1 means at most once and n means any number. A debtor name with cardinality 1..1 must appear exactly once, while a remittance information block with cardinality 0..1 may appear once or not at all. A charge bearer with 0..1 is optional, but if the scheme requires it, a business rule makes it mandatory even though the schema does not. A business analyst must know the difference between schema mandatory and business rule mandatory, because a message can pass schema validation and still be rejected by the scheme. Schema validation is the automatic check that a message matches its XSD, and it is the first gate a message must pass. The validator checks that every element is in the right place, that the order is correct, that the types are right, and that the cardinality rules are met. If a message carries a letter where a number is expected, or a mandatory element is missing, the validator rejects the whole message and returns an error naming the element and the rule. The receiving system usually replies with a pacs.002 or an admi.002 message status report, so the sender knows the message failed. A message that fails schema validation is never processed further, which is why the sender must validate before sending, not after. When validation fails, the team reads the error, finds the offending element, and decides whether the source data or the mapping was wrong before resending.
