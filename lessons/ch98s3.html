An AI feature is only as good as the data behind it, so the product owner has to treat data as a requirement, not as something the engineers will sort out later. Start by writing down exactly what data the feature needs, where each field comes from, and how fresh it has to be. A payment matching model, for example, might need the payer name, the payment amount, the value date, the reference, and the account number. If any of those fields is missing or out of date, the model has to guess, and guessing with money is a bad idea.

Next, check quality and coverage. Look at real payment data, not a clean sample. Are there missing references, duplicate payments, or amounts in the wrong currency. Does the data cover all the payment types you serve, or only the easy ones. Suppose your history covers domestic payments well, but only a small number of cross-border payments of 28,000 pounds and above. The model will be confident on domestic payments and weak on the cross-border ones, and that is exactly where an error costs the most.

Then ask what happens when the data is incomplete or biased. If past data reflects old manual decisions that favoured one type of customer or one channel, the model will learn that bias and repeat it. You need a plan for that.

Define the minimum data quality before the feature goes live, define what the system does when a field is missing, and define who owns the data feed when it breaks. Write these as requirements, with owners and checks, so data is not an afterthought but part of the product.

Data Requirements for an AI Feature

An AI feature is only as good as the data behind it, so the product owner has to treat data as a requirement, not as something the engineers will sort out later. Start by writing down exactly what data the feature needs, where each field comes from, and how fresh it has to be. A payment matching model, for example, might need the payer name, the payment amount, the value date, the reference, and the account number. If any of those fields is missing or out of date, the model has to guess, and guessing with money is a bad idea.

Next, check quality and coverage. Look at real payment data, not a clean sample. Are there missing references, duplicate payments, or amounts in the wrong currency. Does the data cover all the payment types you serve, or only the easy ones. Suppose your history covers domestic payments well, but only a small number of cross-border payments of 28,000 pounds and above. The model will be confident on domestic payments and weak on the cross-border ones, and that is exactly where an error costs the most.

Then ask what happens when the data is incomplete or biased. If past data reflects old manual decisions that favoured one type of customer or one channel, the model will learn that bias and repeat it. You need a plan for that.

Define the minimum data quality before the feature goes live, define what the system does when a field is missing, and define who owns the data feed when it breaks. Write these as requirements, with owners and checks, so data is not an afterthought but part of the product.
