What you will learn

Your objective. By the end of this lesson, you will be able to explain database design for payments. The payment instruction table is the core record.

Why it matters. This matters because the architecture decides what the bank can build, how fast it can change, and where a payment can fail. Most payment requirements live in the architecture.

Chapter objective: Learner applies system design to payments, covering throughput, latency, idempotency, exactly-once processing, and failure recovery, and designs a system for a stated load. Learner practises this skill on realistic banking cases, explaining the reasoning clearly and using correct terminology throughout the work.

Key learning points

  • Payment instruction table
  • Payment event table recording every significant thing
  • Event table
  • System failure interrupting a posting halfway
  • Seven-year message retention
  • Transition: recorded in event table

Key terms

Value date: The date on which funds become available to the beneficiary and on which interest starts to accrue. It is the date used for settlement and for nostro posting.

Settlement: The final movement of funds between banks to discharge obligations created by cleared payments. Settlement is usually made in central bank money or through correspondent accounts.

Exercise

Design the database tables in this lesson for a bank processing 2 million payments a day: the instruction table and the event table.

Use the lesson facts: the instruction table holds one row per instruction, partitioned by date and indexed on reference and account, and the event table writes a new row for each state change and is append-only.

  1. What to do. State the instruction table fields, the partitioning and indexes, and the event table rules.

Correct result. The payment instruction table is the core record. It holds one row per payment instruction, with the unique reference number, the debit account, the beneficiary name and account, the amount and currency, the value date, the payment type, and the channel it came from. A bank processing 2 million payments a day adds 2 million rows a day to this table, so it is partitioned by date and indexed on the reference number and the account number. Without those indexes, finding a single payment among billions of rows would take minutes instead of milliseconds. When a payment is received, validated, screened, queued, released, settled, confirmed, rejected, or returned, a new event row is written with a timestamp, the old status, the new status, and the system or user who made the change. This table is essential for investigations, because when a beneficiary bank says it never received a payment, the bank can produce the exact message, the exact time, and the acknowledgement reference. For a cross-border payment this includes the pacs.008 message sent to the correspondent bank, the pacs.002 status report received back, and the MT103 equivalent if the payment went through the older SWIFT format. The event table is append-only, meaning rows are never updated or deleted, so the history cannot be rewritten.

Why. An investigator can only replay a payment if the instruction is findable in milliseconds and the history was never overwritten.

The payment instruction table is the core record. It holds one row per payment instruction, with the unique reference number, the debit account, the beneficiary name and account, the amount and currency, the value date, the payment type, and the channel it came from. A bank processing 2 million payments a day adds 2 million rows a day to this table, so it is partitioned by date and indexed on the reference number and the account number. Without those indexes, finding a single payment among billions of rows would take minutes instead of milliseconds. The table also holds the current status of the payment, which is updated as the payment moves through its lifecycle. The payment event table records every significant thing that happens to a payment. When a payment is received, validated, screened, queued, released, settled, confirmed, rejected, or returned, a new event row is written with a timestamp, the old status, the new status, and the system or user who made the change. This event history is the audit trail. If a customer asks why a payment of 80,000 dollars took three days, the bank can show the exact sequence, received at 12 minutes past 9 in the morning, validated at 13 minutes past 9 in the morning, held for sanctions review at 14 minutes past 9 in the morning, released by compliance at 40 minutes past 11 in the morning, settled at 5 minutes past 12 in the afternoon. The event table is append-only, meaning rows are never updated or deleted, so the history cannot be rewritten. The account entry table holds the accounting postings for each payment. Every payment creates at least two entries, a debit to the sender account and a credit to the internal settlement account, followed by a debit to the settlement account and a credit to the beneficiary or the nostro account. Each entry records the account number, the amount, the currency, the value date, and the reference to the payment instruction. These entries must balance exactly, and the database enforces this with a rule that the total debits equal the total credits for every payment. If a system failure interrupts a posting halfway, the database transaction is rolled back so that no partial posting survives, which is why payment databases use strict transactional guarantees. The message log table stores the actual messages sent and received for each payment. For a cross-border payment this includes the pacs.008 message sent to the correspondent bank, the pacs.002 status report received back, and the MT103 equivalent if the payment went through the older SWIFT format. The log holds the full message text, the sender and receiver, and the time of transmission. This table is essential for investigations, because when a beneficiary bank says it never received a payment, the bank can produce the exact message, the exact time, and the acknowledgement reference. Message logs are kept for at least seven years in most countries to meet regulatory requirements. A payment moves through a defined set of states, and the database enforces the allowed transitions. The states are received, validated, queued, released, settled, confirmed, rejected, and returned. A payment in the received state can move to validated or rejected, but it cannot jump directly to settled. A payment in the queued state can move to released or returned, but not back to received. A payment in the settled state can move to confirmed when the clearing system acknowledges it, or to returned if the beneficiary bank rejects it. Each transition is recorded in the event table with the user or system that triggered it, and the database rejects any transition that is not on the approved list. This state machine is what stops a payment from being settled twice or confirmed before it has been released.
