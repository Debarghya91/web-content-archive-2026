Key terms

Execution date: The date on which the bank executes a payment instruction, debiting the debtor account and sending the message onward.

Charge bearer: A code that states who pays the charges for a payment. In ISO 20022 the values are DEBT for debtor, CRED for creditor, SHAR for shared and SLEV for service level.

ISO 20022: An international standard for financial messaging that defines XML message formats for payments, securities and trade.

  1. What to do. List the three levels of the message and name the field that carries the amount and the field that carries the end-to-end reference.

Correct result. The amount is carried in the instructed amount element and the reference in the end-to-end identification. The three levels are the group header, the payment information, and the credit transfer transaction information.

Why. A message is only useful if you can read it. The group header identifies the message, the payment information identifies the batch, and the transaction information carries the single payment.

Common errors in a pacs.008 fall into three categories, which are structural errors, business validation errors, and data quality errors. Structural errors occur when the XML is not well formed, when a mandatory element is missing, or when an element contains data in the wrong format, such as a date that is not in ISO format or an amount that contains a comma instead of a decimal point. These errors are usually caught by XML schema validation, and the message is rejected before it reaches the payment engine. The sender receives a pacs.002 status report with a rejection code, and must correct and resend the message. Business validation errors occur when the XML is well formed but the business rules are violated. Examples include a debtor account that does not exist, a creditor BIC that is invalid, a charge bearer code that is not allowed for that scheme, or a requested execution date that is in the past. These errors are caught by the payment engine, and they also result in a rejection with a status code. Data quality errors are more subtle, and they occur when the message is technically valid but the data is wrong, such as a creditor name that is misspelled, an address that is incomplete, or a remittance reference that does not match any invoice. These errors may not cause a rejection, but they can cause the payment to be repaired manually, to be delayed, or to be returned by the creditor agent. For a business analyst, validation requirements must be precise. You must document which fields are mandatory, which are optional, and which are conditional, and you must document the error code and the action for each validation failure. Your test cases should include a happy path message that validates cleanly, a message with each mandatory field missing, a message with an invalid BIC, a message with a duplicate Message Identification, and a message with a Control Sum mismatch. Those tests will catch most of the errors that occur in production, and they will give operations teams a clear guide to fixing them.

Take a worked example with real numbers. A bank sends a pacs.008 with 50 transactions, and the clearing system rejects the whole message because the Group Header control sum is EUR 499,000 but the transactions total EUR 500,000. The sender finds that one transaction was entered as EUR 9,000 instead of EUR 10,000, corrects it to EUR 10,000, recomputes the control sum to EUR 500,000, generates a new MsgId, and resends. The message is accepted.

In the same file, one transaction is then returned by the creditor agent as a pacs.004 with reason code AC01, because the creditor account number has a transposed digit, and the debtor is refunded EUR 10,000. The other 49 transactions settle normally. The two failures are different: the first is a structural error that stops the whole message, and the second is a business error that affects one transaction, and the recovery is different for each.

Failure and recovery by category: structural errors reject the whole message, and the recovery is to fix the field and resend with a new MsgId. Business validation errors return one transaction as a pacs.004, and the recovery is to correct the data and send a new payment, not to resend the old one, because the old payment was already processed. Data quality errors, such as a beneficiary name that does not match the account, are held for manual review, and the recovery is to confirm the details with the customer before releasing or returning the payment.

The operations team must be able to read the pacs.002 reason code and tell the customer which field to fix, and the requirement must state which reason codes the product can produce and what the customer sees for each one. The most common reason codes are AC01 for an incorrect account number, AC04 for a closed account, AM04 for insufficient funds, BE01 for inconsistent end customer information, FF01 for an invalid file format, RC01 for an incorrect bank identifier, and AG01 for a transaction forbidden by the scheme.

For a business analyst, product owner or subject matter expert, the test is to write the validation requirements for a pacs.008 product as a table, with one row per field, the validation rule, the error code, and the customer message. A requirement that says validate the message is not enough, because it does not say which fields are mandatory, which are optional, which are conditional, and what happens when each one fails. The test cases are built from the same table, with one test per row, and a test that covers only the happy path will miss the errors that cause most production incidents.
