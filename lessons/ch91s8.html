Transcript and full text

Show transcript

BACS, the United Kingdom system for Direct Debits and Direct Credits, runs on files. The file format is called Standard 18, and the BACS glossary defines it in one line as the standard file and record format used by the Direct Debit and BACS Direct Credit schemes. It is a flat, fixed width, fixed length text file. There is no XML, no JSON, and no delimiter. Every field is found by counting characters from the start of the line, exactly as it was when these files travelled on magnetic tape. A service user that submits BACS payments, or a bureau that submits them on behalf of others, must produce Standard 18 files that balance and validate, or the submission is rejected.

A Standard 18 submission is a sandwich of label records and payment records. The label records are 80 characters long. VOL1 is the volume header: it identifies the submitting party and carries the Service User Number. HDR1 is the first file header: the file identifier, the creation date, and the expiration date. HDR2 is the second file header: it declares the record format, the block length, and the record length. UHL1 is the user header label: it carries the BACS processing day and the work code. After the labels come the payment records, then a contra record, and then the trailer labels EOF1, EOF2, and UTL1. A file that does not follow this sequence is rejected outright.

The payment record is where the work is. Each record is 100 characters long, and there is a 106 character variant that appends a processing date to each record for multi processing files. Counting from position 1: the destination sort code occupies the first six characters, and the destination account number the next eight. The transaction code sits at positions 16 and 17: 01 for a first Direct Debit collection, 17 for a regular collection, 18 for a re-presented collection, 19 for a final collection, 99 for a bank giro credit, and 0N, 0C, and 0S for AUDDIS new, cancelled, and converted Direct Debit instructions. The amount, the reference, and the service user details follow in fixed positions. The character set is restricted: uppercase letters, digits, spaces, and four special characters, the hyphen, the full stop, the ampersand, and the solidus.

Dates in Standard 18 use the Julian convention. A date is written as a blank space followed by the last two digits of the year and the day number of the year, from 001 to 365, or 366 in a leap year. The UHL1 record carries the BACS processing day in this form, and it must be a valid BACS processing day, or the file is rejected. In the 106 character variant, each record carries its own processing date, which must not be earlier than the UHL1 date and must not be more than 39 days after it. The Julian convention looks archaic, but it is unambiguous and compact, and it has survived every modernisation of the surrounding systems.

A Standard 18 file must balance. The BACS glossary defines a file as a self balancing set of records from a service user, and the definition is enforced: the contra record carries the totals for the payment records, and if the totals do not match, the file is not a file, it is a rejection. The balancing check catches truncation, duplication, and corruption before any payment is processed. It is the file level equivalent of a control total in a batch system, and it is why BACS submissions are reliable despite the age of the format: the format checks itself.

Standard 18 files travel to BACS over BacsTel-IP, the internet based submission channel, signed with digital certificates and tied to the service user number. BACS is migrating toward ISO 20022, and new services are built on the new standard, but Standard 18 remains the working format for the bulk of Direct Debit and Direct Credit submissions. Reading a Standard 18 record by counting characters, saying what each field carries, and spotting a balancing error are still working skills for anyone who operates BACS submissions, builds BACS software, or investigates a rejected file.
