Key terms

Reconciliation: The process of comparing records from two sources, such as a bank statement and an internal ledger, to confirm they agree.

Charge bearer: A code that states who pays the charges for a payment. In ISO 20022 the values are DEBT for debtor, CRED for creditor, SHAR for shared and SLEV for service level.

Value date: The date on which funds become available to the beneficiary and on which interest starts to accrue. It is the date used for settlement and for nostro posting.

Exercise

Write the acceptance criteria for the core conversion story: an MT103 with field 32A value date 15 November 2024, currency USD and amount 125,000 must convert to a pacs.008. Name the target elements and the checks.

Use the lifecycle stages in this lesson: acceptance, processing, clearing, settlement, beneficiary credit, ledger posting and reconciliation.

  1. What to do. Name each stage, state what happens, and say when the payment is truly final.

Correct result. The pacs.008 must carry the same value date in IntrBkSttlmDt and the same currency and amount in the interbank settlement amount, IntrBkSttlmAmt. The instructed amount, InstdAmt, comes from field 33B where the payment carries one. The charge bearer must be SHAR for field 71A SHA, and the message must pass schema validation with zero errors.

Why. The lifecycle is the map of a payment. If you cannot say which stage a payment is in, you cannot answer where the money is.

The first user story covers the core conversion. As a payment operations officer, I want the system to convert an outward MT103 into a pacs.008 message automatically, so that cross-border payments meet the ISO 20022 standard without manual intervention. The acceptance criteria state that given an MT103 with field 32A value date 15 November 2024, currency USD and amount 125,000, when the message is converted, then the pacs.008 must carry the same value date, currency and amount. A second criterion states that given an MT103 with field 71A set to SHA, when the conversion runs, then the charge bearer in pacs.008 must be SHAR. The second user story covers field validation. As a payment operations officer, I want the system to reject MT103 messages with invalid data before conversion, so that no invalid pacs.008 message is ever sent to a correspondent bank. The acceptance criteria state that given an MT103 with a beneficiary IBAN that fails the modulus 97 check, when the message is submitted for conversion, then it must be routed to the repair queue with the error code INVALID_IBAN. Another criterion states that given an MT103 with an amount of zero, when the message is submitted, then it must be rejected with the error code INVALID_AMOUNT and the rejection must be logged. The third user story covers exception handling for the 50K and 59 parsing problem. As a payment operations officer, I want messages that cannot be parsed automatically to appear in a repair queue with the original text visible, so that I can correct them manually and release the payment. The acceptance criteria state that given an MT103 where field 59 has five lines and no recognisable account pattern, when the conversion runs, then the message must appear in the repair queue within one minute with the full original field 59 displayed. A further criterion states that given a repaired message, when the officer corrects the beneficiary account and submits it, then the conversion must complete and the payment must be released. The fourth user story covers duplicate detection. As a corporate customer, I want the system to warn me before sending a duplicate payment, so that I do not pay the same supplier twice by mistake. The acceptance criteria state that given a payment of 250,000 rupees to the same supplier account with the same value date submitted twice within 24 hours, when the second payment is submitted, then the system must return a duplicate warning with the first payment's reference. A second criterion states that given the warning, when the customer confirms the payment is intentional, then the second payment must be processed normally. The fifth user story covers reconciliation reporting. As a reconciliation analyst, I want a daily report showing every MT103 received and its converted pacs.008, so that I can prove no payment was lost or altered during migration. The acceptance criteria state that given 12,000 MT103 messages received on a day, when the report is generated at 6 in the evening, then it must list all 12,000 with a status of Converted, In Repair or Rejected, and the totals must reconcile to zero differences. Another criterion states that given a converted message, when the analyst opens the report detail, then the original field 32A amount and the pacs.008 instructed amount must be shown side by side and must match exactly.
