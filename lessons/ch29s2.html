Why take this lesson

By the end of this lesson, you will be able to explain SWIFT MT103 to ISO 20022 pacs.008 message mapping. A mapping document is a table that lists every field in the source message, the matching field in the target message, and the rule that converts one into the other, and it is the single most important deliverable of the migration. A mapping document is the single most important deliverable of the migration: if a field maps to the wrong element, the payment fails schema validation or settles the wrong amount, so the analyst who writes it decides whether the migration works.

Key terms

Remittance information: Information that explains what a payment is for, such as invoice numbers, contract references or salary month.

Charge bearer: A code that states who pays the charges for a payment. In ISO 20022 the values are DEBT for debtor, CRED for creditor, SHAR for shared and SLEV for service level.

Purpose code: A code that states the commercial reason for a payment, such as supplier payment, salary or goods. Purpose codes are taken from an ISO external code list and support regulatory reporting, screening...

Show transcript

A mapping document is a table that lists every field in the source message, the matching field in the target message, and the rule that converts one into the other, and it is the single most important deliverable of the migration. The MT103 is a free-text based message with numbered fields such as 20 for the transaction reference, 32A for the value date, currency and amount, 50K for the ordering customer, 59 for the beneficiary, and 70 for the remittance information. The pacs.008 is a structured XML message with named elements such as Group Header, Payment Information and Credit Transfer Transaction Information, and every MT field must be placed into the right element.

Mappings fall into three types, and the analyst must label each one. A direct mapping copies a field unchanged, such as the transaction reference in field 20 going straight into the message identification element. A derived mapping calculates a value from one or more source fields, such as building the instructed amount in pacs.008 from the currency and amount in field 32A. A translated mapping converts a value from one code set to another, such as converting the charge code in field 71A from OUR to DEBT, BEN to CRED, and SHA to SHAR in the charge bearer element of pacs.008.

Mandatory and optional fields must be handled differently. In pacs.008, the message identification, the instructed amount, the debtor agent and the creditor agent are mandatory, which means the conversion must always produce them or the message fails schema validation. Fields such as the remittance information and the purpose code are optional, but the bank's policy may make them mandatory for certain corridors, for example purpose codes are required for all payments to India above 50,000 rupees. The mapping document records the pacs.008 requirement and the bank's own rule side by side, so there is no confusion about which one governs.

The hardest problem in the migration is the parsing of fields 50K and 59, because both are free-text fields with no fixed structure. Field 50K holds the ordering customer, and a typical value looks like four lines. The account number, the name, and two lines of address, with no labels to say which line is which. Field 59 holds the beneficiary in the same loose format. The conversion engine must split these lines, decide which line is the name and which lines are the address, and place them into the structured debtor and creditor elements of pacs.008, which have separate elements for name, postal address and account identification.

The parsing problem gets worse with real data. Some customers write the account number on the first line and some write it on the second, some include a country code and some do not, and some addresses run to three lines while others fit in one. The analyst documents a parsing rule for each pattern found in a sample of 5,000 real messages. If the first line matches the pattern of an account number, treat it as the account, and treat the next line as the name. Messages that do not match any known pattern are sent to a manual repair queue, and the mapping document records the expected repair rate, which the operations team uses to plan staffing.

The mapping document is validated by running a sample conversion and checking the results field by field. The team takes 1,000 real MT103 messages, converts them, and compares the pacs.008 output against the mapping rules. Any field that is empty when it should be populated, any amount that does not match, or any name that is truncated is logged as a mapping defect and fixed in the document. Only when the sample passes with zero critical defects does the mapping document go for sign-off, because every downstream deliverable, from user stories to test cases, depends on it being correct.
