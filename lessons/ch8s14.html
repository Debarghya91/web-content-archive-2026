Key terms

Remittance information: Information that explains what a payment is for, such as invoice numbers, contract references or salary month.

Market practice: An agreed way of using a message standard in a particular market or community, covering field usage, codes and validation rules.

Reconciliation: The process of comparing records from two sources, such as a bank statement and an internal ledger, to confirm they agree.

  1. What to do. List the main blocks of the message, name the field that carries the amount, and name the field that identifies the payment.

Correct result. The message is made of blocks, each carrying a part of the payment instruction. The amount field and the identification field are the two a receiving bank checks first, because without them it cannot process or reconcile the payment.

Why. A message is only useful if you can read it. The blocks tell the receiving bank what to do, and the amount and identification fields are what it checks first.

Transcript and full text

Show transcript

Migration from MT to ISO 20022 needs translation. An MT message must become an MX message without losing meaning, and that is harder than it sounds. The two standards describe the same payment in different shapes, with different data, and different rules. Conversion is a mapping discipline: every field in the source must find its home in the target, every gap must be named, and every loss must be detected rather than silent. A conversion that drops data quietly is a payment defect waiting for a customer to find it.

The structural gap is the first problem. MT is flat: blocks of tagged fields, each field a short string with a format. MX is nested XML: elements inside elements, with names that say what each value means. One MT field often splits into several MX elements. Field 59, the beneficiary customer, becomes a creditor block with a name element, an account element, and a postal address block. Several MT fields can also merge into one MX structure, where the target groups data the source kept apart. The translator must know the target usage guideline, CBPR+ or HVPS+ or a market practice guideline, because the guideline decides which elements are mandatory and which values are allowed.

The data gap is the second problem. MT has no Legal Entity Identifier, no structured purpose code, and no Unique End to End Transaction Reference. The MX message has elements for all three, and they stay empty unless the source system supplies the data. Character sets differ too: MT uses a restricted character set, while MX uses UTF-8, so names and addresses with characters outside the MT set must be handled carefully in both directions. Address lines are a classic case: MT carries four lines of 35 characters, and MX wants a structured or hybrid postal address. Fitting four free text lines into structured fields without truncation needs rules, and the rules must be tested.

Remittance information is where conversion most often loses data. MT field 70 carries four lines of 35 characters, 140 characters in total, and it is unstructured text. MX remittance information can be unstructured or structured, and the structured form carries invoice numbers, dates, and amounts as separate elements. A translator that copies field 70 into unstructured remittance preserves the text but loses the chance to structure it. A translator that tries to structure it must parse free text, which is unreliable. The safe approach is to preserve the text exactly, flag any truncation, and let the business decide where structured remittance is worth the investment.

During the coexistence period, SWIFT offered in flow translation services, so that an MT sender could reach an MX receiver and the translation happened inside the network. The translation rules were published as part of the CBPR+ guidance, so banks could predict exactly how a message would convert. Banks also built local translators, inside their payment hubs and interfaces, for traffic that never touched the network service. Both approaches need the same testing: golden files of known messages, converted and compared field by field, with round trip checks where a message is converted and converted back to prove nothing was lost.

Conversion quality is a testing discipline. Field by field reconciliation compares the source and the target for every message in the test set. Truncation reports list every value that did not fit its target element. Code list mapping is checked separately: instruction codes, charge codes, and purpose codes must map to the right target values, because a wrong code changes the meaning of the payment. A conversion defect is a payment defect: the wrong account, the wrong amount, or the wrong instruction, delivered with full confidence. The analyst job is to make conversion boring: specified, tested, and monitored, so that migration changes the format without changing the money.
