Show transcript

Balances change all day. A treasurer who needs to know the position on an account right now cannot wait for the end of day statement, and cannot guess. The MT920 is the message that asks. Its name is simply the Request Message, and it sits in Category 9, the cash management family. Its most common use is to request an MT941 balance report, but the request mechanism is general: the MT920 names the report wanted, and the account servicing institution responds with it. It is the question half of a question and answer pair, and the MT941 is the answer.

The fields of the MT920 are few, because a request needs little data. Field 20 carries the transaction reference, so the request and the response can be matched. Field 12 names the message requested: the type number of the report wanted, most commonly 941 for a balance report. Field 25 identifies the account the report should cover. The request may also carry a floor limit indicator, field 34F, which sets a threshold: the report is triggered when the balance crosses the stated floor. The structure is deliberately minimal. A request that needed pages of data would defeat its own purpose.

The flow is a simple round trip. The account owner, or the bank acting for the account owner, sends the MT920 to the account servicing bank. The servicing bank reads the request, prepares the named report for the named account, and returns it, usually as an MT941, sometimes as an MT942 interim statement where transaction detail is also wanted. The response carries a related reference back to the MT920, so the requester can match the answer to the question even when several requests are outstanding at once. The whole exchange is designed to complete quickly, because a balance report that arrives late is a balance report that misleads.

The MT920 exists because balances are a moving target. During the operating day, payments arrive and leave, and the balance on a nostro account can swing by millions in an hour. A treasurer funding the afternoon payment run needs the position now, not the position at the last statement. A requested snapshot at a chosen time beats a scheduled report at a fixed time, because the requester chooses the moment that matters: before a funding decision, before a cut off, or after a large expected receipt. The MT920 is how the requester takes control of the timing.

The floor limit indicator adds a second use: exception driven reporting. Instead of requesting a report at a fixed time, the requester can ask to be told when the balance crosses a threshold. The servicing bank watches the account and sends the report when the floor is breached. This is useful for accounts that must never fall below a minimum, for liquidity buffers, and for accounts where a low balance signals a failed receipt. The requester gets the information at the moment it becomes important, without polling the account all day.

In ISO 20022 the MT920 maps to the camt.060, the AccountReportingRequest. The camt.060 carries the same request with richer data: the account, the report type, the balance types wanted, and the schedule or trigger. The MT941 and MT942 responses map to the camt.052, the BankToCustomerAccountReport. The question and answer pattern survives migration unchanged, because the business need is unchanged: treasurers will always need to ask for the position now, and the standard will always need a message that asks.
