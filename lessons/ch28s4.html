What you will learn

Your objective. By the end of this lesson, you will be able to explain writing jira user stories for payments. A user story is a short description of a feature written from the perspective of the person who needs it, and it is the unit of work that agile payments teams build, test and release.

Why it matters. A story without a testable acceptance criterion cannot be built or tested, so the analyst who writes the criterion decides whether the developer builds the right mapping and whether the tester can prove it.

Chapter objective: Learner applies business analysis techniques to a payments project, writing requirements, user stories, acceptance criteria, and a traceability matrix for a real payment feature. Learner applies this skill in realistic banking scenarios, with clear examples and correct terminology throughout.

Key terms

Charge bearer: A code that states who pays the charges for a payment. In ISO 20022 the values are DEBT for debtor, CRED for creditor, SHAR for shared and SLEV for service level.

Value date: The date on which funds become available to the beneficiary and on which interest starts to accrue. It is the date used for settlement and for nostro posting.

ISO 20022: An international standard for financial messaging that defines XML message formats for payments, securities and trade.

Exercise

Read the ISO 20022 migration message described in this lesson and identify its key parts.

Use the message structure, fields and example in this lesson.

  1. What to do. List the main blocks of the message, name the field that carries the amount, and name the field that identifies the payment.

Correct result. The MT103 is made of numbered fields. Field 20 carries the transaction reference that identifies the payment, and field 32A carries the value date, currency and interbank settlement amount, which maps to IntrBkSttlmDt and IntrBkSttlmAmt in pacs.008. The instructed amount comes from field 33B where the payment carries one.

Why. A message is only useful if you can read it. The blocks tell the receiving bank what to do, and the amount and identification fields are what it checks first.

A user story is a short description of a feature written from the perspective of the person who needs it, and it is the unit of work that agile payments teams build, test and release. The standard format is simple. As a named role, I want a named capability, so that I get a named benefit. For payments, the role might be a payment operations officer, a corporate customer, or a compliance analyst. The benefit must be real and measurable, such as reducing manual repair work or meeting a regulatory deadline, because a story without a clear benefit is hard to prioritise. Stories are grouped under epics, which are large bodies of work that span several sprints. An epic for ISO 20022 migration might cover the conversion of all outward SWIFT payments from MT format to pacs.008, and it would contain dozens of stories. One for the field mapping, one for the validation rules, one for the exception handling, and one for the reporting. Each story is small enough to be completed in a single sprint, and each one has acceptance criteria that define exactly when it is done. Acceptance criteria are written in the Given, When, Then format, which makes them testable. Given describes the starting state, When describes the action, and Then describes the expected result. A good criterion is specific enough that a tester can run it without asking the analyst a follow-up question. For example, given an MT103 with a valid beneficiary IBAN, when the message is converted, then the pacs.008 must contain the same IBAN in the creditor account identification field. Vague criteria such as the message should convert correctly are not acceptable. A worked example makes the format concrete. Consider the story. As a payment operations officer, I want the system to convert an outward MT103 into a pacs.008 message automatically, so that cross-border payments meet the ISO 20022 standard without manual intervention. The story belongs to the epic called ISO 20022 Migration for Outward Payments, it is estimated at five story points, and it has a clear definition of done. The conversion runs in the test environment, all acceptance criteria pass, and the mapping document is updated. The acceptance criteria for this story cover the main mapping, the edge cases and the failure paths. First, given an MT103 with field 32A value date 15 November 2024, currency USD and amount 125,000, when the message is converted, then the pacs.008 must carry the same value date, currency and amount in the instructed amount field. Second, given an MT103 where field 50K contains the ordering customer name and account, when the message is converted, then the debtor name and debtor account in pacs.008 must match exactly. Third, given an MT103 with an invalid currency code, when the conversion is attempted, then the message must be rejected to the repair queue with the error code INVALID_CCY. Two more criteria complete the story. Fourth, given an MT103 with field 71A set to OUR, when the conversion runs, then the pacs.008 charge bearer must be DEBT, which is the ISO 20022 equivalent of OUR. Fifth, given a converted pacs.008, when the message is validated against the ISO 20022 schema, then it must pass with zero schema errors. These five criteria give the developer a precise target and the tester a precise checklist, and the story is only marked done when all five pass in the test environment.
