What you will learn

Your objective. By the end of this lesson, you will be able to explain mandatory, optional and conditional fields, schema validation, external code sets, version management and market practice rules. Every field in an ISO 20022 message has a usage rule, mandatory, optional, or conditional.

Why it matters. This matters because the message is the payment instruction. A wrong field, a missing element or a misunderstood format is a failed payment, a return, or a compliance breach.

Chapter objective: Learner navigates the complete ISO 20022 catalogue, selecting the right message for each business scenario across payments, cash management, securities, and reporting. Learner practises this skill on realistic banking cases, explaining the reasoning clearly and using correct terminology throughout the work.

Key terms

Remittance information: Information that explains what a payment is for, such as invoice numbers, contract references or salary month.

Market practice: An agreed way of using a message standard in a particular market or community, covering field usage, codes and validation rules.

Charge bearer: A code that states who pays the charges for a payment. In ISO 20022 the values are DEBT for debtor, CRED for creditor, SHAR for shared and SLEV for service level.

Every field in an ISO 20022 message has a usage rule, mandatory, optional, or conditional. A mandatory field must always be present, such as the message identifier in the group header and the instructed amount in a pacs.008 transaction. An optional field may be present or absent, such as the ultimate creditor name when the creditor and the ultimate creditor are the same person. A conditional field is required only when a stated condition is true, such as the creditor agent BIC when the payment is sent through SWIFT, or the mandate reference when the payment is a direct debit. A message that omits a mandatory field is rejected, and a message that includes a conditional field without its condition can also be rejected, so the rules must be read carefully. Schema validation checks a message against its XML schema, the XSD file that defines the structure, the order, the data types, and the lengths of every field. A schema check will reject a message where the amount is written as text instead of a number, where a date is written as 06/11/2026 instead of 2026-11-06, where a name is longer than the allowed seventy characters, or where a field appears in the wrong order. Schema validation is only the first check, because a message can be perfectly valid against the schema and still be wrong for business reasons, such as an amount with three decimal places for EUR, or a creditor account that does not exist. Business validation runs after schema validation and checks the values themselves. External code sets are the shared lists of allowed values that ISO 20022 uses instead of letting each bank invent its own codes. The charge bearer code set allows only DEBT, CRED, SHAR, and SLEV, and a value of SHARED will be rejected. The service level code set includes SEPA for a Single Euro Payments Area payment and URGP for an urgent payment. The return reason code set includes AC01, AC04, AM04, and MS03, each with a defined meaning. A bank that uses a code outside the allowed set will have its message rejected, and a bank that uses the wrong code from the set will mislead the receiving bank about the nature of the payment, so code sets must be checked against the current published list. Version management is the discipline of knowing which version of a message each counterparty and each payment system expects, and of moving to new versions in a controlled way. A pain.001.001.03 from an older implementation and a pain.001.001.09 from a newer one have different fields and different rules, and a bank cannot send one version to a counterparty that expects the other. The migration to ISO 20022 for cross border payments, known as CBPR plus, moved banks from MT messages to pacs and camt messages over several years, with a coexistence period where both formats were accepted. Each bank published a migration plan with dates, test windows, and a cutover date, and a payment sent after cutover in the old format was rejected. Market practice rules add a further layer on top of the ISO 20022 standard, because the standard allows more than any single payment system needs. The High Value Payment Systems plus group, known as HVPS plus, publishes usage guidelines that state which optional fields must be used, which codes are allowed, and which characters are permitted for high value payments. The Single Euro Payments Area rulebook states the same for euro payments inside Europe, including the maximum execution time and the character set for remittance information. A pacs.008 that is valid against the global schema can still be rejected by a specific payment system if it breaks that system market practice, so a professional must check the standard, the version, and the market practice together before sending a message.

Mandatory, optional, and conditional fields are the three statuses a field can have in an ISO 20022 message. A mandatory field must always be present, and a message without it will be rejected by the schema validation. An optional field may be present or absent, and the receiving bank must accept the message either way. A conditional field must be present if a stated condition is true, and must be absent if the condition is false. For example, in a pacs.008, the instructed amount, InstdAmt, is mandatory, the equivalent amount, EqvtAmt, is optional, and the exchange rate, XchgRate, is conditional, it must be present if the instructed amount is in a different currency from the equivalent amount, and it must be absent if the two amounts are in the same currency. An SME must know the status of each field, because a message with a missing mandatory field will be rejected, and a message with a conditional field that should not be present will also be rejected.

Schema validation is the process by which a system checks a message against the XML schema definition, XSD, for that message type and version. The XSD defines the structure, the fields, the data types, and the allowed values. A message that does not conform to the XSD, for example because a field is missing, because a field has the wrong data type, or because a field has a value that is not in the allowed list, will fail schema validation and will be rejected. Schema validation is the first check a receiving bank performs, before it applies any business validation. A message that fails schema validation is not processed, and the sending bank receives a rejection, normally with a pacs.002 status of RJCT and a reason code of FF01, invalid file format, or a reason code that states the specific schema error.

External code sets are the lists of codes that ISO 20022 uses for fields such as the charge bearer, the purpose, the service level, the local instrument, the category purpose, and the status reason. The codes are published by ISO in the external code sets, and they are updated regularly. For example, the charge bearer code set includes DEBT, CRED, SHAR, and SLEV. The purpose code set includes SUPP for supplier payment, SALA for salary payment, RENT for rent payment, and TAXS for tax payment. The service level code set includes SEPA, URGP for urgent payment, and SDVA for same day value. The status reason code set includes AC01, AC04, AC06, AM04, AM05, AG01, MD07, RC01, and FF01. An SME must know the code sets, because a message with a code that is not in the code set will fail schema validation, and a message with a code the receiving bank does not recognise will be treated as an error, even if the code is valid.

Version management is the process of managing the different versions of a message, and it is a significant issue in ISO 20022, because the standard evolves and the versions change. A pacs.008.001.08 and a pacs.008.001.10 are different versions, and they have different fields and different rules. The CBPR+ usage guidelines specify which version to use for cross border payments, and they state the market practice rules that narrow the standard. A bank must support the version its counterparty uses, and it must handle the migration from one version to another. The migration is normally done on a big bang date, when all banks move to the new version at the same time, or on a phased basis, when the banks move in groups. An SME must know the version in use, and must plan for the migration, because a message in the wrong version will be rejected.

Market practice rules are the rules that a community, such as the CBPR+ community, or a scheme, such as SEPA, adds to the ISO 20022 standard, to narrow it to a specific implementation. The standard allows many options, and the market practice rules state which options to use. For example, the ISO 20022 standard allows the charge bearer to be DEBT, CRED, SHAR, or SLEV, but the CBPR+ market practice rules may state that only DEBT, CRED, and SHAR are allowed, and that SLEV is not used. The standard allows the remittance information to be structured or unstructured, but the market practice rules may state that only unstructured remittance information is used, and that it is limited to 140 characters. An SME must know the market practice rules for the community it works in, because a message that conforms to the standard but not to the market practice rules will be rejected by the receiving bank.

Truncation is a specific issue in the migration from MT to ISO 20022. The MT messages have fixed length fields, for example field 70 remittance information is 4 lines of 35 characters, a total of 140 characters. The ISO 20022 messages have longer fields, for example the unstructured remittance information is 140 characters, but the structured remittance information can be much longer. When a bank converts an MT103 to a pacs.008, it must map the MT fields to the ISO 20022 fields, and it must handle the cases where the MT field is longer than the ISO 20022 field, or where the ISO 20022 field is longer than the MT field. The CBPR+ usage guidelines state the truncation rules, and the bank must follow them, because a truncated field can lose information, and a lost remittance reference can cause the beneficiary to be unable to match the payment to an invoice.

For a business analyst, the field status and validation requirement must state the mandatory, optional, and conditional fields, the schema validation, the code sets, the version, and the market practice rules. The requirement should say that the system validates each message against the XSD before sending it, that it uses only the codes in the external code sets, that it uses the version specified in the CBPR+ usage guidelines, and that it follows the market practice rules for the community. A system that does not validate against the XSD will send invalid messages, and a system that does not follow the market practice rules will have its messages rejected by the receiving bank, even if they are valid against the standard.
