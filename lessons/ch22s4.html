Key terms

Authorisation: Approval by the issuer for a card transaction to proceed, confirming the card is valid and funds or credit are available.

Scheme: A card or payment network that sets the rules, standards and fees for transactions between issuers and acquirers.

Issuer: A bank or licensed institution that issues payment cards to customers and holds their accounts. It authorises transactions, debits cardholder accounts, and manages credit limits and fraud controls.

Use the four-party model and the stage timings in this lesson.

  1. What to do. State what happens at each stage, who pays whom, and when the merchant is actually credited.

Correct result. Authorisation holds the funds and returns a response code. Clearing sends the transaction in a batch file. Settlement moves the net amount between banks, and the acquirer credits the merchant after deducting interchange, scheme fees and its margin.

Why. A card payment is not one event. The customer sees it on Monday, the merchant gets it on Wednesday, and the difference is the clearing and settlement cycle.

Tokenization replaces a sensitive value with a surrogate value that has no meaning on its own. In cards, the real card number, known as the primary account number, is replaced by a token. If a merchant database is breached and the tokens are stolen, the thief cannot use them to pay elsewhere, because a token is only valid in the context where it was issued. The real card number is held securely in a token vault, and only the token service provider can map a token back to the real number. That single change transforms the security of card data, because the value stored by merchants and wallets is no longer the value that can be used to commit fraud. Step one is the token request, and it starts when a customer saves a card. The customer enters the card number once, with a merchant, a wallet or a payment service provider, known as the token requestor. The requestor sends a token request to the token service provider, usually the card scheme itself for a network token. The token service provider checks the card with the issuer, and if the issuer approves, it creates a token, stores the mapping in the vault, and returns the token to the requestor. From that moment the merchant stores the token, not the real card number, and the real number never needs to be stored or transmitted again. Step two is the token in use, and a network token behaves like a card number with controls attached. A network token looks like a card number, it passes the usual format checks, and it carries domain controls set at issue: it may be valid only for one merchant, only for one device, only up to a spending limit, or only until an expiry date. When the customer pays, the merchant sends the token instead of the real number in the authorisation request. The scheme or the token service provider detokenizes it, replacing the token with the real number before routing to the issuer, and the issuer sees that the transaction used a token. Step three is the payment itself, and the token adds a security check at authorisation. Many tokenized transactions also carry a cryptogram, a one time code generated for that transaction, which the issuer validates before approving. If the cryptogram is missing or wrong, the issuer declines, even if the token itself is valid. Schemes report that tokenized transactions have higher approval rates and lower fraud rates than transactions using the real card number, because the token plus the cryptogram proves the payment came from the enrolled merchant or device. For the analyst, this is a measurable benefit to track: approval rate and fraud rate, tokenized against non tokenized, for the same merchant. Step four is the card lifecycle, and this is where network tokens save the customer real effort. When a card expires or is replaced because it was lost, the scheme updates the token automatically through its lifecycle service, so the customer does not need to update saved details with every merchant. The merchant keeps using the same token, and the token service provider maps it to the new card number. Without tokens, a reissued card breaks every saved payment, and the merchant loses sales while customers re-enter details. Exceptions in tokenization have their own paths. A token provisioning request can be declined by the issuer, for example if the card is blocked, and the customer must be told to use another card. A token can be suspended when fraud is suspected, and payments using it will decline until it is reactivated. A token used outside its domain, for example a merchant specific token presented by a different merchant, will be rejected by the token service provider. Each of these is a decline with a specific reason, and the merchant journey must explain it in plain language instead of showing a generic payment failed message. For the analyst, tokenization changes where sensitive data lives and how it flows. A design that stores tokens instead of real card numbers reduces the scope of payment security compliance, because the merchant no longer stores the value that attackers want. It simplifies breach response, because stolen tokens cannot be reused elsewhere. And it improves the customer experience when cards are replaced.
