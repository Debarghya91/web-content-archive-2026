Your objective. By the end of this lesson, you will be able to explain exercise: design an instant payment flow (initiation to confirmation with timeouts, retries and failure handling). Start with the scenario and the actors, because a design without a scenario is only a diagram.

Why it matters. This matters because the next payment product you work on may use one of these technologies. Knowing what is real and what is still a proposal is what separates a good analyst from a confused one.

Chapter objective: Learner designs real-time payments architecture, covering 24 by 7 availability, instant clearing, liquidity, and failure handling, and explains how it differs from batch systems. Learner applies this skill in realistic banking scenarios, with clear examples and correct terminology throughout.

Key learning points

  • Scenario and actors
  • Happy path drawn first with a time budget
  • Hub and pacs.008 message
  • Hub and scheme using original end-to-end identifier
  • Retry once with the same key and reference
  • Empty settlement account

Key terms

Sanctions screening: Checking payment parties, countries and references against sanctions lists published by governments and international bodies.

Reconciliation: The process of comparing records from two sources, such as a bank statement and an internal ledger, to confirm they agree.

Fraud scoring: A risk score assigned to a payment based on factors such as amount, location, device, velocity and customer history.

Start with the scenario and the actors, because a design without a scenario is only a diagram. Your customer is a small business owner in Manchester who needs to pay a supplier GBP 4,800 before a five o clock deadline. She opens her mobile banking app, enters the supplier sort code and account number, and sees a confirmation of payee match. She taps pay, and the app shows a spinner while the payment is processed. Your flow must cover the app, the channel layer, the payment hub, the fraud and sanctions checks, the core banking debit, the scheme, and the receiver bank, and it must end with a confirmation screen that she can trust. Draw the happy path first, and put a time budget on every step. The app sends a payment instruction to the channel layer with a unique idempotency key. The channel layer turns that instruction into a pain.001 XML message, which is the format the instruction takes when it travels as a message or a file, and forwards it to the hub within one second. The channel validates the format and forwards the payment to the hub within one second. The hub runs account validation, sanctions screening, and fraud scoring in parallel, completing all three within one second. The core banking system debits GBP 4,800 and returns a success response within two seconds. The hub sends a pacs.008 message to the Faster Payments scheme, which forwards it to the receiver bank. The receiver credits the supplier and returns a pacs.002 acceptance, which travels back to the app as a confirmation within ten seconds of the tap. Add a timeout to every external call, and define what happens when each one fires. Give the core banking call a three-second timeout, the scheme call a five-second timeout, and the whole end-to-end journey a ten-second limit. If the core banking call times out, the hub must query the core system for the status of that debit before doing anything else. If the scheme call times out, the hub must query the scheme using the original end-to-end identifier. Never retry a payment blindly after a timeout, because the first attempt may have succeeded. Write the timeout values into your diagram, and check that each inner timeout is shorter than the outer timeout that contains it. Design the retry and duplicate rules next, and make them explicit enough for a developer to build. The mobile app must disable the pay button after the first tap and show a processing state, so a double tap cannot create a second instruction. The channel layer must store the idempotency key before forwarding the payment, and return the stored result if the same key arrives again. If the scheme returns a technical rejection, the hub may retry once with the same key and the same reference. If the scheme returns a business rejection, such as an invalid account, the hub must not retry, but must reverse the debit and tell the customer the exact reason. Finish with the failure cases and the reconciliation that catches what the flow misses. Test your design against three failures, a lost pacs.002 confirmation, a settlement account that runs dry at midday, and a fraud hold that needs a human decision. For the lost confirmation, define a status query and a reconciliation job that runs every five minutes. For the empty settlement account, define a queue and a treasury alert that triggers an automatic top-up. For the fraud hold, define a pending state, a workbench case, and a customer message that explains the delay. Present your flow as a diagram plus a one-page table of timeouts, retries, and failure actions, and ask a colleague to break it.
