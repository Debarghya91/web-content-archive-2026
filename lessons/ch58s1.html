Key terms

Reconciliation: The process of comparing records from two sources, such as a bank statement and an internal ledger, to confirm they agree.

Settlement: The final movement of funds between banks to discharge obligations created by cleared payments. Settlement is usually made in central bank money or through correspondent accounts.

Creditor: The party that is owed money and receives a payment, such as a supplier, a seller or a service provider.

The one rule that decides reject versus return is timing, and it is simple to state. If a payment has not yet been credited to the creditor account, the problem is handled as a reject. If the payment has already been credited to the creditor account, the problem is handled as a return. That distinction sounds small, but it drives the whole CBPR+ flow, because a reject stops a payment before value reaches the beneficiary, while a return takes value back after the beneficiary bank has already received it. Operations teams that learn this rule first make far fewer errors than teams that try to memorise lists of reason codes.

A reject happens while the payment is still in flight between banks, before the creditor agent has posted the funds. For example, Deutsche Bank in Frankfurt receives a pacs.008 for USD 100,000 from JPMorgan Chase in New York, and its validation finds that the creditor account number is closed. Deutsche Bank has not credited any customer account, so it rejects the payment. It sends a pacs.002 with a rejection status back to JPMorgan Chase, and the funds never reach the intended beneficiary. The original payment instruction is dead, and no new settlement instruction is needed to move the money back.

A return happens after the creditor agent has already credited the beneficiary, and later discovers a problem or receives a request to send the money back. For example, BNP Paribas in Paris credits EUR 50,000 to a corporate customer, and the customer then reports that the payment was sent in error and asks for the funds to be returned. BNP Paribas cannot simply send a status report, because the money is already in the customer account. It must create a new payment instruction, a pacs.004, to move the funds back through the chain. The original pacs.008 remains a settled payment in the records, and the pacs.004 is a separate transaction.

The reason codes also change with the timing, and that is where many learners get confused. A reject uses status reason codes in pacs.002, such as AC01 for an incorrect account number, AM05 for a duplicated payment, or BE04 for a missing creditor address. A return uses return reason codes in pacs.004, such as AC03 for an invalid account number discovered after credit, DUPL for a duplicate payment, or FRAD for a fraudulent payment. The code families overlap in meaning, but they live in different messages, and sending the wrong code in the wrong message will fail validation at the next bank. Always check the timing first, then choose the message, then choose the code.

In practice, the timing test also protects the customer and the bank from double handling. If a bank tried to return a payment that was never credited, the return would move money that was never received, and the nostro account would go out of balance. If a bank tried to reject a payment that was already credited, the status report would claim the funds were never delivered, while the beneficiary still held them, and the reconciliation would break. A simple question at the start of every case prevents both failures. Has the creditor account been credited yet. If the answer is no, reject with pacs.002. If the answer is yes, return with pacs.004. That discipline keeps every case clean.
