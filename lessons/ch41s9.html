Key terms

Value date: The date on which funds become available to the beneficiary and on which interest starts to accrue. It is the date used for settlement and for nostro posting.

Repair: Manual correction of a payment that failed straight through processing because of missing or invalid data.

Return: A payment that is sent back to the sender after settlement because it cannot be credited to the beneficiary.

Transcript and full text

Show transcript

Repair is the work of fixing a message that failed, so that it can proceed. A message can fail validation, fail processing, or fail a business check, and each failure lands in a repair queue with an error code and the message content. The repair handler diagnoses the failure, decides what to do, applies the fix, revalidates, and resubmits. Repair is skilled work: it needs knowledge of the message standard, the business rules, and the counterparties, and it needs judgement about when to fix and when to return. A repair operation that is fast but careless creates worse problems than the failures it fixes.

Failures fall into three types. Format errors: a field in the wrong format, an invalid character, a value that breaks a network validated rule. Data errors: a missing mandatory field, an unknown account, an invalid code, a reference that does not match. Business errors: insufficient funds, a closed account, a sanctions hit, a limit breach. The type decides the repair path. Format errors are usually fixed from the message itself. Data errors need information, from the sender, from reference data, or from the customer. Business errors often cannot be repaired at all: the payment must be returned, queued, or escalated, because the problem is not in the message but in the world the message describes.

The repair workflow is a loop with controls. The failure is queued with its error code. The handler diagnoses: what failed, why, and what the correct value should be. The handler decides: repair the data, request information from the sender, or return the payment. The fix is applied, the message is revalidated against the full rule set, not just the failed rule, and the message is resubmitted. Every repair is logged: who repaired it, what was changed, what the evidence was, and when. The log is the audit trail, and it is also the data that feeds prevention: the repairs that happen most often point at the validations that should exist upstream.

The hardest repair decision is repair versus return. Repair when the correct data is known with confidence: an obvious formatting error, a code that maps unambiguously, a truncation that can be restored from the source. Return when the instruction itself is wrong, or the correct data cannot be established: a wrong beneficiary, an unknown account, an amount that does not match the instruction. Repairing a payment into a different payment is a control failure: the repaired message must be the same instruction, correctly expressed, not a new instruction invented by the handler. When in doubt, ask the sender. A returned payment is a delay; a wrongly repaired payment is a loss.

Common repairs have standard patterns. Account number corrections, validated against modulus checking and directory lookups before the repair is applied. Field truncation fixes, restoring data cut off by a length limit from the source system. Code corrections, mapping an obsolete or invalid code to the current valid value. Value date corrections, where the date in the message cannot be honoured and the next valid date applies. Each pattern needs a documented rule, an authority level, and a test: the handler must know what they are allowed to fix alone, what needs a second pair of eyes, and what needs the sender.

Prevention is the purpose of repair data. Every repair is a signal that something upstream failed: a customer sent bad data, a mapping dropped a field, a validation was missing. The most repaired errors become new upfront validations, new customer guidance, or new mapping rules. Repair rates are a quality metric, reported alongside the straight through processing rate: a falling repair rate means the operation is getting cleaner, and a rising repair rate means a new problem has arrived. The best repair operation is the one that repairs less every quarter, because it designed the failures out instead of just working them faster.
