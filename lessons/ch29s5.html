Key terms

Reconciliation: The process of comparing records from two sources, such as a bank statement and an internal ledger, to confirm they agree.

Purpose code: A code that states the commercial reason for a payment, such as supplier payment, salary or goods. Purpose codes are taken from an ISO external code list and support regulatory reporting, screening...

Value date: The date on which funds become available to the beneficiary and on which interest starts to accrue. It is the date used for settlement and for nostro posting.

A test case is a structured instruction that tells the tester exactly what to do and what result to expect, and it has a fixed format. A test case identifier, a title, a precondition, a set of steps, the expected result for each step, and the actual result recorded during execution. A test case for the migration might be titled Convert MT103 with valid data to pacs.008, with the precondition that the test environment holds a valid MT103 message, and steps that walk the tester through submission, conversion and verification. The tester marks each step as pass or fail, and a test case only passes when every step passes.

The happy path test case is the simplest. A valid payment flows through without any exception. The tester submits an MT103 for 125,000 US dollars from a corporate account in Mumbai to a supplier in Frankfurt, with a valid IBAN, a purpose code of P0101, and a value date of 15 November 2024. The expected result is that the pacs.008 is generated within five seconds, that the debtor and creditor details match the MT103 exactly, that the instructed amount is 125,000 dollars, and that the payment status changes to Released. The tester also checks the reconciliation report to confirm the payment appears with the status Converted.

The reject path test case checks what happens when a payment fails validation. The tester submits an MT103 with an invalid beneficiary IBAN, where one character has been deliberately changed so the modulus 97 check fails. The expected result is that the message is not converted, that it appears in the repair queue within one minute with the error code INVALID_IBAN, that no pacs.008 is generated, and that no debit is posted to the customer account. The tester then corrects the IBAN in the repair screen and resubmits, and the expected result is that the conversion completes and the payment is released.

The return path test case checks what happens when the beneficiary bank cannot apply the payment. The tester releases a pacs.008 for 75,000 euros to a beneficiary in Paris, and then simulates a pacs.004 return message from the beneficiary bank with the reason code AC01, meaning the account number is incorrect. The expected result is that the original payment status changes to Returned, that the 75,000 euros is credited back to the debtor account, that a notification is sent to the customer, and that the reconciliation report shows the original payment and the return linked by the same end-to-end identification.

The recall path test case checks the cancellation flow. The tester releases a pacs.008 for 50,000 US dollars, and then the customer asks the bank to recall the payment because the supplier details were wrong. The tester raises a camt.056 recall request, and the expected result is that the recall is sent to the beneficiary bank, that the payment status changes to Recall Requested, and that when the beneficiary bank accepts the recall, a pacs.004 return is received and the 50,000 dollars is credited back. The tester also checks the negative path, where the beneficiary bank rejects the recall because the funds have already been released, and the status changes to Recall Rejected with the reason displayed.
