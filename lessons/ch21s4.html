Key terms

Authorisation: Approval by the issuer for a card transaction to proceed, confirming the card is valid and funds or credit are available.

Settlement: The final movement of funds between banks to discharge obligations created by cleared payments. Settlement is usually made in central bank money or through correspondent accounts.

Clearing: The process of exchanging payment instructions between banks and calculating what each bank owes the others.

Practise this lesson

Exercise

Trace a card sale from authorisation on Monday to settlement on Wednesday.

A shop owner sees a card sale authorised on Monday, cleared on Tuesday, and settled on Wednesday. In a shop, batching usually happens automatically at the end of the day, when the terminal sends a batch of all the day authorised transactions to the acquirer.

  1. What to do. State what happens on each of the three days, and what happens to a transaction that was authorised but never sent for clearing.

Correct result. On Monday, authorisation holds the funds and returns a response code, but no money moves. At the end of the day the terminal batches the authorised transactions and sends them to the acquirer, which sends a clearing file to the scheme. On Tuesday, clearing turns the authorised transactions into financial obligations: the scheme validates the file, sorts the transactions by issuer, and calculates interchange. On Wednesday, settlement moves the net amounts between banks, and the acquirer credits the merchant after deducting interchange, scheme fees and its margin.

A transaction that was authorised but never cleared does not appear in settlement at all.

Why. Clearing discipline, including timely presentment, is a control the analyst must watch, because a late or missing batch means the merchant is not funded on time.

Batching is how the acquirer collects captured transactions and prepares them for clearing. At agreed cut off times, usually once a day, the acquirer groups all the transactions it has received from its merchants into clearing files, organised by scheme and by issuer. Each file contains the full details of every transaction, including the card number, the amount, the merchant, the date and the authorisation code that links the clearing record back to the original authorisation. The acquirer sends these files to the scheme, which validates them and sorts them for delivery to each issuer.

The scheme plays a central role in clearing. It checks each file for errors, such as missing fields, duplicate transactions or amounts that do not match the authorisation. It converts currencies where needed, for example when a customer uses a card issued in one country to pay a merchant in another. It calculates the totals that each issuer owes and each acquirer is owed, and it prepares settlement reports. The scheme's clearing system is a high volume operation, processing billions of transactions a year, and its accuracy is critical, because an error in clearing can mean an issuer is charged for a transaction that never happened.

Clearing files use standard formats defined by each scheme, and the details matter enormously in implementation work. A business analyst working on a clearing interface needs to understand the file layout, the field definitions, the validation rules and the error handling procedures. They also need to understand the clearing cycle, including cut off times, the treatment of late files, and the process for correcting errors. A file that misses its cut off may be held to the next cycle, which delays settlement to the merchant and can affect the merchant's cash flow, so timing is a real operational concern.

Follow one clearing file through the night. An acquirer batches 8,400 transactions worth Rs 6.2 crore from its merchants at the 10 in the evening cut off and sends the clearing file to the scheme. The scheme validates the file and rejects two records, because their amounts do not match the original authorisations. The acquirer corrects the two records and resubmits, but the corrected file misses the scheme's processing window, so settlement to those two merchants is delayed by a day. A second file arrives at ten forty in the evening, forty minutes after the cut off, and is held for the next cycle entirely, which delays settlement for all of its merchants by a day and affects their cash flow. The file format, the validation rules, and the cut off time are not back office details. They decide when merchants get paid.

An analyst working on a clearing interface needs to document the file layout field by field, the validation rules and the error codes, the cut off times, and the procedure for correcting and resubmitting a failed file. The test pack should include a file with a duplicate transaction, a file with an amount that does not match its authorisation, a file that arrives after cut off, and a file with a missing mandatory field. Each test should assert the error message, the handling, and the effect on merchant settlement timing, because a file that fails silently is worse than a file that fails loudly. The operations runbook should name who is called when a file fails after hours, since clearing files do not respect office hours.
