Exercise

Use the message structure, fields and example in this lesson.

  1. What to do. List the main blocks of the message, name the field that carries the amount, and name the field that identifies the payment.

Correct result. The message is made of blocks, each carrying a part of the payment instruction. The amount field and the identification field are the two a receiving bank checks first, because without them it cannot process or reconcile the payment.

Why. A message is only useful if you can read it. The blocks tell the receiving bank what to do, and the amount and identification fields are what it checks first.

FIN is the original SWIFT service, and it carries MT messages such as MT103, MT202 and MT950 in a store and forward model. The sender creates an MT message, sends it through FIN, and SWIFT stores it until the receiver is ready to collect it. FIN guarantees delivery, provides acknowledgements, and supports the full range of message categories from 1 to 9. A payment of 367,574.90 dollars from BNP Paribas to Banco Santander travels as an MT103 through FIN, and the MT950 statement that Santander receives the next morning also travels through FIN. FIN remains the backbone of cross border payments.

InterAct is an interactive service that supports real time request and response exchanges using XML messages, including ISO 20022 messages such as pacs.008 and pain.001. Unlike FIN, which stores a message and delivers it later, InterAct opens a session between the sender and the receiver and allows them to exchange messages and replies within that session. A bank that wants to query the status of a payment, or to send a single pacs.008 and receive an immediate acknowledgement, will use InterAct. The interactive model suits services where the sender needs an answer in seconds, not minutes.

FileAct is a file transfer service that moves bulk files securely between institutions. It is used for large batches that would be inefficient to send as single messages, such as a file of 50,000 salary payments, a daily statement file, or a bulk sanctions screening file. A corporate client that submits a pain.001 file with 4,000 payments worth 18,000,000 pounds may send that file through FileAct to its bank, and the bank may return a pain.002 status report file through FileAct in return. FileAct supports large files, compression, and delivery confirmations, and it is designed for volume rather than for single transactions.

The three services can work together on one payment. A corporate treasury system might send a pain.001 bulk file through FileAct to its bank, the bank might convert each item into a pacs.008 and send it through InterAct to a clearing system, and the clearing system might return an MT103 through FIN to a correspondent bank for the cross border leg. Each service does the job it is best at, and the BIC remains the routing address throughout. Operations teams must know which service carried each leg, because the investigation path is different for a FIN message, an InterAct exchange, and a FileAct transfer.

The choice of service also affects security, timing and cost. FIN messages are validated against strict MT formats and are subject to SWIFT format checks, while InterAct and FileAct messages are validated against XML schemas and business rules agreed between the parties. FIN delivery is usually measured in seconds, InterAct responses in seconds as well, and FileAct transfers in minutes depending on file size. A bank that sends 10,000 MT103 messages a day through FIN will pay a different tariff from a bank that sends 100 FileAct files a day, and the operations team must understand both tariffs when it designs a new payment product.
