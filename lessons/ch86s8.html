Key terms

Remittance information: Information that explains what a payment is for, such as invoice numbers, contract references or salary month.

Payment hub: A central system in a bank that receives payment instructions from all channels, validates them, applies screening and routing rules, and sends them to the correct clearing system or correspondent.

ISO 20022: An international standard for financial messaging that defines XML message formats for payments, securities and trade.

Correct result. The message is made of blocks, each carrying a part of the payment instruction. The amount field and the identification field are the two a receiving bank checks first, because without them it cannot process or reconcile the payment.

Why. A message is only useful if you can read it. The blocks tell the receiving bank what to do, and the amount and identification fields are what it checks first.

Transcript and full text

Show transcript

The migration from MT to ISO 20022 is usually described as a messaging change, but for compliance teams it is a data change, and the data changes everything about how screening, monitoring and reporting work. ISO 20022 messages carry more data, more structured data, and better identified data than MT messages, and each of those three changes has compliance consequences. More data means more fields to screen. More structured data means screening can be more precise. Better identified data, with legal entity identifiers and structured addresses, means matching can be more accurate. The analyst who treats the migration as a format swap will miss the compliance redesign it requires.

Screening improves first, because structured data matches better than free text. In an MT103, the ordering customer name and address sit in a single field as unstructured lines, and the screening engine must parse the lines, guess which line is the name and which is the address, and match the name against sanctions lists with fuzzy logic that produces false positives. In a pacs.008, the name, the address lines, the town, the country and the postcode are separate structured elements, and the screening engine can match the name element against the lists without guessing. The result is fewer false positives, faster clearance, and fewer payments held for manual review. The analyst must redesign the screening rules for the structured fields, because rules written for unstructured text will not use the structure, and the benefit will be lost.

The legal entity identifier, the LEI, is the second improvement. An LEI is a 20 character code that uniquely identifies a legal entity, and ISO 20022 messages can carry the LEI for the debtor, the creditor and other parties. Screening against LEIs is exact: either the LEI is on a list or it is not, with no fuzzy matching and no name variants to consider. For corporates and financial institutions, LEI screening is faster and more reliable than name screening, and it lets the compliance team focus manual review on the cases where no LEI is present. The analyst must make sure the payment hub captures and passes the LEI where the customer provides it, and must not design a flow that drops the LEI because an intermediate system cannot store it. Dropping the LEI throws away the most precise identifier in the message.

Richer data also creates new compliance obligations. More personal data in messages means more data subject to privacy law, and the bank must handle the structured address, the purpose codes and the remittance information under its data protection rules, including retention limits and cross border transfer controls. More data means more fields that can be wrong, and the bank must validate the new fields, not just pass them through, because a screening decision based on a wrong LEI or a wrong country code is worse than no screening at all. Regulatory reporting benefits from the richer data, because the bank can produce more accurate reports from the structured fields, but the reporting logic must be rebuilt for the new message structures, and the old MT based reports must be reconciled to the new ones during the migration.

The coexistence period is the highest risk phase for compliance. During coexistence, the same payment can arrive as an MT message from one bank and as an ISO 20022 message from another, and the screening engine must screen both formats to the same standard. A sanctions name that is screened in the ISO 20022 message must also be screened in the MT equivalent, and a payment that is truncated during format conversion must not lose the data the screening depends on. The analyst must design the screening to run on a canonical internal model, fed by both formats, rather than running two separate screening implementations, because two implementations will diverge, and the divergence will be found by a regulator, not by the bank. The migration plan must include a screening parity test, proving that the same payment screened in both formats produces the same decision.

A worked example shows the improvement. A payment arrives for a corporate beneficiary with a common name that matches several entries on a sanctions list. In the MT world, the screening engine flags the payment, an analyst spends an hour checking the name variants and the address lines, and the payment is held. In the ISO 20022 world, the message carries the beneficiary LEI, the screening engine checks the LEI against the lists, finds no match, and clears the payment in seconds. The same payment, the same beneficiary, and the compliance outcome changes from an hour of manual work to an automatic clearance, because the data was structured and identified. The migration did not change the law. It changed the data, and the data changed the work.
