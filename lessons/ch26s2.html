What you will learn

Your objective. By the end of this lesson, you will be able to explain REST APIs for payments. Most modern payment APIs use REST, which is an architectural style built on standard HTTP methods and on resources that have clear identifiers.

Why it matters. This matters because APIs and integrations are how systems talk to each other. A badly specified API is a failed payment, a duplicate, or a security hole.

Chapter objective: Learner explains API banking and open banking, including consent, authentication, and third-party access, and writes API requirements for a payment initiation use case. Learner demonstrates this skill using realistic banking examples, explaining each step clearly and using correct terminology throughout.

Key learning points

  • Modern payment APIs use REST
  • Original result of creating new payment return
  • REST call
  • Treasury system
  • Same key returning the original 202 response
  • Error and status code, business code, message

Key terms

Idempotency: The property that repeating the same request has the same effect as sending it once. In payments, an idempotency key lets a client safely retry a request after a timeout without creating a duplicate...

ISO 20022: An international standard for financial messaging that defines XML message formats for payments, securities and trade.

Creditor: The party that is owed money and receives a payment, such as a supplier, a seller or a service provider.

  1. What to do. Write the JSON request with the required fields, the success response, and one error response with its error code.

Correct result. A correct request has all mandatory fields, a valid idempotency key, and the right resource and operation. The success response confirms acceptance, and the error response names the field or rule that failed.

Why. An API contract is a promise between two systems. If the request is wrong, the API must reject it cleanly, not fail silently.

Most modern payment APIs use REST, which is an architectural style built on standard HTTP methods and on resources that have clear identifiers. A payment is a resource, an account is a resource, and a payment status is a resource, each with its own URL. To create a payment, a client sends a POST request to the payments resource with the payment details in the body. To check the status, the client sends a GET request to that payment's URL. To cancel a payment that has not yet been released, the client might send a DELETE or a PATCH request. This consistency is the main strength of REST, because a developer who has used one REST API can understand another one quickly, and standard tools can test and monitor them. Idempotency is the most important payment specific concern in REST API design. Networks fail, and when a client does not receive a response, it does not know whether the payment was created or not, so it will retry. Without idempotency, the retry creates a second payment, and the customer is charged twice. The solution is an idempotency key, a unique value the client sends with the creation request, which the bank stores alongside the payment. If the same key arrives again, the bank returns the original result instead of creating a new payment. A BA writing API requirements must insist on idempotency for every operation that moves money, and must define how long keys are retained and what happens when a key is reused with different payment details. Versioning, pagination and error handling are the other essentials. APIs change over time, and versioning, usually in the URL or in a header, lets the bank improve the API without breaking existing clients. Pagination controls how large lists, such as transaction histories, are returned, so that a client asking for a year's transactions does not receive a single enormous response. Error responses must be consistent and useful, with a machine readable code, a human readable message, and enough detail for the developer to fix the problem, without leaking sensitive information. A BA should review the error catalogue for an API as carefully as the success cases, because developers spend most of their integration time handling errors, not the happy path. A worked example shows a REST call end to end. A corporate treasury system creates a payment of EUR 25,000 to a supplier. It sends POST /v1/payments with a JSON body containing the debtor account, the creditor account, the amount, and an Idempotency-Key header with a UUID. The bank returns 202 Accepted with a payment identifier PAY-20261105-8841 and a status ACCP. The treasury system then calls GET /v1/payments/PAY-20261105-8841/status every 30 seconds until the status changes to ACCC, which confirms the beneficiary was credited. The whole flow takes 8 seconds for a SEPA Instant payment, or up to one business day for a standard SEPA credit transfer. The treasury system stores the payment identifier and the idempotency key, so that if the network times out on the POST, it can safely retry with the same key and receive the same payment identifier back, instead of creating a duplicate payment. A failure scenario tests the error handling. The treasury system sends a payment with a creditor account number that is missing a digit. The bank returns 422 Unprocessable Content with a business error code AC01 and a field path creditorAccount.iban, and a message stating the account number is invalid. The treasury system logs the error, alerts the operator, and does not retry, because retrying the same invalid request will fail again. The operator corrects the account number and resubmits with a new idempotency key, because the instruction has changed. A client that retries a 422 error with the same body is wasting its rate limit; a client that retries a 500 error without an idempotency key is creating a duplicate. For a business analyst, the requirement is to define the error code for each failure, the HTTP status, and the client behaviour for each, and to test each with a real call. Suppose the bank releases v2 of its payments API with a new mandatory field, and a corporate client still on v1 sends a payment without it. Each error needs a status code, a business code, a message, and the action the client should take. The BA should also define the support process: when a developer gets an error they do not understand, who do they call, and how quickly do they get an answer. An API with a good error catalogue and a good support process is adopted; an API without them is abandoned.
