Show transcript

SWIFTNet, the network that carries SWIFT traffic, offers three service families, and only two of them move messages between applications. InterAct carries real time application to application messaging, with requests and responses. FileAct carries file transfer, store and forward, for bulk data. The third family is Browse, and it is different: Browse is the person to application channel, where a human being with a browser interacts with an application over the SWIFTNet secure network. Knowing which family a service uses shapes the integration design, the security model, and the operations around it.

Browse works through the browser the user already has, plus a SWIFT public key infrastructure certificate. The user opens a browser, presents a certificate that identifies them and their institution, and accesses an application hosted on SWIFTNet: a market infrastructure portal, a SWIFT hosted application, or a counterparty application exposed over Browse. The connection runs over secure web protocols, with the certificate providing the identity that a message based flow would carry in its header. No dedicated interface software is needed on the user machine beyond the browser and the certificate, which is what makes Browse the right channel for interactive work.

The uses of Browse are the uses of a person at a screen. Querying a service: looking up the status of a payment, checking a reference data entry, or viewing a report. Submitting a form: entering a request, an instruction, or an administration change that does not justify a full message integration. Administering a service: managing users, certificates, and configurations for a SWIFT service. Browse suits low volume, human initiated, interactive work, where the cost of building a message interface would exceed the value of automating the flow.

Browse differs from InterAct and FileAct in who acts and when. InterAct is application to application: one system asks another, and the answer comes back in real time, with no human in the loop. FileAct is file transfer: bulk data moves store and forward, and the receiver processes it when ready. Browse is human to application: a person initiates each interaction, sees the response on screen, and decides the next step. The same certificate based identity underpins all three families, but the interaction pattern is different, and a service designed for one family cannot simply be moved to another without redesigning the interaction.

Controls for Browse are the controls for any privileged web access, plus SWIFT specifics. Certificates are issued and managed through the institution security officers, with the same rigour as message signing keys. Access rights are granted per user and per application, so a user sees only the services their role needs. Every interaction is logged, creating an audit trail of who accessed what and when. Certificate expiry, revocation, and renewal are operational routines: an expired certificate locks the user out, and a compromised certificate must be revoked immediately, just as a compromised message key would be.

For a business analyst, the practical point is to ask, for every SWIFT service in scope, which channel it uses. A service reached by Browse needs user provisioning, certificate management, and manual procedures, not message mappings and interface queues. A service reached by InterAct needs the reverse. And Browse should not be confused with browsing the standards library: message specifications live in MyStandards and the SWIFT User Handbook, which are web resources for reading documentation. Browse is a SWIFTNet service family for interactive applications. The words sound alike, and the confusion is common, but the two have nothing to do with each other.
