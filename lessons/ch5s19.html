  1. What to do. List the main blocks of the message, name the field that carries the amount, and name the field that identifies the payment.

Correct result. The message is made of blocks, each carrying a part of the payment instruction. The amount field and the identification field are the two a receiving bank checks first, because without them it cannot process or reconcile the payment.

Why. A message is only useful if you can read it. The blocks tell the receiving bank what to do, and the amount and identification fields are what it checks first.

Transcript and full text

Show transcript

Not every exchange between banks fits a standard message. A local market practice, a bilateral arrangement, or a new product may need to carry data that no published message type defines. The SWIFT answer is the proprietary message family, and its Category 1 member is the MT198. The MT198 is a message whose content is defined by agreement between the parties, not by the standard. The envelope is standard: the header, the trailer, and the reference fields follow SWIFT rules. The payload is private: the sender and receiver agree what it contains, and only they know how to read it.

The MT198 is used where a standard message does not exist or does not fit. Examples include market specific reporting between a bank and a local infrastructure, proprietary exchanges between two institutions that share a system, and transitional arrangements while a market moves to a new standard. The key condition is agreement: both sides must implement the same private layout, document it, and test it. A proprietary message sent to a party that does not share the agreement is unreadable by definition. The message is a contract expressed as a format, and the contract must exist before the first message flows.

The structure of the MT198 reflects that bargain. The standard fields carry the transaction reference and any related reference, so the message can be tracked and reconciled like any other. The proprietary content travels in a dedicated proprietary data field, whose layout the agreement defines. SWIFT validates the envelope: the message must be well formed, correctly addressed, and properly authenticated. SWIFT does not validate the content, because the content is private by design. That division of responsibility is the point: the network guarantees delivery and integrity, and the parties guarantee meaning.

The risks of proprietary messages are the mirror image of their flexibility. There is no network validation of content, so a malformed payload is only caught by the receiver, if it is caught at all. There is no interoperability outside the agreement, so adding a new party means a new agreement and a new implementation. Documentation becomes critical: if the private layout lives only in one team memory, the exchange breaks when that team changes. A business analyst should treat every proprietary message as a liability to be managed: documented, versioned, and reviewed regularly against the question of whether a standard message now covers the need.

The MT198 has siblings in other categories, following the same n98 pattern. The MT298 is the proprietary message in Category 2, for financial institution transfers, and the MT998 is the proprietary message in Category 9, for cash management and customer status. The pattern repeats because the need repeats: every category has exchanges that the standard does not cover. The numbering itself is a useful clue: any message type ending in 98 is proprietary, and its content is defined by agreement rather than by the standard.

In the ISO 20022 world the need for proprietary content does not disappear, but the mechanisms change. Supplementary data elements let a standard message carry agreed additional data without breaking validation. Structured remittance and extended party information reduce the cases where a proprietary payload is needed at all. The investigation analogue is the camt.035, the proprietary format investigation, which carries a proprietary investigation in a standard envelope. The lesson transfers across eras: prefer a standard message wherever one fits, use a proprietary format only where no standard fits, and document the private layout as carefully as the standard itself.
