Bonus 1: Fine-tune an LLM for function-calling

Concepts plus a small worked example. Bonuses do not count toward certificates.

3 lessons.

Lesson B1.1: Why fine-tune for function calling

Fine-tuning for function calling means training a model on examples of choosing the right tool and filling in its arguments correctly. A general model can already call tools, but it may pick the wrong tool, invent an argument, or format the call badly. Fine-tuning teaches the exact behaviour you want: given this kind of request, call this tool, with these arguments, in this format. It is worth doing when you have many examples of correct calls, the tool set is stable, and the same kinds of requests repeat often. It is not worth doing when the tools change every week, when you have only a handful of examples, or when a clearer prompt already fixes the errors. Fine-tuning is a complement to good tool design, not a replacement for it. A small model fine-tuned on your tools can beat a large general model on your narrow task, because it has learned your exact formats. But it can also forget general skills, so you must test it on both your tool tasks and ordinary questions after training.

Worked example

A team has a triage agent that keeps calling the status tool with a full sentence instead of a bare reference. A clearer prompt helps a little, but the error keeps returning. They collect 200 examples of correct calls from their logs, each showing the request and the exact tool call, and fine-tune a small model on them. After training, the model passes the bare reference almost every time. The team also tests it on ordinary questions to check it has not lost general ability. The fine-tune fixed a repeated, narrow error. It did not fix the tool design, which still needs a clear description.

Hands-on exercise

  1. List the three most common tool call errors in your agent runs so far.
  2. Decide for each one whether a clearer prompt, a better tool description, or fine-tuning is the right fix.
  3. Write down how many correct examples you could collect for the error you would fine-tune.
  4. Note one general skill you would test after fine-tuning, to check nothing was lost.

Lesson B1.2: Preparing training data

Training data for function calling is a set of examples, each with a user request, the correct tool call, and the correct arguments. Quality matters more than size. Each example must show a real request type, the right tool, and arguments copied from the request, never invented. Cover the common cases first, then the tricky ones: similar tools that are easy to confuse, missing arguments the model must ask for, and requests that need no tool at all. Keep a held-out set of examples the model never trains on, so you can measure honestly. Check every example by hand or by script before training: a wrong example teaches a wrong behaviour. Balance the set so no one tool dominates, or the model will favour it everywhere. Write the tool descriptions into the training format exactly as the model will see them at run time, so training matches real use. If your data is thin, collect more from logs before training, rather than training on a small set and hoping.

Worked example

A team prepares 200 training examples for their triage tools. Each example has a request, the correct tool, and arguments taken from the request text. They add 20 examples where two tools look similar, so the model learns the difference, and 20 examples where no tool is needed, so the model learns to answer directly. They hold out 40 examples for testing and check the rest by script for invented arguments. The set is balanced across both tools. Training matches run time exactly, because the tool descriptions in the examples are the same ones the agent uses live.

Hands-on exercise

  1. Take your three most common tool call errors and write five correct examples for each.
  2. Add two examples where similar tools are easy to confuse, and two where no tool is needed.
  3. Set aside a held-out set of examples the model will never train on.
  4. Check every example for invented arguments, and fix or drop any that fail the check.

Lesson B1.3: Worked example and limits

Here is a small worked example. The task is the status lookup from Unit 1. One training example looks like this: the user asks for the status of payment PAY-1042, and the correct call is get_payment_status with the argument PAY-1042, nothing else. A second example asks about PAY-1043, and the call is the same tool with PAY-1043. A third example asks a general question about what a held payment means, and the correct behaviour is no tool call at all, just an answer. After training on many such examples, the model should call the status tool with a bare reference for status questions, and answer directly for general questions. The limits matter as much as the method. Fine-tuning cannot fix a bad tool description, missing data, or a task the model has never seen. It can overfit, learning your exact examples instead of the general rule, which is why the held-out set exists. It also goes stale: when a tool changes, the training data must change too. Treat fine-tuning as one tool in the kit, used for repeated narrow errors, and keep evaluating after every change.

Worked example

A team fine-tunes on 200 status lookup examples. Before training, the model passed a bare reference in about half of its calls. After training, it passes a bare reference in nearly all of them on the held-out set. But a new test shows a limit: when asked about a reference with a typo, the model still calls the tool with the typo instead of asking the user to check it. The training data had no typo examples, so the model never learned that behaviour. The team adds typo examples to the data and retrains. The lesson is that a model only learns what the data shows.

Hands-on exercise

  1. Write three training examples for your status tool: two status questions and one general question needing no tool.
  2. Write one example where the request has a typo in the reference, and the correct behaviour is to ask the user to check it.
  3. List two limits of fine-tuning that apply to your task, and how you would spot each one.
  4. Decide whether fine-tuning is worth it for your agent, and write down why in one sentence.
