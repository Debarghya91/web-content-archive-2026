Unit 2: Frameworks

smolagents, LangGraph, and LlamaIndex. How the Unit 1 fundamentals map onto each one, and when to pick which.

4 lessons. About 3 to 4 hours. All three libraries in this unit, smolagents 1.26.0, langgraph 1.2.24, and llama-index 0.14.26, are free, open-source, and pip-installable.

Lesson 2.1: smolagents in depth

smolagents is a small library built around one idea: let the model write short code that calls your tools. A CodeAgent takes a model and a list of tools, then runs the think, act, observe loop by generating code. The @tool decorator turns an ordinary Python function into a tool the agent can call, using the function docstring as the description the model reads. Because the agent writes code, it can also combine tool results in a few lines, for example by looking up two payments and comparing their statuses. The strengths are simplicity and transparency: the code the agent writes is visible, so you can read exactly what it did. The limits are also clear. Code the model writes can fail, so you need step limits and error handling. The library suits short tasks with a few tools, such as a status lookup or a rule question. It is not the right pick for a long workflow with many branches and approvals, where a state machine fits better. Keep tools small, descriptions precise, and the step limit low.

Try it in your browser (no account needed)

Run this demo in the lesson page. It uses only the Python standard library, no network, and no API keys. It prints each Thought, each Action with its tool call, each Observation, and the final answer.

STATUS = {
    "PAY-1042": "held, reason: missing field",
    "PAY-1043": "complete",
}

def lookup_payment_status(reference):
    return STATUS.get(reference, "reference not found")

# The lines a CodeAgent writes: each line is one tool call in code.
CODE = [
    ("Check the first payment.", "status_1042 = lookup_payment_status('PAY-1042')"),
    ("Check the second payment.", "status_1043 = lookup_payment_status('PAY-1043')"),
]

results = {}
for thought, line in CODE:
    print("Thought: " + thought)
    print("Action: " + line)
    if "PAY-1042" in line:
        results["status_1042"] = lookup_payment_status("PAY-1042")
        print("Observation: " + results["status_1042"])
    else:
        results["status_1043"] = lookup_payment_status("PAY-1043")
        print("Observation: " + results["status_1043"])

print("Thought: Compare the two results.")
print("Action: compare(status_1042, status_1043)")
if results["status_1042"] != "complete" and results["status_1043"] == "complete":
    outcome = "PAY-1042 needs action first."
elif results["status_1043"] != "complete" and results["status_1042"] == "complete":
    outcome = "PAY-1043 needs action first."
else:
    outcome = "Both payments need a check."
print("Observation: " + outcome)
print("Final answer: " + outcome + " PAY-1042 is held because a field is missing. PAY-1043 is complete and needs no action.")

Run it locally (real agent code)

from smolagents import CodeAgent, LiteLLMModel, tool

STATUS = {
    "PAY-1042": "held, reason: missing field",
    "PAY-1043": "complete",
}

@tool
def get_payment_status(reference: str) -> str:
    """Look up the status of a payment by its reference.
    Args:
        reference: the payment reference, for example PAY-1042.
    """
    return STATUS.get(reference, "reference not found")

model = LiteLLMModel(
    model_id="ollama_chat/qwen2.5:7b",
    api_base="http://127.0.0.1:11434",
    num_ctx=8192,
)
agent = CodeAgent(tools=[get_payment_status], model=model, max_steps=6)
answer = agent.run(
    "Check payments PAY-1042 and PAY-1043 and say which one needs action first, with a reason."
)
print(answer)

Install first with pip install "smolagents[litellm]" and start Ollama with ollama pull qwen2.5:7b. The model is swappable: change the model_id and api_base to point at any provider you choose.

What you should see:

PAY-1042 needs action first: it is held because a field is missing. PAY-1043 is complete and needs no action.

Your wording may differ slightly. The answer must name PAY-1042 first with its reason, and must not claim PAY-1043 needs action.

Worked example

An agent needs the statuses of two payments to compare them. With smolagents, it writes a few lines of code: call the status tool for PAY-1042, call it again for PAY-1043, then compare the two results. The code is visible in the log, so a reviewer can see both calls and the comparison. If the second call fails, the agent sees the error as an observation and can say so, rather than comparing a real status with an invented one. The visible code is the audit trail: anyone can check what the agent actually did.

Hands-on exercise

  1. Add a second tool to your Unit 1 agent, for example a detail lookup that returns the missing field for a held payment.
  2. Ask the agent to check two payments and report which one needs action first, with a reason.
  3. Read the code the agent wrote in the log and check that both tool calls happened.
  4. Tighten one tool description that the agent misread, and run the task again.

Lesson 2.2: LangGraph, state machines for payment flows

LangGraph builds agents as graphs: nodes that do work, and edges that decide what happens next. The shared state is the key idea. Every node reads the same state, for example the payment reference, the status so far, and the list of checks done, and every node writes its result back into that state. Edges can branch: if the payment is held, go to the missing field node; if it is complete, go to the summary node; if a tool fails, go to the human review node. This makes long payment flows predictable. You can see the path a case took through the graph, pause it for approval, and resume it later, which matters when a payment case waits for a person. The cost is more setup than smolagents: you define the state, the nodes, and the edges up front. That cost pays off when the flow has branches, retries, and approval points. Use LangGraph when the workflow matters as much as the answer, and when you need to prove which path a case took.

Try it in your browser (no account needed)

Run this demo in the lesson page. It uses only the Python standard library, no network, and no API keys. It prints each Thought, each Action with its tool call, each Observation, and the final answer.

STATUS = {
    "PAY-1042": "held, reason: missing field",
    "PAY-1043": "complete",
}

def lookup_payment_status(reference):
    return STATUS.get(reference, "reference not found")

def fetch_status(state):
    print("Thought: Fetch the status first.")
    print("Action: lookup_payment_status('" + state["reference"] + "')")
    state["status"] = lookup_payment_status(state["reference"])
    print("Observation: " + state["status"])
    return "check_reason"

def check_reason(state):
    print("Thought: Map the reason to a route.")
    print("Action: route(state)")
    if "missing field" in state["status"]:
        state["route"] = "ask the sender"
    elif state["status"] == "complete":
        state["route"] = "no action"
    else:
        state["route"] = "human review"
    print("Observation: Route is " + state["route"] + ".")
    if state["route"] == "ask the sender":
        return "draft_reply"
    return "END"

def draft_reply(state):
    print("Thought: Write the triage summary.")
    print("Action: draft(state)")
    state["draft"] = state["reference"] + " is " + state["status"] + ". Route: " + state["route"] + "."
    print("Observation: Draft ready.")
    return "END"

NODES = {"fetch_status": fetch_status, "check_reason": check_reason, "draft_reply": draft_reply}
state = {"reference": "PAY-1042", "status": "", "route": "", "draft": ""}
node = "fetch_status"
while node != "END":
    node = NODES[node](state)
print("Final answer: " + state["draft"])

Run it locally (real agent code)

from typing import TypedDict
from langgraph.graph import StateGraph, START, END

STATUS = {"PAY-1042": "held, reason: missing field", "PAY-1043": "complete"}

class TriageState(TypedDict):
    reference: str
    status: str
    route: str
    draft: str

def fetch_status(state):
    return {"status": STATUS.get(state["reference"], "reference not found")}

def check_reason(state):
    if "missing field" in state["status"]:
        return {"route": "ask the sender"}
    if state["status"] == "complete":
        return {"route": "no action"}
    return {"route": "human review"}

def draft_reply(state):
    return {"draft": state["reference"] + " is " + state["status"] + ". Route: " + state["route"] + "."}

def route(state):
    if state["route"] == "ask the sender":
        return "draft_reply"
    return END

graph = StateGraph(TriageState)
graph.add_node("fetch_status", fetch_status)
graph.add_node("check_reason", check_reason)
graph.add_node("draft_reply", draft_reply)
graph.add_edge(START, "fetch_status")
graph.add_edge("fetch_status", "check_reason")
graph.add_conditional_edges("check_reason", route)
graph.add_edge("draft_reply", END)
app = graph.compile()
result = app.invoke({"reference": "PAY-1042", "status": "", "route": "", "draft": ""})
print(result)

Install first with pip install langgraph and run it with Python. The nodes here call the lookup table directly so the graph runs without a model; in a real agent the decide node would call the model. If an import name differs in your installed version, check that version's docs; the pattern stays the same.

What you should see:

{'reference': 'PAY-1042', 'status': 'held, reason: missing field', 'route': 'ask the sender', 'draft': 'PAY-1042 is held, reason: missing field. Route: ask the sender.'}

The final state shows the path the case took: fetched, routed to ask the sender, and drafted.

Worked example

A triage flow has four nodes: fetch status, check the reason, draft a reply, and human review. The state holds the payment reference, the status, and the draft. If the status is held, the edge goes to the reason check. If the reason is a missing field, the edge goes to draft a reply asking for it. If the tool fails, the edge goes to human review. Every case leaves a clear path through the graph, so a reviewer can see why this case went to a human and that case did not. The graph is the control; the model does the thinking inside the nodes.

Hands-on exercise

  1. Sketch a graph for your running example with four nodes and the edges between them.
  2. Write down what the shared state holds at each node.
  3. Add one branch for a tool failure that goes to human review.
  4. Compare your graph with your smolagents version and note which one is easier to audit for this task.

Lesson 2.3: LlamaIndex, retrieval for scheme rules, and choosing a framework

LlamaIndex is built for retrieval: turning documents into an index the agent can search. You load documents, such as scheme rule extracts or internal procedure notes, split them into chunks, and store them in an index. At run time the agent searches the index for the passages most relevant to the question, then answers using those passages. This is retrieval augmented generation, or RAG: the model generates the answer, but the facts come from your documents. It is the right tool when the answer must come from a specific source, such as a rulebook, rather than from the model memory. The quality of the answer depends on the quality of the chunks and the search: short, focused chunks with clear headings beat long, mixed ones. LlamaIndex is not a full agent framework on its own; it is the retrieval layer you pair with an agent. Choosing a framework is then simple. Pick smolagents for short tool tasks, LangGraph for branched workflows with approvals, and LlamaIndex retrieval whenever the answer must be grounded in your documents. Many real systems combine them.

Try it in your browser (no account needed)

Run this demo in the lesson page. It uses only the Python standard library, no network, and no API keys. It prints each Thought, each Action with its tool call, each Observation, and the final answer.

DOCUMENTS = [
    ("missing field", "A payment held for a missing field waits for the sender to supply the field. Do not release it early."),
    ("duplicate payment", "A suspected duplicate payment must be checked against the original reference before any refund."),
]

def retrieve(query):
    return [text for key, text in DOCUMENTS if key in query]

print("Thought: The rule must come from the documents, not from memory.")
print("Action: retrieve('missing field')")
passages = retrieve("missing field")
print("Observation: Found 1 passage: " + passages[0])
print("Thought: Answer using only the retrieved passage.")
print("Action: synthesise(passages)")
answer = passages[0] + " Check the current scheme rulebook for the latest wording."
print("Observation: Answer ready.")
print("Final answer: " + answer)
print("")
print("Thought: Try a question no passage answers.")
print("Action: retrieve('weekend cut-off')")
misses = retrieve("weekend cut-off")
print("Observation: Found 0 passages.")
print("Final answer: No rule passage found for that question. Ask a human instead of guessing.")

from llama_index.core import VectorStoreIndex, Settings, Document
from llama_index.llms.ollama import Ollama
from llama_index.embeddings.ollama import OllamaEmbedding

Settings.llm = Ollama(model="qwen2.5:7b")
Settings.embed_model = OllamaEmbedding(model_name="nomic-embed-text")

documents = [
    Document(text="A payment held for a missing field waits for the sender to supply the field. Do not release it early."),
    Document(text="A suspected duplicate payment must be checked against the original reference before any refund."),
]
index = VectorStoreIndex.from_documents(documents)
query_engine = index.as_query_engine(similarity_top_k=2)
response = query_engine.query("What should we do when a payment is held for a missing field?")
print(response)

LlamaIndex retrieval and choosing a framework

  1. Load documents. Scheme rule extracts and internal procedure notes go in.
  2. Split into chunks. Short, focused chunks with clear headings beat long, mixed ones.
  3. Store in an index. The chunks are stored so the agent can search them.
  4. Search the index. Find the passages most relevant to the question.
  5. Answer from passages. The facts come from your documents, not from model memory.
  6. Choose a framework. smolagents for short tool tasks, LangGraph for branched workflows with approvals, LlamaIndex retrieval when the answer must be grounded in documents. Many real systems combine them.

The index, not the model memory, is the source of truth.

Lesson 2.4: The 8-layer agentic banking AI framework

Good tools are not enough. A bank that wants agents in production needs more than a strong model and a clever prompt: it needs an enterprise-grade architecture that holds together under real load, real data, and real regulation. That is the point of the 8-layer agentic banking AI framework described by Arosti Nahas in a LinkedIn post published 27 Nov 2026. The framework is a blueprint for deploying autonomous AI in financial services. Its holistic point is that the work does not stop at the Orchestration and Model layers. It equally prioritises the Data Foundation, built on real-time unified data fabrics, and strict Governance, Risk and Compliance, incorporating SR 11-7 and EU AI Act checks. The full stack has eight layers, and the post names four of them: Orchestration, Model, Data Foundation, and Governance, Risk and Compliance. To move from AI pilots to secure, scalable production, banks need to master every layer of the stack, not just the ones that demo well. The other four layers are not named in the post, so this course does not name them. What follows is this course's own explanation of what mastering every layer means: the rest of the stack must cover connecting agents to core banking systems, observing what agents do, controlling what an agent can touch, and keeping a human in the loop. A pilot that skips those jobs is a demo, not a production system.

The 8-layer agentic banking AI framework

  1. Orchestration. Runs the agent loop: think, act, observe, repeat.
  2. Model. The foundation model that reasons and writes.
  3. Layer 3, not named in the post. Job, in this course's own words: connects agents to core banking systems.
  4. Layer 4, not named in the post. Job: observes what agents do.
  5. Data Foundation. Real-time unified data fabrics the agent reads from.
  6. Layer 6, not named in the post. Job: controls what an agent can touch.
  7. Governance, Risk and Compliance. SR 11-7 and EU AI Act checks.
  8. Layer 8, not named in the post. Job: keeps a human in the loop.

To move from AI pilots to secure, scalable production, banks need to master every layer of the stack.

Step 1 of 8
paymentstraininghub.com

Worked example

A bank pilots a triage agent like the one in Unit 3. The model is strong and the orchestration works, so the demo impresses everyone. But the pilot has no unified data feed, so the agent reads stale payment data. It has no governance checks, so nobody has tested it against SR 11-7 or EU AI Act expectations. It has no log of what it did, so a wrong triage cannot be explained. And any agent action goes straight through with no human check. The pilot cannot go live, and the team must now build the layers the demo skipped: the data fabric, the governance checks, the observation, the access controls, and the human review step. The framework would have shown those gaps on day one, before the demo, because it asks about every layer, not just the model.

  4. Write down what production ready means for your agent, in one sentence that mentions more than the model.
