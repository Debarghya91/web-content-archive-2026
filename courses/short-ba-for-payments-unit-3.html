Unit 3: Process flows and message mapping

Drawing a payment process flow, mapping it to messages, and finding the gaps.

Lesson 3.1: Drawing a payment process flow

A process flow shows the sequence of steps in a process so that everyone can see it at a glance. Start with the happy path: the steps that happen when everything goes well. Name each step with a verb, such as validate the reference or look up the payment. Use a diamond for a decision, such as is the reference valid, with one branch for yes and one for no. Use swimlanes to show who does each step: the customer, the system, or the operations team. Number the steps so that requirements can refer to them, for example step 3 in the flow. Keep one flow per process and keep it to one page if you can; a flow that needs a wall is really two flows. Add the exceptions after the happy path is clear, as branches off the main line. A flow is finished when a colleague can follow it with a real example and reach the right outcome at every branch. If they cannot, the flow is missing a step, and that missing step is exactly what this unit teaches you to find.

Drawing a payment process flow

  1. Ask status. The customer asks where the payment is.
  2. Validate. The system validates the reference, using a verb for each step.
  3. Decision. Is the reference valid? One branch for yes, one for no.
  4. Look up. On the yes branch, the system looks up the payment.
  5. Show status. The status is updated after the stage completes, then the current status is shown.
  6. Not found. On the no branch, operations shows a clear not found message, so every branch ends in an outcome.

A flow is finished when a colleague can follow it with a real example and reach the right outcome at every branch.

Lesson 3.2: Mapping a flow to messages

Each step of a flow that crosses a system or bank boundary is usually carried by a message, and a message map records that link. The map is a table with these columns: the flow step, the sender, the receiver, the message, the key fields, and what happens next. The four messages a payments BA meets most often in this course are these. A pacs.008 is a FI to FI customer credit transfer. A pacs.002 is a payment status report. A pacs.004 is a payment return. A camt.056 is a cancellation request. A step with no message and no owner is a gap: either the work happens nowhere, or nobody has said how it travels. The map also exposes missing fields. If a step needs the original payment reference to match a return, the map shows whether that reference travels in the message. Build the map beside the flow, not after it, because the two correct each other: the flow shows the order, the map shows the wiring.

Mapping a flow to messages

  1. pacs.008. A pacs.008 is a FI to FI customer credit transfer; it moves the money.
  2. pacs.002. A pacs.002 is a payment status report; it reports the status.
  3. pacs.004. A pacs.004 is a payment return; it returns a payment that cannot be completed.
  4. camt.056. A camt.056 is a cancellation request.
  5. Gap check. A step with no message and no owner is a gap: either the work happens nowhere, or nobody has said how it travels.

Build the map beside the flow, not after it, because the two correct each other.

Worked example. A learner is mapping a flow for a customer credit transfer and needs the exact fields, so she opens the ISO 20022 Explorer on paymentstraininghub.com. The input is simple: she picks MT103 from the list of 27 messages. The tool returns a full field-by-field page. It shows 14 fields, each marked mandatory, optional or conditional, with the business purpose of the message, the sending and receiving participants, the message structure, scheme-specific rules, a valid and an invalid example, validation errors, related messages, and the processing and accounting implications. She reads that field :20: is the mandatory transaction reference, field :32A: carries value date, currency and amount, with the example 261105USD25000,00 for USD 25,000, field :59a: is the mandatory beneficiary customer, and field :71A: states who pays the charges as OUR, BEN or SHA. The valid example is Meridian Bank London sending reference MER1035521 for USD 25,000 to Harbour Bank Singapore for Bright Logistics, invoice INV-1187. The invalid example has a value date in the past and no beneficiary account in :59a:, so the receiving bank rejects it for repair. The related messages list includes pacs.008, the ISO 20022 message that now carries new cross-border customer payments. She copies the :59a: rule into her message map as a validation step and adds pacs.008 to the map as the message for the credit transfer leg. The Explorer gave her the fields; the map records them.

  3. Add one key field per message.
  4. Mark any step that has no message.

Lesson 3.3: Finding the gaps a flow hides

Most flows look complete until they are tested with a real example, and the gaps hide in the same places every time. There is no step for not found, so an unknown reference ends nowhere. There is no timeout, so a payment waiting for a reply waits forever. There is no owner for an exception, so it sits in a queue nobody watches. Duplicate handling is missing, so the same instruction processed twice pays twice. The status is never updated after a return, so the customer sees sent forever. There is no audit trail, so nobody can prove what happened. To find these gaps, walk the flow with a real example and ask what if this fails at every step. Check that every branch ends somewhere, that every status change has a message or a screen update behind it, and that every step has an owner. Then compare the flow with the message map: a flow step with no message is a gap, and a message with no flow step is a gap too. Fixing gaps at the drawing stage costs minutes; fixing them after launch costs weeks.

Finding the gaps a flow hides

  1. Not found. There is no step for not found, so an unknown reference ends nowhere.
  2. No timeout. There is no timeout, so a payment waiting for a reply waits forever.
  3. No owner. There is no owner for an exception, so it sits in a queue nobody watches.
  4. Duplicate. Duplicate handling is missing, so the same instruction processed twice pays twice.
  5. Stale status. The status is never updated after a return, so the customer sees sent forever.
  6. No audit trail. There is no audit trail, so nobody can prove what happened.

Fixing gaps at the drawing stage costs minutes; fixing them after launch costs weeks.

Step 1 of 6
paymentstraininghub.com

Worked example. A learner walks her status enquiry flow with a real example: a payment that was returned. The flow looks up the payment, finds it, and shows the status as sent. But the payment was returned by a pacs.004, and her flow has no step that processes a return, so the status stays sent forever. The gap is a missing branch. She adds a step after the lookup: check for a return, and if a pacs.004 has been received, show returned instead. She also adds a step for an unknown reference, which now shows a clear not found message. Two branches added, two gaps closed, and the flow now survives a real example.

Try it yourself.

  1. Take your status flow and ask what if at each step.
  2. List three gaps you find.
  3. Add the missing branches to your flow.
  4. Check that every branch ends in an outcome.
