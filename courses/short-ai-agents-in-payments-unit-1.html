Unit 1: Agent Fundamentals

The think, act, observe loop, tools, and the language model as the brain.

4 lessons. About 3 to 4 hours.

Lesson 1.1: The think, act, observe loop

Every agent runs the same loop. First it thinks: given the goal and what it knows so far, what should it do next? Then it acts: it calls a tool or writes an answer. Then it observes: it reads the tool result and updates what it knows. Then it thinks again. The loop repeats until the goal is done, the agent asks a human for help, or it hits a step limit. The step limit matters. Without one, an agent that keeps failing can loop forever and burn time and cost. A good agent also keeps a short history of its steps, so each new thought builds on what already happened instead of starting over. In payments, the loop maps neatly onto real work. Think: which check comes first for this exception? Act: call the status lookup. Observe: the payment is on hold. Think again: what does a hold mean, and what is the next check? The loop is simple, and that simplicity is its strength. When an agent misbehaves, the first place to look is the loop: did it think clearly, did it pick the right tool, and did it read the result correctly?

Worked example

An exception arrives: a payment has not reached the beneficiary. The agent thinks: check the payment status first. It acts by calling the status tool. It observes: the payment is held because a field is missing. It thinks again: the next step is to find which field is missing and who can supply it. It acts by calling a detail lookup, observes the missing field, and drafts a message to the sender asking for it. Each step follows from the previous observation. Nothing was guessed. If the status tool had returned an error instead, the agent would have stopped and asked a human, rather than inventing a status.

Hands-on exercise

  1. On paper, trace the loop for a payment status question: write one think, act, and observe line for each of three steps.
  2. Add a step limit of five steps to your trace and note where the agent should stop and ask a human.
  3. Write down what history the agent needs to keep between steps so it does not repeat a tool call.
  4. Compare your trace with the worked example and fix any step where the agent acts before it observes.

Lesson 1.2: Tools, giving the agent hands

A language model on its own can only produce text. Tools give it hands: functions it can call to read data or take actions. A tool has a name, a clear description of what it does, and defined inputs and outputs. The description matters more than the code, because the model reads the description to decide when to call the tool. A good tool does one thing, has a narrow job, and returns a short, clear result. A bad tool does five things at once, takes vague inputs, or returns a wall of text the model cannot use. In payments, useful tools include a payment status lookup, a scheme rule search, a currency conversion, and a log search. Dangerous tools include anything that moves money, changes a payment, or sends a message to a customer without a human check. Give the agent the smallest set of tools that can finish the job. Every extra tool is another chance for the model to pick the wrong one. When a tool call fails, the tool should return a short error the model can understand, not a crash.

Worked example

An agent needs to answer a scheme rule question. It has two tools: search_scheme_rules, which takes a short query and returns the matching rule text, and get_payment_status, which takes a payment reference. The agent picks search_scheme_rules because the question is about a rule, not a specific payment. The tool returns one short rule passage. The agent quotes it and adds that the reader should check the current scheme rulebook for the latest wording. The agent did not call the status tool, because it had no payment reference and the question did not need one. Picking the right tool is half the skill.

Hands-on exercise

  1. List three tools your running example task needs, each with one sentence describing what it does.
  2. For each tool, write its inputs and what it returns in one line each.
  3. Mark any tool that moves money or contacts a customer as needing human approval, and write down why.
  4. Remove one tool from your list and check whether the task can still be done. Keep the smallest set that works.

Lesson 1.3: The LLM as the brain, messages, special tokens, chat templates

The language model is the brain of the agent: it reads the conversation, decides the next step, and writes the text. It does not see a chat the way you do. It sees a sequence of messages, each with a role: system, user, or assistant. The system message sets the rules and the persona. The user message carries the task. The assistant message holds what the model has already said or done, including tool calls. Between these messages sit special tokens: short markers the model was trained to recognise, such as the markers that say a turn has started or ended. A chat template is the recipe that turns the list of messages into the exact text the model expects, with the special tokens in the right places. If the template is wrong, the model can confuse a system instruction with user text, or treat its own output as a new instruction. That is why you should use the template that ships with the model, not invent your own. In payments work, the system message is where you put the guardrails: use tools, do not invent facts, quote the rule source, and ask a human when unsure.

Worked example

An agent gets a system message: you are a payments assistant, use tools, never invent a payment status, and quote the source of any rule. The user message asks: what is the status of payment PAY-1042? The chat template wraps these into the model input with the correct special tokens marking where the system message ends and the user message begins. The model then produces an assistant message that calls the status tool instead of answering from memory. Because the template placed the guardrail in the system role, the model treats it as an instruction, not as part of the question. The template did quiet, essential work.

Hands-on exercise

  1. Write a system message for your running example agent in three sentences: role, tools rule, and honesty rule.
  2. Write one user message that asks your agent to do the task.
  3. Sketch the message list the agent will hold after one tool call: system, user, assistant tool call, tool result.
  4. Note one thing that could go wrong if the system message and the user message were swapped.

Lesson 1.4: Your first agent, a payment status agent with smolagents

Now build a first agent with smolagents, a small library for agents that write code to act. The pattern has three parts. First, define a tool with the @tool decorator: a small Python function with a clear docstring, for example a payment status lookup that takes a reference and returns a status from a small local table. Second, create a model object that connects to your LLM provider. Third, create a CodeAgent with the model and your tools, then run it with a task such as: check the status of payment PAY-1042 and explain it in one sentence. The agent will think, call your tool, observe the result, and answer. Keep the first version tiny: one tool, one task, and a step limit. Do not connect it to a real payment system. Use a small local table of made up references and statuses so you can see the loop work safely. If the agent invents a status instead of calling the tool, the fix is usually in the tool description or the system prompt: make the instruction to use the tool explicit. This code is a learning pattern; it was not run here, so test it in your own setup and read any error before changing the code. The model is swappable: change the model_id and api_base to point at any provider you choose.

Try it in your browser (no account needed)

Run this demo in the lesson page. It uses only the Python standard library, no network, and no API keys. It prints each Thought, each Action with its tool call, each Observation, and the final answer.

STATUS = {
    "PAY-1042": "held, reason: missing field",
    "PAY-1043": "complete",
    "PAY-1044": "held, reason: beneficiary bank details do not match",
}

def lookup_payment_status(reference):
    return STATUS.get(reference, "reference not found")

PLAN = [
    ("Check the payment status first, before answering.", "lookup_payment_status", "PAY-1042"),
]

for thought, tool_name, arg in PLAN:
    print("Thought: " + thought)
    print("Action: " + tool_name + "('" + arg + "')")
    result = lookup_payment_status(arg)
    print("Observation: " + result)

print("Final answer: Payment PAY-1042 is " + result + ", and the sender should supply it.")

Run it locally (real agent code)

from smolagents import CodeAgent, LiteLLMModel, tool

STATUS = {
    "PAY-1042": "held, reason: missing field",
    "PAY-1043": "complete",
    "PAY-1044": "held, reason: beneficiary bank details do not match",
}

@tool
def get_payment_status(reference: str) -> str:
    """Look up the status of a payment by its reference.
    Args:
        reference: the payment reference, for example PAY-1042.
    """
    return STATUS.get(reference, "reference not found")

model = LiteLLMModel(
    model_id="ollama_chat/qwen2.5:7b",
    api_base="http://127.0.0.1:11434",
    num_ctx=8192,
)
agent = CodeAgent(tools=[get_payment_status], model=model, max_steps=5)
answer = agent.run(
    "Check the status of payment PAY-1042 and explain it in one sentence."
)
print(answer)

Install first with pip install "smolagents[litellm]" and start Ollama with ollama pull qwen2.5:7b. The model is swappable: change the model_id and api_base to point at any provider you choose. If an import name differs in your installed version, check that version's docs; the pattern stays the same.

What you should see:

Payment PAY-1042 is held because a field is missing, and the sender should supply it.

Your wording may differ slightly. The answer must name the held status and the missing field, and must not add a delivery date.

Worked example

The status tool takes PAY-1042 and returns: status held, reason missing field. The agent calls it, reads the result, and answers: payment PAY-1042 is held because a field is missing, and the sender should supply it. It does not add a delivery date, because the tool gave none. If the reference is not in the table, the tool returns: reference not found. The agent then says it cannot find the payment and asks the user to check the reference. In both cases the answer comes from the tool, not from memory. That is the behaviour to aim for in your first build.

Hands-on exercise

  1. Write a status lookup tool with the @tool decorator, using a small local table of three made up references and statuses.
  2. Create a CodeAgent with your model and that one tool, with a step limit of five.
  3. Run it with: check the status of payment PAY-1042 and explain it in one sentence.
  4. Run it again with a reference that is not in the table, and check that it reports not found instead of inventing a status.
  5. Write down what the agent did at each loop step, and one thing you would improve.
