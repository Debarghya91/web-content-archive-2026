Unit 4: Final Project

Build a payments exception triage agent and evaluate it against a checklist.

3 lessons. About 3 to 4 hours.

Lesson 4.1: Plan the final project

Before you write code, write the plan. The final project is a payments exception triage agent: given a payment reference, it checks the status, finds the reason, checks the rule, and writes a three-part triage summary with a route. The plan has five parts. First, the scope: which exceptions it handles, such as held for a missing field and held because details do not match, and which it must send to a human. Second, the tools: a status lookup and a rule search, each with a clear description. Third, the data: a small table of made up cases for testing, with the expected triage for each. Fourth, the route rules: when to resolve, when to ask the sender, and when to escalate. Fifth, the evaluation checklist: correct triage, no invented facts, clear escalation, and an audit trail. Write the plan on one page. If a part is unclear, fix the plan before the code, because code written on a vague plan just automates the vagueness. A good plan also names the step limit and the model you will use, so the build stays small and testable.

Worked example

A learner writes a one page plan for the triage agent. Scope: two held reasons plus unknown references, which go to a human. Tools: status lookup and rule search. Data: five made up cases, each with the expected route written down before the agent runs. Routes: missing field goes to ask the sender, details mismatch goes to a specialist, unknown reference goes to a human. Checklist: the four items from this unit. The plan fits on one page, and the build in the next lesson follows it step by step. Nothing in the plan needs a real payment system.

Hands-on exercise

  1. Write the scope of your triage agent: which exceptions it handles and which go to a human.
  2. List your two tools with one sentence each describing what they do.
  3. Write five test cases with the expected route for each, before you build.
  4. Write your evaluation checklist: correct triage, no invented facts, clear escalation, audit trail.
  5. Set a step limit and name the model you will use.

Lesson 4.2: Build the triage agent

Build the agent from your plan, keeping it small: two tools, one model, a step limit of six, and the three-part triage summary. Start with the tools from Unit 3: a status lookup over a small local table and a rule search over short passages. Then create the agent with the swappable model, pointing at your local Ollama model by default. Run it on your five test cases one at a time and read each trace before moving to the next. If the agent invents a fact, the fix is usually a clearer tool description or a sharper system instruction, not a bigger model. If it picks the wrong route, check the route rules in your plan: the agent can only follow rules you wrote down. Keep the build in one file so you can read it end to end. When all five cases triage correctly, save the traces: they are the audit trail your evaluation needs. Do not connect the agent to a real payment system. The local tables are the whole data layer for this project.

Try it in your browser (no account needed)

Run this demo in the lesson page. It uses only the Python standard library, no network, and no API keys. It runs the same triage over three cases and prints each Thought, Action, and Observation.

STATUS = {
    "PAY-1042": "held, reason: missing field",
    "PAY-1043": "complete",
    "PAY-1044": "held, reason: beneficiary bank details do not match",
}
RULES = {
    "missing field": "A payment held for a missing field waits for the sender to supply the field.",
    "details do not match": "A payment held because details do not match must be checked against the original instruction before any release.",
}
EXPECTED = {
    "PAY-1042": "ask the sender",
    "PAY-1043": "no action",
    "PAY-1044": "escalate to a specialist",
}

def lookup_payment_status(reference):
    return STATUS.get(reference, "reference not found")

def get_scheme_rule(query):
    return RULES.get(query, "No matching rule passage found.")

def triage(reference):
    print("Case: " + reference)
    print("Thought: Check the status of " + reference + " first.")
    print("Action: lookup_payment_status('" + reference + "')")
    status = lookup_payment_status(reference)
    print("Observation: " + status)
    if status == "complete":
        route = "no action"
        print("Thought: The payment is complete, so no action is needed.")
    elif "missing field" in status:
        print("Thought: The reason needs the rule for missing fields.")
        print("Action: get_scheme_rule('missing field')")
        print("Observation: " + get_scheme_rule("missing field"))
        route = "ask the sender"
    elif "do not match" in status:
        print("Thought: A details mismatch needs a specialist check.")
        print("Action: get_scheme_rule('details do not match')")
        print("Observation: " + get_scheme_rule("details do not match"))
        route = "escalate to a specialist"
    else:
        print("Thought: This reason is unknown, so a human must decide.")
        route = "escalate to a specialist"
    print("Final answer: " + reference + " is " + status + ". Route: " + route + ".")
    ok = "yes" if route == EXPECTED[reference] else "no"
    print("Checklist: correct triage: " + ok + "; no invented facts: yes; clear escalation: yes; audit trail: yes.")
    print("")

for ref in ["PAY-1042", "PAY-1043", "PAY-1044"]:
    triage(ref)

Run it locally (real agent code)

from smolagents import CodeAgent, LiteLLMModel, tool

STATUS = {"PAY-1044": "held, reason: beneficiary bank details do not match"}
RULES = {
    "details do not match": "A payment held because details do not match must be checked against the original instruction before any release.",
}

@tool
def get_payment_status(reference: str) -> str:
    """Look up the status of a payment by its reference.
    Args:
        reference: the payment reference, for example PAY-1044.
    """
    return STATUS.get(reference, "reference not found")

@tool
def search_scheme_rules(query: str) -> str:
    """Search the scheme rule extracts for a short query.
    Args:
        query: a short search phrase, for example details do not match.
    """
    return RULES.get(query, "No matching rule passage found.")

model = LiteLLMModel(
    model_id="ollama_chat/qwen2.5:7b",
    api_base="http://127.0.0.1:11434",
    num_ctx=8192,
)
agent = CodeAgent(
    tools=[get_payment_status, search_scheme_rules], model=model, max_steps=6
)
answer = agent.run(
    "Triage exception PAY-1044. Say what happened, what rule applies, "
    "and what to do next."
)
print(answer)

Install first with pip install "smolagents[litellm]" and start Ollama with ollama pull qwen2.5:7b. The model is swappable: change the model_id and api_base to point at any provider you choose. A hosted version of this demo will be linked here once it is published.

What you should see:

What happened: payment PAY-1044 is held because the beneficiary bank details do not match. Rule: a payment held because details do not match must be checked against the original instruction before any release. Next step: escalate to a specialist. Your wording may differ slightly. The answer must cover all three parts and must not invent a timeline.

A learner builds the triage agent from their one page plan: two tools, a local Ollama model, and a step limit of six. The build stays in one file, and no real payment system is touched.

Lesson 4.3: Evaluate against the checklist

Evaluation is judging the agent against the checklist on cases it has not been tuned for. The checklist has four items. Correct triage: the route matches the expected route for the case. No invented facts: every claim in the answer comes from a tool result or a retrieved passage. Clear escalation: when the agent cannot decide, it names a human route instead of guessing. Audit trail: every step is recorded, so a reviewer can see the thoughts, the tool calls, and the observations. Score each case on each item, and write the result in a table. A pass needs all four items on every case. If a case fails, read the trace to find the step that went wrong, fix that step, and re-run only that case. Do not fix the agent by changing the expected answer: the expected answers were fixed before the build. When all cases pass, write one short paragraph saying what the agent does well and what it still cannot do. That honest summary is the real deliverable of the project, more than the code itself.

Worked example

A learner evaluates the triage agent on five cases. Four pass all four checklist items. One fails on correct triage: a details mismatch was routed to ask the sender instead of a specialist. The trace shows the agent searched the rule for missing fields instead of mismatched details, because the reason text was misread. The learner tightens the routing rule in the plan, re-runs only that case, and it passes. The final table shows five passes, and the summary says the agent handles the two known held reasons well but still sends every unfamiliar reason to a human, which is the safe behaviour.

Hands-on exercise

  1. Score each of your five cases on all four checklist items and write the result in a table.
  2. For any failed case, read the trace to find the step that went wrong.
  3. Fix the failing step and re-run only that case.
  4. Write one short paragraph saying what the agent does well and what it still cannot do.
  5. Check your completion: Units 1, 3 and 4 finished earns the Certificate of Completion.
