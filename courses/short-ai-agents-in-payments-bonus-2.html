Bonus 2: Observability and evaluation

Traces, eval sets, and what to measure. Bonuses do not count toward certificates.

3 lessons.

Lesson B2.1: Traces and logs

Observability means you can see what the agent did, step by step, after the run is over. The basic unit is the trace: the full record of one run, with every thought, tool call, tool result, and final answer, in order. Logs collect traces across runs so you can compare them. A good trace answers three questions: what did the agent try, what did the tools return, and where did it go wrong. Record the model name, the tool versions, and the time with each trace, or you cannot reproduce a result later. Keep traces for every production run, even the good ones, because the good runs are the baseline the bad runs are judged against. Do not log secrets: payment details, API keys, and personal data must be redacted before storage. When something fails, the trace is the first place to look, before the code. Most agent failures are visible in the trace as a wrong tool choice, a misread result, or a missing step.

Worked example

A triage agent routes a case to the wrong team. The trace shows the steps: the status lookup returned a held reason, the rule search returned the wrong passage because the query was too broad, and the agent followed that passage to the wrong route. The fix is a narrower search query, not a new model. Without the trace, the team would have guessed. With it, the failure is a single line in the log. The trace also shows the model name and tool versions, so the team can re-run the same case after the fix and compare the two traces side by side.

Hands-on exercise

  1. Turn on trace logging for your triage agent, recording every thought, tool call, and tool result.
  2. Run your five test cases and save the five traces.
  3. Pick one trace and check it answers: what did the agent try, what did the tools return, where could it go wrong.
  4. List anything in your traces that must be redacted before storage, such as personal data or keys.

Lesson B2.2: Eval sets

An eval set is a fixed set of test cases with expected answers, used to judge the agent the same way every time. Build it from real cases: the common ones, the tricky ones, and the ones that failed before. Each case needs the input, the expected route or answer, and the checklist items it tests. Keep the eval set fixed while you improve the agent, or you cannot tell whether a change helped. Add new cases when new failures appear, but never remove a case just because the agent fails it. Run the eval set after every change: a new tool, a new prompt, a new model. A change that fixes one case and breaks two others is not an improvement, and only a fixed eval set shows that. Score each case on the four checklist items from Unit 4: correct triage, no invented facts, clear escalation, and audit trail. The eval set is the contract between you and the agent: it says what good looks like, in advance, in writing.

Worked example

A team keeps an eval set of 20 triage cases: 12 common, 5 tricky, and 3 that failed before. After a prompt change, the agent passes 19 of 20, up from 17. The one failure is a case that failed before, and the trace shows the same wrong tool choice. The team fixes the tool description, re-runs the set, and reaches 20 of 20. Because the set was fixed, the improvement is real and measurable. If they had changed the set at the same time, they could not have known whether the prompt or the set had improved.

Hands-on exercise

  1. Build an eval set of 10 cases for your triage agent: 6 common, 3 tricky, and 1 that failed before.
  2. Write the expected route and the checklist items for each case.
  3. Run the eval set and record the score per case.
  4. Add one new case for each failure you find, and never remove a failing case.

Lesson B2.3: What to measure and improve

Measure four things, and improve the worst one first. Accuracy: how often the route and the answer are right, measured on the eval set. Groundedness: how often every claim comes from a tool result or a retrieved passage, with no invented facts. Escalation quality: how often the agent sends the right cases to a human, and how often it guesses instead. Cost and speed: how many model calls and tool calls each case takes, and how long a case takes end to end. A common pattern is that accuracy looks fine while groundedness is poor: the agent gives the right route for the wrong reason, which will fail on the next new case. Another pattern is high cost for little gain: ten tool calls where two would do. Improve in small steps, one change at a time, and re-run the eval set after each change. When a metric stops improving, stop tuning that part and look at the next worst metric. The goal is not a perfect score. It is a known score, on a fixed set, with traces that explain every failure.

Worked example

A team measures their triage agent: accuracy 18 of 20, groundedness 15 of 20, escalation quality 19 of 20, and an average of 7 tool calls per case. Groundedness is the worst metric, so they work on it first. The traces show the agent adding timelines the tools never gave. They tighten the system instruction to forbid timelines, re-run the eval set, and groundedness rises to 19 of 20 while accuracy stays at 18. Next they cut the average tool calls from 7 to 4 by merging two lookups. Each change is one step, measured on the same set, so the improvement is real.

Hands-on exercise

  1. Measure your triage agent on the four metrics: accuracy, groundedness, escalation quality, and cost and speed.
  2. Find your worst metric and write down why it is the worst, using trace evidence.
  3. Make one small change aimed at that metric, and re-run the eval set.
  4. Write one paragraph with your known score on the fixed set and what still fails.
