Unit 2: Requirements and user stories

Writing a BRD, acceptance criteria and Gherkin, and good versus bad requirements.

Lesson 2.1: Writing a business requirements document

A business requirements document, or BRD, is the single agreed record of what the business needs. It usually has these sections: background, objectives, scope, stakeholders, business requirements, functional requirements, non-functional requirements, assumptions, dependencies, risks, and acceptance criteria. Background explains why the work exists. Objectives state what success looks like. Scope says what is in and what is out, and the out of scope list matters as much as the in scope list because it stops the work growing without agreement. Each requirement has a unique ID, such as R1 or R2, so it can be traced to a test and to a change later. Each requirement covers one idea, uses plain language, and is testable: a tester must be able to say whether it passed or failed. The BRD describes what is needed, not how to build it; the design belongs to the engineers. Assumptions and open questions are listed openly, never hidden. A good BRD is short enough to read in one sitting and complete enough to build from.

Worked example. A BRD for a payment status enquiry starts with background: customers call support because they cannot see where a payment is. The objective is to cut those calls. Scope covers status lookup for credit transfers only; cancelling a payment is out of scope. Requirement R1 says the system must show the current status for a payment when given its reference. Requirement R2 says an unknown reference must show a clear not found message. Two requirements, one page of scope, and the team knows exactly what to build.

Try it yourself.

  1. Draft the BRD headings for a return handling feature.
  2. Write the scope in and out in three lines each.
  3. Write two business requirements with IDs.
  4. List two assumptions for your BRD.

Lesson 2.2: Acceptance criteria and Gherkin

Acceptance criteria state when a story is done, in terms a tester can check. Gherkin is a simple format for writing them: Given describes the starting context, When describes the action, Then describes the expected outcome. One scenario covers one behaviour, and a story usually needs several: the happy path, an error case, and an edge case. Keep each scenario short, use plain words, and use tables of examples when the same behaviour repeats with different values. Criteria must be testable. A sentence such as the status should update quickly cannot be tested, because quickly means something different to everyone. A sentence such as the status must show the value from the latest pacs.002 can be tested, because the tester can send a pacs.002 and check the screen. Developers use the criteria to know what to build, testers use them to know what to test, and the product owner uses them to accept the work. When all the criteria pass, the story is done.

Worked example. A status enquiry story has three scenarios. Given a payment was sent today, when the customer asks for its status, then the current status is shown with the last update time. Given the payment reference does not exist, when the customer asks, then a clear not found message is shown. Given the payment was returned, when the customer asks, then the status shows returned. Three scenarios, three behaviours, and the tester can check each one.

Try it yourself.

  1. Write three acceptance criteria for a status enquiry.
  2. Turn one of them into Gherkin with Given, When and Then.
  3. Add a negative scenario for a reference that does not exist.
  4. Check that each criterion you wrote is testable.

Why: Then states what must be true after the action.

Why: When all criteria pass, the story is done.

Lesson 2.3: Good requirements versus bad requirements

A good requirement is specific, measurable, testable, unambiguous, and covers one idea. A bad requirement fails one of those tests. Vague words are the most common fault: fast, user-friendly, properly, and support all payments mean something different to every reader. Compound requirements hide two ideas in one sentence, so one half can be built and the other forgotten. Solution-led requirements state how to build something, such as use a dropdown, instead of stating the need, which is that the user must pick one option from a list. Untestable requirements cannot be checked, such as the system should be good. Fixing them is straightforward. Replace vague words with numbers or examples. Split compound sentences into two requirements. Replace a solution with the underlying need. Then read the result and ask whether a tester could pass or fail it. In payments the test is easy to apply, because every requirement should name the message, the field, or the status it concerns.

Worked example. Bad: The system must handle returns properly. Good: When a pacs.004 return is received, the system must match it to the original payment by its reference. If no match is found, it must raise an exception for the operations team. The bad version cannot be tested, because properly is undefined. The good version names the message, the matching rule, and the failure behaviour, so a tester can check all three.

Try it yourself.

  1. Rewrite three vague requirements so each one is specific.
  2. Split one compound requirement into two separate requirements.
  3. Turn one solution-led requirement into a statement of need.
  4. Check each rewrite by asking whether a tester could pass or fail it.

Quiz 2.3.1. Which is a good requirement?





Why: A number makes the requirement specific and testable.

Quiz 2.3.2. Why split a compound requirement?





Why: Two ideas in one sentence means one can be built and the other forgotten.

Quiz 2.3.3. Why is use a dropdown a bad requirement?





Why: Requirements state the need; the design belongs to the engineers.

Quiz 2.3.4. What is wrong with support all payments?





Why: All payments is unbounded, so nobody can tell when it is done.
