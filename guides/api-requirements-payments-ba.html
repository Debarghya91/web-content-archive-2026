Writing API Requirements as a Payments BA

By Payments Training Hub · Last reviewed 18 November 2026

Key takeaways

  • An API requirement must name the endpoint, the method, the request and response fields, the error codes, and the retry behaviour, or engineers will guess each one.
  • Idempotency is mandatory for payment APIs: the same instruction sent twice must create one payment, never two.
  • Specify status handling explicitly: polling, webhooks, or both, with the states, the timing, and what the client must do on each state.
  • Acceptance criteria for APIs are scenarios: given a request, when the API is called, then the response, the state change, and the side effects are exactly these.

Reading time: about 7 min

What it is

API requirements state what a payments API must do, from the perspective of the business and the client consuming it. They cover the endpoints, the fields, the validation rules, the error handling, the status model, and the non-functional needs, in enough detail that engineers can build the API and testers can verify it without inventing behaviour. In payments, API requirements carry extra weight, because an API that creates payments moves money, and every gap in the specification becomes a financial risk.

The BA writing API requirements is not writing code and not designing the implementation. The BA specifies the contract: what goes in, what comes out, what happens on failure, and how the client knows what happened. The contract is the requirement.

Why it matters

Payment APIs fail in predictable ways, and almost all of them are specification failures. A missing idempotency key creates duplicate payments. An undefined error code leaves the client guessing whether the payment went through. A status model with no terminal states leaves clients polling forever. A retry rule that nobody specified turns a network glitch into a double debit. Each of these is prevented by a requirement written before the build, and each is expensive to fix after clients have integrated.

API requirements also protect the bank's clients. A corporate customer integrating a payment initiation API builds its own reconciliation, its own retry logic, and its own user experience on the bank's contract. If the contract is vague, the client's build is fragile, and the bank inherits the support calls.

How it works in a bank

Endpoints and methods. Each operation gets an endpoint, a method, and a purpose: initiate a payment, get a payment status, list payments, cancel a payment. The BA states the business operation; engineering owns the URL design, but the BA must be able to read it and challenge it.

Request and response fields. Every field is specified: name, type, mandatory or optional, format, validation rule, and default. Payment fields include debtor and creditor accounts, amount and currency, value date, references (including the UETR and EndToEndId), charge options, and remittance information. The response specifies the payment identifier, the status, and the timestamps the client needs for reconciliation.

Idempotency. The client sends an idempotency key with each instruction. If the same key arrives again, the API returns the original result without creating a second payment. The BA specifies the key format, the retention period, and the behaviour when a key is reused with different content (an error, not a second payment).

Error codes and retry behaviour. Every failure gets a code, a message, and a retry classification: retryable (try again), non-retryable (fix the request), or unknown (check status before retrying). The BA specifies which errors are which, because a client that retries a non-retryable error, or gives up on a retryable one, causes harm either way.

Status handling. The BA specifies the status model (received, accepted, rejected, settled, failed), how the client learns the status (polling an endpoint, receiving a webhook, or both), the timing of updates, and what the client must do on each state, including the terminal states where no further change is possible.

Authentication, authorisation and limits. How the client authenticates, what it is allowed to do, rate limits, and the behaviour when a limit is hit. In open banking contexts, consent and scope rules apply, and the BA must specify them with compliance.

Versioning and change. How the API changes without breaking clients: versioning policy, deprecation notice periods, and backward-compatibility rules. A breaking change without notice is a client incident.

Worked example

Requirement for a "initiate payment" endpoint, as a BA would specify it:

REQ-API-003. The API must accept a payment initiation request carrying debtor account, creditor account, amount, currency, value date, EndToEndId, and an idempotency key. Validation: reject requests with a missing mandatory field, an invalid IBAN, or an amount of zero, with error code 422 and a field-level message naming the failing field. Idempotency: a request repeating an idempotency key within 24 hours returns the original response with the original payment identifier, and creates no second payment; a repeated key with different content returns error code 409. Response: return the payment identifier, the status RECEIVED, and the creation timestamp. Status: the client polls the status endpoint or receives a webhook on each status change; terminal states are SETTLED, REJECTED and FAILED. Acceptance criteria: given a valid request, when it is submitted twice with the same idempotency key, then one payment is created, both responses carry the same identifier, and the ledger shows one debit.

Technical detail

Field mapping to messages. API fields map to message fields downstream: the API's creditor account maps to the pacs.008 creditor account, the API's references map to the message references. The BA specifies the mapping, because a field the API accepts but the message drops is a data-loss defect.

State machines. The status model is a state machine with defined transitions. The BA specifies the states, the allowed transitions, and the terminal states, and forbids impossible transitions (a settled payment cannot return to received).

Webhooks vs polling. Webhooks push updates and need retry, signing, and replay handling specified. Polling pulls updates and needs rate limits and freshness expectations specified. Many APIs offer both, and the BA must specify how they stay consistent.

Testing hooks. The BA specifies what testers and clients need: a sandbox, test data, error simulation (force a reject, force a timeout), and idempotency test scenarios. An API without error simulation cannot be tested properly.

Common mistakes

No idempotency requirement. The most expensive omission in payment APIs. Duplicates are a matter of time, not chance.

Error codes without retry guidance. A code without a retry classification leaves every client to guess, and guesses differ.

Status model with no terminal states. Clients poll forever, support queues fill with "where is my payment", and reconciliation never closes.

Fields specified without validation rules. "Creditor account: string" is not a specification. Format, length, mandatory status, and validation rule are all required.

Assuming the client reads the documentation. Clients integrate against the contract as specified. If the behaviour is not in the requirements, it is not in the contract, and the client will discover the gap in production.

Forgetting versioning. An API without a versioning policy breaks clients on its first change. Specify the policy before the first release, not after the first incident.
