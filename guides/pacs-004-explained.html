pacs.004 Explained

By Debarghya Mondal · Last reviewed 08 November 2026

What it is

pacs.004 is the Payment Return message. It is the ISO 20022 message a bank sends to return funds that have already settled. The name comes from the ISO 20022 message set: pacs stands for Payments Clearing and Settlement, and 004 is the payment return variant.

A return is different from a rejection. A rejection happens before settlement, when no money has moved. A return happens after settlement, when the money has already been credited and now needs to come back. The pacs.004 is a real payment in reverse: it moves funds from the beneficiary bank back to the sending bank.

Why it matters

pacs.004 matters because settled payments sometimes need to come back. The beneficiary account may be closed, the beneficiary may have returned the goods, the payment may have been sent in error, or a recall may have been accepted. In all these cases, the money cannot simply be cancelled. It has to travel back through the payment chain, and the pacs.004 is the message that moves it.

It also matters because returns are slower and more expensive than rejections. A rejection is a status report and costs nothing. A return is a new settlement instruction with its own charges, its own cut-off, and its own timeline. A BA who understands this can set correct customer expectations and avoid promising a same day refund when the return will take days.

How it works in a bank

The return is initiated by the beneficiary bank, or by an intermediary bank, after settlement. The bank builds a pacs.004 that references the original payment, including the original UETR, the original message identification, and the original instruction identification. This linkage is what lets both banks reconcile the return against the original payment.

The pacs.004 travels back along the same chain the original payment took, but in reverse. If the original went from bank A to bank B to bank C to bank D, the return goes from bank D to bank C to bank B to bank A. Each bank debits the account it credited and forwards the return.

The amount returned can differ from the original amount, because return charges may be deducted along the way. The sending bank reconciles the variance and tells the customer what was returned and what was deducted.

Worked example

A customer pays a supplier EUR 10,000. The payment settles and the supplier is credited. The next day, the supplier realises the goods were never shipped and agrees to return the money.

The supplier's bank initiates a pacs.004. The message carries the original payment references, the return identification, the returned amount EUR 10,000, and the return reason code. The supplier's bank debits the supplier and sends the pacs.004 to the next bank in the chain.

Each bank in the chain debits the account it credited and forwards the pacs.004. The original sending bank receives the pacs.004, credits the customer's account, and sends a pacs.002 confirming the return was accepted and settled. The customer sees the EUR 10,000 back in their account, less any return charges that were deducted.

If the return had been initiated by a recall, the flow is slightly different. The sending bank first sends a camt.056 cancellation request. The beneficiary bank decides whether to accept. If it accepts, it replies with a camt.029 and then initiates the pacs.004. The pacs.004 is the message that actually moves the money.

Technical detail

The pacs.004 has two main parts:

  • GrpHdr (Group Header): message identification (MsgId), creation date and time (CreDtTm), number of transactions (NbOfTxs), settlement information (SttlmInf), and the instructing and instructed agents.
  • TxInf (Transaction Information): payment identification (PmtId, with InstrId, EndToEndId and UETR), returned interbank settlement amount (RtrdIntrBkSttlmAmt), charge bearer (ChrgBr), charges information (ChrgsInf), debtor (Dbtr), debtor account (DbtrAcct), creditor agent (CdtrAgt), creditor (Cdtr), creditor account (CdtrAcct), return reason information (RtrRsnInf), and the original transaction reference (OrgnlTxRef).

Key fields to know:

  • RtrdIntrBkSttlmAmt: the returned interbank settlement amount. This is the amount actually coming back, which may be less than the original if charges were deducted.
  • RtrRsnInf: the return reason information, with a reason code. Common codes include DUPL for duplicate payment, AC04 for closed account, and CUST for a customer request.
  • OrgnlTxRef: the original transaction reference, carrying the original message identification, instruction identification, and UETR. This is what links the return to the original payment for reconciliation.
  • RtrId: the return identification, a unique reference for the return itself.

Common mistakes

The most common mistake is trying to use a pacs.002 to return a settled payment. A pacs.002 is only a status report. It informs, it never settles. Once settlement has happened, only a pacs.004 can move the money back. A team that sends a pacs.002 expecting a refund will wait forever.

Another mistake is assuming the returned amount will equal the original amount. Return charges are often deducted by intermediary banks. The customer should be told the expected returned amount, and the variance, before the return is initiated.

A third mistake is initiating a return without checking whether the beneficiary bank has already released the funds. If the beneficiary has already spent the money, the return will fail and the bank will need to pursue a different route, such as a commercial claim.
