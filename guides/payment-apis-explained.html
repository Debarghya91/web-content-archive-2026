Payment APIs Explained

What it is

A payment API (Application Programming Interface) lets one system ask another system to do something with a payment, using a defined set of requests and responses over the internet. Instead of uploading a file or typing into a screen, a customer, a partner, or an internal system sends a structured request to the bank's API, and the bank responds with a structured result.

Payment APIs are used for payment initiation (starting a payment), status enquiry (asking where a payment is), account information (checking a balance or a statement), and webhooks (receiving a notification when something changes). They are the foundation of open banking, of embedded finance, and of most modern fintech products.

A payment API is not a single thing. It is a set of endpoints, each of which does one job, with defined request and response formats, authentication rules, and error handling.

Why it matters

APIs are how modern payments work. A marketplace that pays its sellers, an app that lets users send money, a corporate treasury system that initiates hundreds of payments a day: all of these use payment APIs. A bank that does not offer APIs cannot serve these customers.

For a business analyst, APIs matter because they are where the business requirements meet the technical implementation. The API contract, what the caller sends, what the bank returns, what happens when something is wrong, is a business document as much as a technical one. A business analyst who cannot read an API specification and explain it to a stakeholder cannot work on modern payment products.

In an interview, API questions test whether a candidate understands how systems actually connect, not just how they work in isolation.

How it works in a bank

Payment initiation. A caller sends a request to the bank's payment initiation endpoint. The request contains the debtor account, the creditor account, the amount, the currency, the value date, and a reference. The request also carries an idempotency key, a unique identifier that the bank uses to detect duplicate requests. The bank validates the request, checks the account and the balance, runs fraud and sanctions checks, and creates the payment. The bank responds with a payment identifier and a status, usually "accepted" or "pending".

Status enquiry. The caller can ask the bank for the status of a payment using the payment identifier. The bank responds with the current status: accepted, settled, rejected, or failed. The status comes from the payment hub, which tracks the payment through its lifecycle.

Webhooks. Instead of the caller asking repeatedly whether a payment has completed, the bank can send a webhook, a notification pushed to the caller's system when the payment status changes. The caller provides a URL, and the bank sends a message to that URL when the payment is accepted, settled, or rejected. Webhooks are more efficient than polling, but they require the caller to have a system that can receive them reliably.

Authentication. Payment APIs use strong authentication. The caller authenticates with a client certificate (mutual TLS) and an OAuth token. The token proves the caller is who they claim to be and has permission to initiate payments. Without valid authentication, the API rejects the request.

Idempotency. If a caller sends the same request twice, for example because the first response was lost, the bank must not create two payments. The idempotency key solves this. The bank stores the key with the payment. If a request arrives with a key that has already been used, the bank returns the original response instead of creating a new payment.

Worked example

A marketplace needs to pay 200 sellers every Friday.

The API call. The marketplace's system sends a payment initiation request to the bank's API for each seller. The request includes the seller's account, the amount, the currency, and an idempotency key (a unique value for each payment, such as "payout-2026-11-07-seller-123"). The bank validates each request, debits the marketplace's account, and creates the payments. The bank responds with a payment identifier for each one.

The status. The marketplace wants to know when each payment is complete. Instead of asking the bank 200 times, it registers a webhook URL. When each payment settles, the bank sends a webhook to the marketplace with the payment identifier and the new status. The marketplace updates its own records and notifies the sellers.

A failure. One payment is rejected because the seller's account number is invalid. The bank returns an error in the API response: a business error code and a message explaining the problem. The marketplace logs the error, flags the seller's account for review, and does not retry the payment until the account details are corrected.

A duplicate. The marketplace's system times out while waiting for a response to one payment. It retries the same request with the same idempotency key. The bank recognises the key, sees that the payment was already created, and returns the original response. No duplicate payment is created.

Technical detail

Request and response format. Most modern payment APIs use JSON over HTTPS. The request is a JSON object with named fields. The response is a JSON object with the result, a status, and either the payment details or an error. Older bank APIs may use XML, and ISO 20022 defines XML message formats for payment initiation (pain.001) and status reporting (pain.002).

Error handling. API errors fall into two types. A technical error means the request could not be processed: the authentication failed, the request was malformed, or the system was unavailable. The caller should fix the technical problem and retry. A business error means the request was understood but the payment cannot proceed: the account has insufficient funds, the beneficiary account is invalid, or the payment breaches a limit. The caller should not retry a business error without fixing the underlying problem.

HTTP status codes. A successful payment initiation returns 200 or 201. A bad request returns 400. An authentication failure returns 401. A forbidden action returns 403. A payment that cannot be found returns 404. A rate limit returns 429. A server error returns 500. The caller must handle each code correctly.

Rate limiting. Banks limit how many API calls a caller can make in a given period. If the caller exceeds the limit, the bank returns a 429 response. The caller must slow down and retry later, with exponential backoff, rather than hammering the API.

Versioning. APIs change over time. The bank versions its API so that existing callers are not broken when a new version is released. The version is usually in the URL (for example, /v1/payments) or in a header. Callers should pin to a version and test before upgrading.

Common mistakes

Retrying without an idempotency key. If a caller retries a payment initiation without an idempotency key, the bank may create a duplicate payment. Every payment initiation request must carry a unique idempotency key.

Polling instead of webhooks. Asking the bank for a payment status every few seconds wastes resources and is slower than receiving a webhook. Use webhooks where the bank supports them.

Treating a timeout as a failure. A timeout means the response was lost, not that the payment failed. The correct action is to check the status using the payment identifier or the idempotency key, not to blindly retry.

Ignoring error codes. An API returns structured error codes for a reason. A caller that treats all errors the same will retry business errors that will never succeed and will miss technical errors that should be retried.

No authentication. Payment APIs require strong authentication. A design that calls a payment API without mutual TLS or OAuth is not secure and will not be approved by the bank's security team.
