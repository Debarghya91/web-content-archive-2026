Payment State Machine Simulator

Payment State Machine Simulator

One payment, USD 25,000 from a London corporate to Tanaka Trading Pte Ltd in Singapore, reference INV-8841, payment ID PAY-20261105-8841, UETR a3e1f2b4-5c6d-4a7e-9b1c-2d3e4f5a6b7c. The machine starts at Received. Click any state to see what it means, what event caused entry, what data is held, what happens next, and what can go wrong. Then fire events from the injector and watch the machine accept the event or reject it with a reason.

Four states look alike and are not the same. Accepted is message acknowledgement: the payment passed technical validation (ACTC) and customer-profile checks (ACCP), usually confirmed by pacs.002 ACCP, and no money has moved. Clearing Accepted is settlement in process: the clearing system took the message into its cycle and settlement is in process, usually with pacs.002 ACSP, and still no money has moved. The full ladder is ACTC, ACCP, ACSP, ACSC, ACCC, in that order. Settled is settlement finality: value moved finally and irrevocably between banks. Credited is beneficiary credit: the beneficiary bank posted the funds to the beneficiary account. Acceptance is not settlement, and settlement is not beneficiary credit.

Current state: Received  

Main flow

Flow order: Received, Validated, Accepted, Clearing Accepted, Settled, Credited, Reconciled. Queued and Held sit on side paths off Accepted and Validated.

Exception states

Received

What it means. The payment instruction has arrived at the hub and is recorded, but nothing has been checked yet.

What caused entry. Customer submits the instruction through a channel. The hub records it with a payment ID.

What data is held. Instruction reference, debtor and creditor details, amount, currency, value date, idempotency key.

What happens next. Validation runs. A pass moves it to Validated, a fail moves it to Rejected, a duplicate match moves it to Duplicate.

What can go wrong. An unvalidated payment could carry a wrong account or amount, so no funds move from this state.

Event injector

Fire an event. If it is valid from the current state, the machine moves and tells you why. If it is invalid, the machine stays put and tells you why the event cannot fire here.

Recovery and investigation events: these complete the machine so a held, queued, credited or unknown payment can finish.

No event fired yet. The machine is at Received. Try "validate OK" to move to Validated, or try "settlement confirm" to see an invalid event rejected with its reason.

Out-of-order events

Messages do not always arrive in order. These demos show what the system does when an event arrives before the event it depends on.

Duplicate instruction handling

The same instruction can arrive twice, for example when a channel retries after a timeout. The idempotency key decides whether it is a new payment or a duplicate.

Timeout and unknown outcome

When a confirmation never arrives, the payment moves to Unknown. The bank must investigate before it acts, because the money may already have moved.

Learning outcome and debrief

Learning outcome. After using this simulator you can follow one payment through its states from Received to Reconciled and explain what event caused each transition and which events the machine rejects.

Debrief. Accepted, Clearing Accepted, Settled and Credited look alike and are not the same: acceptance is not settlement and settlement is not beneficiary credit. The full ladder is ACTC, ACCP, ACSP, ACSC, ACCC, in that order. Fire events from the injector and note which ones the machine accepts and which it rejects with a reason.
