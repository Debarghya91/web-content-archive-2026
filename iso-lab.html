EX-01: Business Application Header versus Document

Concept. The Business Application Header, head.001, is the envelope around an ISO 20022 business message. It carries routing and identification data only: sender, receiver, message name, message definition identifier, business service, creation time, business message identifier, and a copy duplicate flag. The Document carries the business content, such as the pacs.008 payment instruction with debtor, creditor, amount, and settlement data. A receiving system reads the header first to decide where to route the message and which schema version to validate against, without opening the payment data. Keeping routing in the header and business data in the Document lets routing, logging, and duplicate checks work the same way for every message type. The six fields shown in the valid example are the minimum routing subset, not the whole header: head.001.001.02 has 15 elements, and under CBPR+ the business service element BizSvc is mandatory and must carry swift.cbprplus.03. Other optional elements exist in the full header, such as MktPrctc (market practice) and Rltd (related business message), and are used only where the relevant usage guideline requires them.

Task. Study the valid head.001 AppHdr below and list every element it contains. Then inspect the invalid version and identify each business element that was wrongly placed inside the header. Write down, for each element, whether it belongs in the AppHdr or in the Document, and explain why a router that only reads the header must never need the amount or the creditor name.

Why the invalid sample fails. This invalid example parses as XML, but it is structurally wrong because business payment data has been placed inside the header. IntrBkSttlmAmt, Cdtr, and Dbtr are Document elements, not head.001 elements, so the message fails schema validation against head.001.001.02. This is a schema rule failure, not a business rule failure. The consequence is rejection before routing: the receiver cannot validate the header, cannot trust the routing data, and must return the message for correction instead of processing the payment.

Expected answer. You should conclude that the header carries only who sent the message, who should receive it, what message type it is, which version applies, which business service it belongs to, when it was created, and its unique identifier. Amount, debtor, creditor, accounts, charges, and remittance information belong only in the Document. The corrected approach is to keep the AppHdr to the routing fields shown in the valid example, including the CBPR+-mandatory BizSvc with value swift.cbprplus.03, and to place all payment data inside the pacs.008 Document, so routers, duplicate checks, and schema validation each work on the correct part. The six fields in the valid example are the minimum routing subset, not the whole head.001 header: the full header has 15 elements, and other elements such as MktPrctc and Rltd appear only where a usage guideline requires them.

EX-02: InstrId, EndToEndId, TxId and UETR

Concept. Four identifiers travel with a payment, and each has a different owner and a different job. InstrId is assigned by the instructing party and identifies one instruction inside one message. EndToEndId is chosen by the debtor, usually an invoice reference such as INV-2026-1147, and travels unchanged from debtor to creditor so the creditor can match the receipt. TxId is assigned by the instructing agent to identify the transaction in its own systems. UETR is a globally unique reference generated once for a cross border payment and carried unchanged across every bank in the chain for tracking. Reusing InstrId creates a duplicate, changing EndToEndId breaks creditor matching, and dropping UETR breaks end to end tracking.

Explain which system would flag each duplicate, what status it would return, and how you would assign fresh values that keep EndToEndId unchanged for the creditor.

Why the invalid sample fails. This invalid example parses as XML, but it is structurally wrong in two ways. First, InstrId INSTR-884120 and the UETR are reused on two different transactions. InstrId must be unique per instructing party, and a UETR must be unique per payment, so duplicate detection treats the second transaction as a possible duplicate payment. Second, the message carries two transactions (NbOfTxs 2, CtrlSum 17,500.00). Under CBPR+ a pacs.008 carries exactly one transaction (NbOfTxs = 1); a multi-transaction pacs.008 is permitted only under other usage guidelines, such as a SEPA batch, not under CBPR+. Both failures are business rule failures enforced by duplicate and usage-guideline checks, not basic XML schema failures. The consequence is rejection or a duplicate investigation: the receiver returns a status report with a duplicate reason, settlement is held, and the creditor may be paid twice if the check is bypassed.

Expected answer. You should conclude that InstrId identifies the instruction, TxId identifies the transaction for the instructing agent, EndToEndId is the debtor reference that must stay unchanged for creditor matching, and UETR is the globally unique tracking key for the whole chain. The corrected approach is to assign a fresh InstrId and a fresh TxId and UETR to the second payment, keep each EndToEndId tied to its own invoice, and never copy an identifier from one payment to another, even when debtor, creditor, amount, and date are identical. Also remember the transaction-count rule: under CBPR+ a pacs.008 carries exactly one transaction (NbOfTxs = 1), so two payments need two separate pacs.008 messages; a multi-transaction pacs.008 is permitted only under other usage guidelines, such as a SEPA batch, not under CBPR+.

EX-03: Group Header versus transaction level data

Concept. GrpHdr describes the message as a whole, while CdtTrfTxInf describes one payment inside it. The group header carries MsgId, creation time, number of transactions, control sum, and settlement information that applies to the group. Each transaction carries its own payment identification, amount, debtor, creditor, agents, charge bearer, purpose, and remittance information. In a pain.001 salary file with five thousand payments totalling EUR 8,400,000, the header states the count and the total, and the receiver checks those totals before processing any single payment. If the count or the sum does not match the transactions that follow, the whole message is rejected because a payment may have been lost or duplicated.

EX-13: Partial batch rejection

Concept. A pain.001 batch can be partially accepted: some transactions pass validation and settle, while one fails and is rejected, and the status report must show that split exactly. The bank sends pain.002 to the customer, or pacs.002 between banks, with a group status of PART for partially accepted, then one TxInfAndSts block per transaction with its own status and reason code. Treating the whole batch as rejected would delay good payments, while treating it as fully accepted would hide the failure and leave a supplier unpaid without explanation.
