Payments Solution Architect Interview Track

Role expectations

A Payments Solution Architect designs how payments move through a bank, end to end, from the channel where a client starts a payment to the core banking posting, clearing, and nostro settlement at the other end. The role covers the payment hub, integration with channels and back office systems, message formats, resilience, security, and the controls that keep money safe. The hiring manager expects the candidate to turn business needs into a clear, buildable design, with the right trade offs made openly. That means knowing when to use real time processing and when batch is right, how to handle a timeout or a duplicate, and how to keep the bank running when a system or a clearing route fails. The architect works with product managers, engineers, operations, risk, and vendors, and must explain a design in plain language to people who do not build systems. Success is a design that is simple, resilient, secure, and able to change, not a design that is clever on paper and hard to run.

Competency framework

  1. End to end payment design - Designs a full payment flow from channel to settlement, with each step and handoff named.
  2. Payment hub architecture - Knows how a hub routes, validates, enriches, and tracks payments across channels and clearing systems.
  3. Integration design - Connects channels, core banking, sanctions, fraud, and external systems with clear contracts and error handling.
  4. Message and data design - Designs ISO 20022, SWIFT, and file formats with correct fields, validation, and mapping.
  5. Resilience and recovery - Designs for failure, with retries, queues, idempotency, and a clear path back to a good state.
  6. Security and control - Builds authentication, authorisation, audit, and fraud and sanctions checks into the design.
  7. Non functional design - Sets clear needs for performance, volume, availability, and recovery time, and proves they can be met.
  8. Trade off and communication - Makes design choices openly, explains the cost of each option, and gains agreement across teams.

Learning objectives

  • Draw an end to end payment hub design, naming each component and its job.
  • Design an integration between a channel, the payment hub, core banking, and a clearing system.
  • Explain how ISO 20022 messages flow through a hub and where mapping and validation happen.
  • Design for duplicates, timeouts, and partial failures so no payment is lost or paid twice.
  • Design a resilient payment service that survives a system or site failure.
  • Set performance, availability, and recovery needs for a payment service and show how to test them.
  • Design sanctions, fraud, and audit controls into a payment flow from the start.
  • Present a design with options, trade offs, and a recommendation in plain language.

Beginner questions

1. Draw and explain the main parts of a payment hub. What does each part do?

Model answer: A payment hub takes payments from many channels and sends them to the right clearing system or bank. The first part is the intake, which receives payments from online banking, mobile, files such as pain.001, and APIs. The next part is validation, which checks the account, amount, currency, and required fields. Then comes enrichment, which adds data such as the value date, charges, and routing. The hub then applies business rules, such as limits and cut off times, and sends the payment for sanctions screening and fraud checks. After that, the hub routes the payment to core banking for posting and to the clearing system, such as Faster Payments, CHAPS, or SWIFT. Finally, the hub tracks the payment status and sends a pacs.002 status report back to the channel and the client.

2. A customer sends a payment online. Walk through the systems it passes through before the beneficiary is paid.

Model answer: The payment starts in the online channel, where the customer enters the beneficiary, amount, and date. The channel sends the instruction to the payment hub, which validates the account and the payment details. The hub checks the customer balance with core banking, and sends the payment for sanctions screening and fraud checks. If the payment passes, the hub debits the customer account in core banking and routes the payment to the right clearing system. For a UK payment, that may be Faster Payments or CHAPS. For a cross border payment, the hub sends a pacs.008 through SWIFT to the beneficiary bank, using a nostro account for settlement. The beneficiary bank then credits the beneficiary account. The hub sends a status update back to the channel, so the customer can see the payment has been sent.

3. What is the difference between a batch payment flow and a real time payment flow, and when would you use each one?

Model answer: A batch flow groups many payments together and processes them at set times. A pain.001 payroll file is a good example. The bank checks the whole file, then sends the payments in a batch, often through BACS or a bulk clearing route. Batch is efficient for large volumes and regular payments, but it is slower. A real time flow processes one payment at once, from instruction to clearing, in seconds. Faster Payments and instant payment systems use this flow. Real time suits a single urgent payment, but it needs systems that run all day and all night, with real time fraud and sanctions checks. I would use batch for payroll and regular supplier runs, and real time for urgent or single payments where the client needs instant confirmation.

4. What is an API payment, and how does it differ from a file based payment?

Model answer: An API payment is started by one system calling another system directly, using an agreed interface. A fintech partner or a corporate treasury system can call the bank API to send a single payment and get a status back at once. A file based payment uses a file, such as pain.001, that holds many payments and is sent in one go, often on a schedule. The API route is good for single payments, instant feedback, and systems that need to act on the result at once. The file route is good for large volumes, such as payroll, where many payments share one value date. The design needs differ too. An API needs strong authentication, clear error codes, and idempotency, so a retry does not pay twice. A file needs validation of the whole file, a clear status report, and a way to handle part of the file failing.

5. Why does the payment hub need to talk to core banking, and what happens if that link is down?

Model answer: The payment hub needs core banking to check the customer balance, to debit the payer account, and to credit the beneficiary account for internal payments. Core banking holds the true account record, so the hub must not guess the balance. If the link is down, the hub must not send payments it cannot post, because that could cause an overdraft or a payment with no debit. A good design will queue the payments safely, tell the client that the payment is held, and retry when the link returns. For urgent payments, the design may include a limited fallback, such as a balance check from a recent copy, but only with clear limits and risk approval. The key rule is that no payment should be lost, paid twice, or sent without a proper account posting. Monitoring must alert operations at once when the link fails.

Intermediate questions

1. A client sends the same payment twice because the first request timed out. How do you design the system so the payment is not paid twice?

Model answer: I would design for idempotency, which means the same request, sent twice, has the effect of one payment. Each payment instruction should carry a unique idempotency key from the channel or the client. The payment hub should store that key with the payment record before it sends the payment on. If the same key arrives again, the hub should return the original result instead of creating a new payment. The design must also handle the case where the first request reached the clearing system but the reply was lost. In that case, the hub should check the payment status by reference before it resends. The hub should also use duplicate detection on the payment details, such as the same payer, payee, amount, and value date within a short window. I would test this with a forced timeout and a forced retry, to prove no duplicate is created.

2. How would you design the ISO 20022 migration from MT103 to pacs.008 in a payment hub?

Model answer: I would design a hub that can handle both formats during the change, so no client or bank is forced to move on day one. The hub needs a clear mapping layer that turns an MT103 into a pacs.008, and a pacs.008 into an MT103 where the next bank still needs the old format. The mapping must handle the new structured address fields, the richer remittance information, and the UETR reference that tracks the payment end to end. Validation must check the new fields and give a clear error when data is missing. The design should log the original message and the mapped message, so operations can trace a payment. I would plan a phased move, with test partners first, then clients in groups, and a rollback plan if the rejection rate rises.

3. A payment is sent to the clearing system but no reply comes back. How should the hub handle this?

Model answer: The hub must never assume the payment failed, because it may have been processed by the clearing system. First, the hub should mark the payment as status unknown and keep it in a safe state, with no retry until the true status is known. Then the hub should run a reconciliation check, using the payment reference and the clearing system response file or query service. If the clearing system confirms the payment was accepted, the hub should update the status and tell the client. If the clearing system has no record of the payment, the hub can safely resend it, with the same reference. If the status is still unknown after the check, the hub should raise an alert to operations with the full payment details and the time of the last attempt.

4. How do you design straight through processing for a corporate payment file, and where should a payment stop for manual work?

Model answer: Straight through processing means a payment moves from file to clearing with no manual touch, when all checks pass. I would design the flow so the pain.001 file is validated on receipt, with a clear error list for any bad payments. Good payments should move through the payment hub, sanctions screening, fraud checks, core banking posting, and clearing without a manual step. A payment should stop for manual work only when it needs a human decision. That includes a sanctions hit that needs review, a fraud alert, a missing or unclear beneficiary detail, a value above a set limit, or a payment that fails validation and cannot be fixed by a rule. The manual queue should show the reason, the payment details, and the action needed, so operations can clear it fast.

5. Your bank connects to a new clearing system. What integration points and risks would you design for?

Model answer: I would start with the clearing system rules, such as message format, cut off times, value limits, and the settlement cycle. The payment hub needs a new adapter that turns the internal payment into the clearing format, and turns the clearing response into a pacs.002 style status. The hub also needs a link to core banking for posting, and a link to the nostro or settlement account for funding. I would design for the main risks, which are a failed connection, a message rejected by the clearing system, a settlement shortfall, and a timeout with no reply. The design should include a queue, a retry with care, a reconciliation check, and a clear alert to operations. I would also design a test plan with the clearing operator, using test payments across the full range of values and error cases, before any live payment is sent.

Advanced questions

1. Design a payment hub that must stay up when one data centre fails. How do you do it?

Model answer: I would design an active active service across two data centres, so both can process payments at the same time. Each payment should be stored in a shared data store that is copied to both sites, so no payment is lost if one site fails. The payment hub should use queues that survive a site failure, and each payment should have a unique reference so a retry after a failover does not create a duplicate. The design must handle the case where a payment was sent to clearing from the failed site but the reply was lost. In that case, the surviving site should check the payment status before it resends. I would set a clear recovery time objective and recovery point objective, and test the failover with live like volumes, including a test where the failure happens in the middle of a large file.

2. How do you design a hub that handles both instant payments and large batch files without one harming the other?

Model answer: I would keep the two flows separate in processing, even if they share the same hub. Instant payments need low latency and must be processed at once, while batch files need high throughput over a longer window. I would use separate queues and separate processing capacity for each flow, so a large payroll file cannot block an urgent instant payment. The design should set clear priorities, with instant payments taking the faster path and batch payments using the remaining capacity. Both flows should share the same validation, sanctions screening, and fraud checks, but the checks for instant payments must run in real time. I would also set separate limits and monitoring for each flow, so operations can see the volume, latency, and failure rate for instant and batch separately.

3. Core banking is old and slow, but the bank wants real time payments. How do you design around this limit?

Model answer: I would not ask core banking to do real time work it cannot do. Instead, I would put a fast payment layer in front of it. The payment hub would check the balance using a fast cache or a shadow balance that is updated from core banking regularly, with clear limits on how much can be spent before a fresh check. The hub would then send the payment to the clearing system at once, and post the debit to core banking as soon as it can, in the right order. If core banking is down, the hub should queue the posting and hold new payments once the safe limit is reached. The design must include a reconciliation check, so the fast layer and core banking always agree at the end of the day.

4. A vendor payment hub product must be integrated with your bank systems. What would your design cover?

Model answer: My design would cover the full flow, not only the vendor product. I would map how channels send payments to the vendor hub, how the hub calls core banking, sanctions screening, and fraud systems, and how it sends payments to each clearing system. I would define the message contracts, such as pain.001 in, pacs.008 out, and pacs.002 status back, with the exact fields and error codes. I would design the data store, so every payment has a full audit trail from intake to settlement. I would also design for vendor failure, with a queue, a safe stop, and a manual route if the hub is down. Security would cover authentication between systems, encryption, and access control. I would set the non functional needs, such as volume, latency, and recovery time, and agree how they will be tested.

5. How do you design sanctions and fraud checks so they are strong but do not delay every payment?

Model answer: I would design the checks as part of the payment flow, not as a step added at the end. The payment hub should send the payment details to the sanctions screening and fraud systems as soon as the payment is validated, so the checks run in parallel with other steps where possible. For low risk payments, such as a repeat payment to a known payee for a normal amount, the checks should return a fast pass. For higher risk payments, the checks should take longer and may hold the payment for review. I would design a clear risk score and a set of rules, so only the payments that need a human look are held. The design should include a manual queue with the reason for the hold, the data needed to clear it, and a time limit.

Expert questions

1. Design a global payment hub for a bank that operates in the UK, the US, and Singapore. What are the key design choices?

Model answer: The key choice is how much to centralise and how much to keep local. I would design one global hub for routing, tracking, and control, with local adapters for each clearing system, such as Faster Payments and CHAPS in the UK, Fedwire and ACH in the US, and FAST in Singapore. Each region needs its own nostro funding and its own cut off times, so the hub must know the local rules and the local time. The hub must handle different message formats, such as pacs.008 for SWIFT and local formats for domestic clearing, with a common internal model. Data must stay in the right region where the law requires it, so the design must split data by region. The hub must also run across time zones, with follow the sun support and a clear handover between operations teams.

2. Your bank is moving its payment hub to the cloud. What risks do you design for, and how do you prove the design is safe?

Model answer: I would design for the main cloud risks, which are loss of control over the platform, a cloud outage, data leaving the right region, and a security breach. The design should use more than one availability zone, so a single zone failure does not stop payments. It should encrypt data in transit and at rest, and control access with strong authentication. It should keep a copy of payment data in the bank, so the bank can recover even if the cloud service is down. I would also design for exit, so the bank can move the hub to another cloud or back in house. To prove the design is safe, I would test a zone failure, a network failure, and a security test, and I would run a full disaster recovery test with live like volumes.

3. Real time, batch, and file payments must all run on one hub. How do you keep the design simple and safe?

Model answer: I would use one common payment model for all three, with the differences handled at the edges. Every payment, whether it comes from an API, a file, or a channel, should be turned into the same internal payment record, with the same fields, the same validation, and the same status tracking. The intake layer would differ, with an API adapter, a file adapter, and a channel adapter, but the core hub would be the same. The core would handle routing, sanctions screening, fraud checks, core banking posting, and clearing. The clearing layer would differ by system, with adapters for instant, batch, and SWIFT routes. This design keeps the core simple and easy to test, while the adapters handle the differences. It also means a fix to validation or screening helps all payment types at once.

4. A critical vendor system fails during the peak morning payment run. How should the architecture respond?

Model answer: The architecture should detect the failure fast, stop new work safely, and give operations a clear path to recover. Monitoring should alert operations within seconds, with the affected payments listed by reference. The payment hub should queue new payments instead of dropping them, and should not retry blindly against a dead system. If the vendor system is the clearing link, the hub should check whether a backup route exists, such as a second clearing system or a manual route, and use it only for payments that meet the backup rules. If no backup exists, the hub should hold the payments safely and tell clients the new timing. When the vendor system returns, the hub should process the queue in order, check for duplicates, and reconcile each payment against the clearing record.

5. How do you design payment data so operations can trace any payment end to end, even across banks?

Model answer: I would design a single payment record that follows the payment from start to finish, with a unique internal reference and the UETR for cross border tracking. The record should hold the original instruction, each message sent and received, such as pain.001, pacs.008, pacs.002, and camt.053, with a timestamp for each step. The record should also hold the status at each step, the reason for any rejection or hold, and the user or system that acted. For cross border payments, the design should use SWIFT gpi tracking, so the bank and the client can see where the payment is in the chain. The data should be searchable by reference, amount, value date, payer, and payee, and it should be kept for the full period required by law.

Scenario

Business problem

A large bank runs a single payment hub that serves retail, corporate, and treasury payments. On a Monday morning, the hub starts to slow down. By 09:30, instant payments are taking three minutes instead of seconds, and a corporate pain.001 file with 12,000 payments is stuck in the queue. The operations team reports that the hub database is under heavy load, and the sanctions screening system is timing out on one in five checks. Clients are calling to ask where their payments are. The bank must restore normal service, clear the backlog safely, and design a fix so a morning peak cannot cause the same failure again.

Information to investigate

The architect should gather the hub queue depth by payment type, the processing time per payment, and the database load by query. The team should check the sanctions screening response times and error rates, and whether the timeouts are caused by load, a slow rule, or a failed link. The team should check the core banking posting times, the clearing submission times, and the number of retries the hub has made. The team should also check whether a large file or a single client caused the load, whether a recent change added a slow query, and whether the hub is retrying failed checks in a loop. The team should look at the logs for the first slow payment, to find when the problem started.

Questions to ask stakeholders

Ask operations which payments are stuck, which have been sent, and which are still unknown. Ask the sanctions screening team whether their system is slow, whether a rule changed, and what the safe fallback is. Ask the database team what queries are slow and whether a recent change added load. Ask the corporate client team which clients are affected and what they have been told. Ask technology whether a recent release changed the hub, the screening link, or the database. Ask risk whether any payments can bypass screening, and what the control rules allow. Ask the clearing team whether any payments have missed a cut off time.

Possible root causes

The cause may be a database bottleneck, such as a missing index or a slow query that runs for every payment. It may be a sanctions screening overload, where the screening system cannot handle the morning peak and times out. It may be a retry storm, where the hub retries a failed check again and again, adding more load. It may be a large file that was processed in one go, blocking the queue for instant payments. It may be a recent change that added a new validation or a new data lookup for every payment. It may also be a resource limit, such as too few hub workers for the morning volume, or a shared service that is also used by another system.

Recommended solution

First, protect instant payments by giving them a separate queue and separate workers, so a large file cannot block them. Next, stop the retry storm by limiting retries and adding a back off, so a failed check does not add load. Then work with the screening team to find the slow rule or the capacity gap, and agree a safe temporary limit on screening calls if the rules allow. Clear the backlog in order, starting with the oldest payments, and check each payment status before resending it, so no payment is paid twice. Fix the database bottleneck, such as adding an index or splitting a slow query. Then test the fix with a morning peak load test, with instant payments and a large file running at the same time. Finally, agree a runbook for the next peak, with queue limits, alerts, and a clear escalation path.

Data and technical considerations

The design needs separate queues for instant, batch, and file payments, with separate capacity and separate monitoring. Each queue needs a depth alert, a processing time alert, and a clear owner. The hub needs idempotency keys, so a retry after a timeout does not create a duplicate. The hub needs a safe state for a payment with an unknown status, with a reconciliation check before any resend. The sanctions screening link needs a timeout, a retry limit, and a circuit breaker that stops calls when the screening system is down, instead of flooding it. The database needs the right indexes for the queries the hub runs most, and a regular check for slow queries. All payment data, including the original message, the screening result, and each status change, must be logged with a timestamp.

Failure and recovery paths

If the hub fails again, the design should queue payments safely and tell clients the new timing, instead of dropping payments. If the sanctions screening system fails, the design should hold payments for review, unless risk has agreed a safe fallback. If the database fails, the design should switch to the standby database, with a check that no payment is lost or duplicated during the switch. If a payment is sent twice during recovery, the design should include a duplicate check and a recovery process with the beneficiary bank. If the backlog cannot be cleared before a cut off, the design should prioritise payments by value date and client impact, and tell affected clients the new value date. Every recovery step must be logged, with the time and the person who approved it.

Expected response

A strong candidate will protect instant payments first, stop the retry storm, and check each payment status before resending it. The candidate will name the likely causes, such as a database bottleneck, a screening overload, and a shared queue. The candidate will design separate queues, a circuit breaker, and idempotency, and will test the fix with a peak load test. The candidate will also set clear alerts and a runbook for the next peak. A weak candidate will suggest adding more servers without finding the cause, or will retry all failed payments at once without checking their status, which risks duplicates.

Interviewer evaluation criteria

The interviewer should check whether the candidate finds the cause with data, not with a guess. The interviewer should check whether the candidate can design separate queues, a circuit breaker, and idempotency. The interviewer should check whether the candidate knows how to handle a payment with an unknown status, and how to avoid a duplicate. The interviewer should check whether the candidate can set clear monitoring, alerts, and a runbook. The interviewer should also check whether the candidate can explain the design in plain language and work across operations, risk, and technology.

Weak vs strong answers

Example 1: How do you stop duplicate payments?

Question: A payment request times out. How do you make sure it is not paid twice?

Weak answer: I would retry the payment a few times until it works. If it is paid twice, operations can fix it later by asking the beneficiary bank to return the extra money. Most clients will not notice a duplicate if the amount is small, and we can handle it as an exception.

Strong answer: I would use an idempotency key on each payment instruction, stored by the payment hub before the payment is sent. If the same key arrives again, the hub returns the original result instead of creating a new payment. If the first request reached clearing but the reply was lost, I would check the payment status by reference before any resend. I would also add duplicate detection on payer, payee, amount, and value date, and test the design with a forced timeout.

Why the strong answer is better: The strong answer prevents the duplicate by design, using an idempotency key and a status check. The weak answer accepts the duplicate and leaves the fix to operations after the money has moved, which is slow, costly, and risky for the client.

Example 2: How do you design for a system failure?

Question: What happens to payments if the payment hub database fails?

Weak answer: I would add more servers and hope the database does not fail. If it does fail, we can restart it and resend the payments from the start. The clients may see a delay, but the payments should go through in the end if we retry them all.

Strong answer: I would design an active active hub across two sites, with the payment data copied to both sites. Each payment would be stored safely before it is sent, with a unique reference. If one site fails, the other site takes over, checks the status of each payment in flight, and only resends payments that clearing has not received. I would test the failover with live like volumes, including a failure in the middle of a large file, and set a clear recovery time objective.

Why the strong answer is better: The strong answer names a concrete design, with data copied across sites, a status check before resend, and a tested failover. The weak answer relies on hope and a blind resend, which risks lost payments and duplicates.

Follow-up questions

  1. You said you would use an idempotency key. Where exactly would you store it, and for how long? Hint: With the payment record, kept for the full reconciliation period.
  2. How would you test that a failover does not create duplicate payments? Hint: Fail in the middle of a large file, then reconcile every payment.
  3. What would you do if the sanctions screening system is down for an hour? Hint: Hold payments safely, check the agreed fallback with risk, and alert operations.
  4. How do you decide between a queue and a direct call between two systems? Hint: Use a queue when the payment must survive a failure or a peak.
  5. How would you prove your hub can handle twice the current peak volume? Hint: Load test with real message types, real checks, and real clearing links.

Practical exercises

  1. Draw a hub design. Draw an end to end payment hub for a UK bank, showing channels, validation, screening, core banking, and clearing. Label each message, such as pain.001, pacs.008, and pacs.002, and mark where a payment can fail and how it recovers.
  2. Design an idempotency test. Write a test plan for a payment API that times out. List the steps, the expected result for each retry, and how you would prove no duplicate was created. Include the status check you would run before any resend.
  3. Run a failure drill. Take the Monday morning scenario in this track. Write the first five actions you would take, the data you would check, and the design change you would make. Then write the runbook for the next peak, with alerts and escalation steps.
