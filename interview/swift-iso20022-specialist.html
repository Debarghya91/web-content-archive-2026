SWIFT and ISO 20022 Specialist

Role expectations

A SWIFT and ISO 20022 Specialist owns message standards across the bank. The role covers MT to MX migration, field level mapping, CBPR+ compliance, message validation, and support for payment, reporting and investigation flows. You work with the payment hub, core banking, SWIFT Alliance, correspondent banks and the clearing house to make sure every message is correct, complete and compliant. The hiring manager expects deep knowledge of message structure, not just general awareness. You must read a pacs.008, pain.001, camt.053 or MT103 field by field, explain what each field means, and spot a mapping error that could delay or misroute a payment. You must also explain a change to operations and technology in plain language, and test it properly before it goes live. You keep a record of mapping decisions and standards interpretations, so the next change starts from evidence rather than memory, and you review each new standards release for its effect on live payment flows.

Competency framework

  • Message structure knowledge: read and explain MT and MX messages field by field, including pacs, pain, camt and head.
  • MT to MX mapping: map MT103, MT202, MT202 COV, MT900, MT910, MT940 and MT950 to their ISO 20022 equivalents.
  • CBPR+ compliance: apply CBPR+ usage guidelines, mandatory fields, and character and format rules.
  • Data quality and validation: find truncation, character set and field length errors before they reach a counterparty.
  • Standards change management: assess a SWIFT standards release, identify the impact, and plan the change.
  • Testing and certification: design test cases, run SWIFT test scenarios, and prove a change works.
  • Troubleshooting: trace a rejected or misrouted message to the exact field or rule that caused it.
  • Stakeholder translation: explain a standards change to operations, technology and business teams in plain language.

Learning objectives

  • Read a pacs.008, pain.001, pain.002, camt.053, camt.054 and camt.056 and explain each key field.
  • Map an MT103 to a pacs.008 and an MT202 to a pacs.009, field by field.
  • Apply CBPR+ rules for mandatory fields, structured addresses and character sets.
  • Identify the cause of a message reject from a pacs.002 reason code and the underlying field error.
  • Explain the difference between MT202 and MT202 COV and when each is used.
  • Assess the impact of a SWIFT standards release on the bank's messages and interfaces.
  • Design a test pack for a message change, including valid, invalid and boundary cases.
  • Advise operations on how to repair a message that failed validation.

Beginner questions

1. What is the difference between an MT103 and a pacs.008?

An MT103 is the SWIFT MT format for a single customer credit transfer. A pacs.008 is the ISO 20022 XML format for the same business purpose. Both carry the debtor, the creditor, the amount, the currency and the remittance information. The pacs.008 is structured XML, so each piece of data sits in a named element, which makes it easier to validate and to process automatically. The MT103 is a flat text format with numbered fields such as field 50 for the ordering customer and field 59 for the beneficiary. Under CBPR+, banks are moving from MT103 to pacs.008 for cross border payments. The business meaning is the same, but the format, the field names and the validation rules are different.

2. Why does ISO 20022 use structured addresses, and why does it matter?

A structured address splits the address into separate elements such as street name, building number, town, postcode and country. A free text address puts the whole address in one or two lines, which is hard for a system to read reliably. Structured data lets a sanctions screening system, a payment hub and a receiving bank find the town and country without guessing. Under CBPR+, structured addresses are required for many cross border payments, because poor address data causes rejects, screening delays and manual repair. If you send an unstructured address where a structured one is required, the payment can be rejected by the next bank. Good address data saves time and reduces risk.

3. What is a pacs.002, and when would you see one?

A pacs.002 is a payment status report. You see one when a bank in the payment chain accepts or rejects a payment instruction. It carries the original payment reference, a status code such as ACCP for accepted or RJCT for rejected, and a reason code when the payment failed. In a SWIFT or CBPR+ flow, the pacs.002 is the formal feedback that tells the sending bank what happened. Operations uses it to confirm acceptance, to find the reason for a reject, and to decide whether to repair and resend. Without the pacs.002, the sending bank would not know whether the payment was accepted downstream.

4. What does CBPR+ mean in simple terms?

CBPR+ stands for Cross Border Payments and Reporting Plus. It is the SWIFT community's set of usage guidelines for ISO 20022 messages in cross border payments. It tells banks exactly which fields are mandatory, which are optional, and how each field must be used in a pacs.008, pacs.009 or camt.053. Before CBPR+, different banks used ISO 20022 in different ways, which caused rejects and manual work. CBPR+ creates one common way of using the messages, so a payment sent by a bank like Standard Chartered can be read correctly by a bank like BNY Mellon. It also sets the timetable for moving from MT to MX messages.

5. A message is rejected for an invalid character. What is the likely cause?

ISO 20022 messages use a restricted character set, and some characters that are normal in free text are not allowed. Common problems are characters such as the forward slash in the wrong place, an accented letter, or a symbol that the CBPR+ character set does not permit. The sending system may have passed through a character from the customer instruction without converting it. To fix it, find the field named in the reject, identify the invalid character, and replace it with an allowed equivalent or remove it. Check the CBPR+ character rules before resending. Test the fix with the exact character, because the same error will repeat if the source system keeps sending it.

Intermediate questions

1. Map the key fields of an MT103 to a pacs.008. What do you check first?

Start with the parties. MT103 field 50, the ordering customer, maps to the debtor in the pacs.008. Field 59, the beneficiary customer, maps to the creditor. Field 32A, the value date, currency and amount, maps to the interbank settlement amount and the instructed amount. Field 70, remittance information, maps to the remittance information element. Field 71A, details of charges, maps to the charge bearer element. Then check the agent chain: fields 52, 53, 54, 56 and 57 map to the debtor agent, intermediary agents and creditor agent. Check that no data is lost, especially the ultimate debtor and ultimate creditor, which have no direct MT103 equivalent in older usage. Validate the result against CBPR+ before testing.

2. What is the difference between MT202 and MT202 COV, and why does it matter?

An MT202 is a general financial institution transfer. It moves money between banks for their own account, with no underlying customer payment. An MT202 COV is a cover payment. It moves the funds for a customer payment that travels separately, usually as an MT103. The COV carries the customer details from the underlying payment, including the ordering customer and the beneficiary, so that sanctions screening and transparency rules are met. Using a plain MT202 for a cover payment hides the customer information, which breaches transparency rules and can cause the payment to be blocked. The ISO 20022 equivalent of the MT202 COV is the pacs.009 with cover information.

3. A pacs.008 is rejected because the creditor agent BIC is missing. How do you fix it?

First confirm whether the BIC is genuinely missing or whether it is present but in the wrong element. Check the source instruction and the payment hub mapping to see whether the BIC was captured at all. If the customer did not provide a BIC, check whether the payment can be routed by another identifier, such as a national clearing code, or whether the BIC must be requested. If the BIC exists in the source but the mapping dropped it, fix the mapping and test it with the same payment type. Check the CBPR+ rule for that payment type, because the creditor agent BIC is mandatory in some flows and optional in others. Do not invent a BIC, and do not resend until the field is correct.

4. How do you test a change from MT to MX for one payment type?

Build a test pack that covers the real range of that payment type. Include a simple domestic style payment, a payment with an intermediary bank, a payment with charges, a payment with a long remittance reference, and a payment with a structured address. For each case, send the MT version and the MX version and compare the business outcome: same debtor, same creditor, same amount, same value date and same charges. Add negative cases: a missing mandatory field, an invalid character, and an amount over the field limit. Run the pack against the SWIFT test environment and the internal payment hub test system. Record the expected result for each case before you run it, so a pass means something.

5. A correspondent bank rejects your pacs.008 for a missing ultimate creditor. What do you do?

Check the original customer instruction to see whether the ultimate creditor was provided. If it was provided but the mapping dropped it, fix the mapping in the payment hub and retest. If it was not provided, ask the customer or the originating channel for the information. Check the CBPR+ rule to confirm whether the ultimate creditor is mandatory for this payment type and this corridor. Do not resend without the field if the rule requires it, because the receiving bank will reject it again. Tell operations the exact field, the rule and the fix, so the repair is done once and done correctly. Log the incident so the mapping gap is tracked.

Advanced questions

1. A SWIFT standards release changes a field from optional to mandatory. How do you manage the change?

Start with the SWIFT standards release notes and identify every message and field affected. Check which of the bank's payment types use that field, and whether the source systems capture the data today. If the data is not captured, work with the channel and payment hub teams to add it, and agree a default or a repair process where the data is genuinely unavailable. Update the mapping, the validation rules and the test pack. Test with the SWIFT test environment and with key correspondent banks. Communicate the change to operations with examples, including what happens if the field is missing. Plan the go live date around the SWIFT deadline, and keep a rollback plan if the change fails in production.

2. Your bank receives a pacs.008 with a truncated remittance reference. What is the impact and the fix?

A truncated remittance reference means the beneficiary cannot match the payment to the correct invoice or account. The money may arrive but sit unmatched, which causes queries, delays and manual work for the beneficiary. The cause is usually a field length limit in the sending system or in the mapping. Find where the truncation happened by comparing the original instruction, the hub record and the received pacs.008. If the sending bank truncated it, ask them to send the full reference in a structured remittance element or as a separate message. If your own system truncated it on receipt, fix the field length and the mapping. Tell the beneficiary what happened and give them the full reference so they can match the payment.

3. How do you handle a payment that needs both a pacs.008 and a camt.056?

A camt.056 is a payment cancellation request. You send it when a pacs.008 has already been sent but the payment must be stopped, for example because it was sent in error or the details are wrong. The camt.056 must carry the original pacs.008 reference, the amount, and the reason for cancellation. The receiving bank replies with a camt.029 resolution of investigation, which says whether the cancellation succeeded or failed. If the payment has already been credited, cancellation may not be possible, and a return via pacs.004 may be needed instead. Track the camt.056, the camt.029 and the original pacs.008 together, so operations can see the full story in one place.

4. Two banks interpret the same CBPR+ rule differently, and payments keep failing between them. How do you resolve it?

Get the evidence first. Collect the rejected pacs.008 messages, the pacs.002 reason codes, and the exact field each bank says is wrong. Compare both readings against the CBPR+ usage guidelines and the SWIFT MyStandards record for that message. Raise the difference with both banks' standards teams, and agree a single interpretation in writing. If the difference is a genuine gap in the guidelines, raise it through the SWIFT community process. In the meantime, agree a temporary workaround that both sides accept, such as populating an optional field that satisfies both readings. Test the agreed format with a small number of live payments before returning to full volume.

5. A high value payment fails validation because the amount exceeds a field limit in the hub. What do you check?

Check the amount, the currency and the field definition in the payment hub and in the pacs.008 schema. The limit may be a genuine CBPR+ field limit, a hub configuration limit, or a mapping error that puts the amount in the wrong element. Check whether other high value payments of the same type have succeeded, and find the threshold where they start to fail. If the limit is a configuration error, fix it and test with the exact amount that failed. If the limit is real, split the payment only if the customer agrees and the business rules allow it, because splitting changes the payment instruction. Tell the customer and the business what happened, and do not release the payment until the validation passes cleanly.

Expert questions

1. Design the migration of a payment corridor from MT to MX. What are the key stages?

Start with scope: which payment types, which currencies, which counterparties and which volumes use the corridor. Map every MT field to its MX equivalent, and list the fields that have no direct equivalent, such as the ultimate parties. Agree the CBPR+ usage rules for the corridor with the correspondent bank. Build the mapping in the payment hub, and create a test pack that covers the full range of real payments on that corridor. Test in the SWIFT test environment, then run a parallel pilot with a small number of live payments and compare the outcomes. Plan the cutover date, the rollback plan, and the communication to operations and customers. After cutover, monitor rejects daily for the first month and fix mapping gaps quickly.

2. A pacs.008 passes your validation but is rejected by the receiving bank for a rule you do not recognise. How do you investigate?

Ask the receiving bank for the exact pacs.002 reason code, the field name, and the rule reference. Compare their rule against the CBPR+ guidelines and your own validation rules. Check whether the receiving bank applies a local market practice or a stricter internal rule on top of CBPR+. Review the SWIFT MyStandards record for that message version, because the rule may come from a newer version. If their rule is valid and yours is missing, update your validation and tell operations. If their rule is wrong, share the guideline reference and agree a correction. Do not keep resending the same message while the rule is disputed, because each reject creates more manual work.

3. How do you prove that a mapping change has not lost data?

Build a before and after comparison for a representative set of payments. For each payment, list the business data in the source message: debtor, creditor, ultimate parties, amount, currency, value date, charges, remittance information and agent chain. Then list the same data in the mapped message, and confirm each item matches exactly. Include edge cases: long names, long references, special characters, and payments with intermediaries. Run the comparison automatically where possible, and review the exceptions by hand. Keep the evidence so an auditor can follow it. A mapping change that passes this test can go live with confidence. One that cannot should not.

4. Your bank must support both MT and MX for the same corridor during a transition. What are the risks?

The main risk is divergence: the MT and MX versions of the same payment can carry different data if the mapping is not kept in sync. A field added to the MX version may be missing from the MT version, or a charge option may be interpreted differently. There is also a routing risk, because the bank must choose the right format for each counterparty. A third risk is testing: every change must be tested in both formats, which doubles the work. Control the risk with a single source of truth for the business data, a shared mapping table, and a daily reconciliation of MT and MX volumes. Agree a clear end date for the dual running period, so it does not become permanent.

5. A new market practice requires structured remittance information for a key corridor. How do you implement it?

First read the market practice document and confirm which remittance elements are required, which are optional, and what format each one must use. Check whether the bank's channels capture structured remittance data today, and whether the payment hub can pass it through to the pacs.008. If the data is not captured, work with the channel team to add the fields and with the business to explain the change to customers. Update the mapping, the validation and the test pack, and test with the correspondent bank on that corridor. Communicate the change to operations with real examples, and monitor the first weeks of live traffic for rejects. A structured remittance change only works if the customer provides the data in the first place.

Scenario

A bank like JP Morgan or Goldman Sachs is migrating its US dollar correspondent payments from MT to MX under CBPR+. During the pilot, the receiving bank rejects 30 percent of the pacs.008 messages. The pacs.002 reason codes point to address and party identification problems, but the operations team says the same payments worked fine as MT103 messages last week.

Business problem

The migration is at risk. If the reject rate stays high, payments will be delayed, customers will complain, and the bank may miss the CBPR+ migration deadline. The operations team is losing confidence in the new format, and the business is asking whether to pause the migration.

Information to investigate

Collect the rejected pacs.008 messages and their pacs.002 reason codes. Compare each rejected pacs.008 with the equivalent MT103 from the previous week, field by field. Check the address data: is it structured or free text, and does it meet the CBPR+ rules for this corridor? Check the party identification: debtor, creditor, ultimate debtor, ultimate creditor, and the agent chain. Check the mapping in the payment hub to see whether any field is dropped or truncated. Check the SWIFT MyStandards record for the message version in use.

Questions to ask stakeholders

Ask the receiving bank which exact fields failed and which CBPR+ rule they applied. Ask the payment hub team whether the mapping was tested with structured addresses and ultimate parties. Ask the channel team whether the source systems capture structured address data. Ask operations for examples of payments that passed and payments that failed, so the pattern is clear. Ask the standards team whether the corridor has a local market practice on top of CBPR+.

Possible root causes

The mapping drops the ultimate creditor, which the MT103 carried in a free text field. The address is sent as free text where CBPR+ requires a structured address. The debtor agent or creditor agent BIC is missing or mapped to the wrong element. The payment hub truncates a long name or reference. The receiving bank applies a stricter local rule that the sending bank did not know about.

Recommended solution

Pause the pilot for the affected payment types, but do not abandon the migration. Fix the mapping for the ultimate parties and the structured address, and add validation that blocks a pacs.008 with missing mandatory party data. Build a test pack from the real rejected payments, and retest with the receiving bank before resuming. Agree the address and party rules for the corridor in writing with the correspondent bank. Resume with a small volume, monitor the reject rate daily, and scale up only when the rate falls to the agreed level.

Data and technical considerations

Use the pacs.008, the pacs.002 and the equivalent MT103 as your evidence set. Keep a mapping table that shows every MT field and its MX destination, and mark the fields that are new or changed. Check character sets, field lengths and mandatory flags against CBPR+. Do not change the mapping in production without a test record that proves the fix works.

Failure and recovery paths

If the fix does not reduce the reject rate, fall back to MT103 for the affected corridor under the agreed SWIFT coexistence rules, and replan the migration. If a payment is rejected after the fix, repair the specific field and resend as a new instruction with a new reference, never by editing the original message in flight. If a customer payment is delayed, tell the customer the reason and the new expected date.

Expected response

A strong candidate compares the MT and MX messages field by field, names the party and address rules, and proposes a test pack built from the real failures. A weak candidate blames the receiving bank, or suggests resending the same messages without a fix.

Interviewer evaluation criteria

Look for field level knowledge, correct use of CBPR+ and SWIFT MyStandards, a structured test approach, and a clear cutover and rollback plan. Award credit for naming the ultimate parties, the structured address rule, and the mapping table. Mark down answers that stay at a general level, or that propose resending without a fix.

Weak vs strong answers

Question: What is the difference between MT and MX?

Weak answer: MT is the old format and MX is the new format. MX is XML and it is better. Banks are moving to MX now because SWIFT told them to.

Why it is weak: it states the obvious and adds nothing. It names no message, no field and no business difference. The interviewer cannot tell whether the candidate has ever read a message.

Strong answer: An MT103 and a pacs.008 carry the same business payment, but the pacs.008 is structured XML with named elements for the debtor, creditor, agents, amount and remittance information. That structure makes validation and automated processing more reliable. Under CBPR+, the pacs.008 also carries structured addresses and ultimate party data that the MT103 often held in free text. The migration matters because a field that was free text in MT must now be mapped to a specific MX element, and a mapping error can reject the payment.

Why it is strong: it names the messages, the structure difference, and the practical consequence. It shows the candidate understands both the format and the business risk of the change.

Question: A message is rejected. How do you find the cause?

Weak answer: I would ask IT to look at it. They know the system and they can fix the mapping. I would wait for them to tell me what went wrong.

Why it is weak: it hands the problem to someone else and shows no method. A specialist must be able to read the message and find the field.

Strong answer: I would read the pacs.002 to get the reason code and the field it points to. Then I would open the pacs.008, find that field, and compare it against the CBPR+ rule and the source instruction. If the field is missing, I would check whether the source captured it. If the field is present but wrong, I would check the mapping. I would tell operations the field, the rule and the fix, so the repair is done correctly the first time.

Why it is strong: it follows the evidence from the reason code to the field to the rule to the source. It shows the candidate can diagnose the problem and explain the fix.

Follow-up questions

  1. Which field would you check first if a pacs.008 is rejected for party data? Hint: start with the debtor and creditor elements.
  2. How would you explain a structured address to a customer? Hint: use street, town, postcode and country as separate items.
  3. What is the risk of dropping the ultimate creditor in a mapping? Hint: think about transparency and screening.
  4. How would you test a mapping change before go live? Hint: use real rejected payments as test cases.
  5. When would you use a pacs.009 instead of a pacs.008? Hint: think about bank to bank transfers and cover payments.

Practical exercises

  1. Take a sample MT103 and map it field by field to a pacs.008. Write down each mapping, mark any data that has no direct equivalent, and note what CBPR+ requires for each field.
  2. Take a pacs.008 that fails validation and find the error. Write the field name, the CBPR+ rule it breaks, and the corrected value. Repeat with three different error types.
  3. Write a one page impact note for a SWIFT standards release that makes a field mandatory. List the affected messages, the systems that must change, the test cases you would run, and the message you would send to operations.
